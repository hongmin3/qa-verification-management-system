이 문서는 `qa-verification-management-system`의 **QA Intelligence Agent** 기능이 어떻게 동작해야 하는가를 정의한다.

공통 사양(시스템 구성·전체 흐름·비기능·데이터·설정·오류·보안)은 상위 `SPEC.md`에 있고 여기서 되풀이하지 않는다.
절 번호는 상위 문서와 같은 뜻이다. 빠진 번호(3·4·6~10)는 공통 사양이라 상위 문서에 있다.

파일 경로는 모두 프로젝트 루트 기준으로 적는다(`specs/` 기준이 아니다). 검사기도 루트 기준으로 확인한다.

> **참고** 처음 읽는다면 1절 "이 기능은"과 흐름도, 5절 "요구사항 지도"를 먼저 본다. 그다음 필요한 카드만 읽는다.
> 이 기능은 상위 SPEC 5.4절 "VXvue 일일 QA 점검"을 바탕으로 한다. 수집·잠금·작업 폴더·메일 같은 공통 부분은 그 절의 카드를 그대로 따른다.

## 1. 목적

QA 담당자가 매일 Polarion 전체를 직접 훑지 않아도, 전날 대비 실제로 의미 있는 변경만 자동으로 찾아 최신 사양과 과거 이슈를 근거로 짧게 정리해 준다.

AI 가 QA 결정을 대신하지 않는다. 자동 실행이 하는 일은 "변경 탐지 → 자료 조사 → 비교 → 근거 정리" 까지다. 판단과 반영은 사람이 한다.

TC·Checklist·매뉴얼은 사람이 손으로 넣는 자료라 최신이 아니거나 틀릴 수 있다. 그래서 자동 실행은 이 자료와 비교하지 않는다. TC 와 맞춰 보는 일(기존 TC 검토, 검증 TC 초안)은 사람이 결과 화면의 버튼을 누를 때만 한다(사용자 결정 2026-10-02).

이유: 사양 변경마다 TC 와 비교하던 분석은 작업 하나에 토큰 176만~516만 개를 써서 Claude 주간 한도를 다 썼다(2026-10-01·02 실행 기록).

### 이 기능은

- 서버가 평일 04:00(한국 시간)에 스스로 한 번 돈다. 주말과 대한민국 공휴일에는 돌지 않는다. QA 담당자는 화면의 [변경사항 점검하기] 버튼으로 같은 일을 바로 돌릴 수도 있다.
- Polarion 에서 SRS 전체와 이슈 전체를 읽어 어제 저장한 사본(스냅샷)과 비교한다. 바뀐 것만 "변경 이벤트"로 남긴다.
- 변경 이벤트의 종류에 따라 신규 이슈 분석, 수정 완료(Fixed) 이슈 분석, Spec 판정 이슈 분석, 새 댓글 분석, 사양 변경 분석을 돌린다.
- 결과는 `/qa-agent` 화면에서 본다. 카드마다 결론 한 가지, 한두 문장 요약, QA 할 일 3줄까지가 보인다(REQ-QAINTEL-033).
- 사양 변경 분석 화면의 [기존 TC 검토], 수정 완료 이슈 분석 화면의 [검증 TC 초안 만들기]를 누르면 그때 TC 와 비교한다.
- 바뀐 것이 하나도 없으면 AI 를 한 번도 부르지 않고 "변경사항 없음"으로 끝난다.

```flow
평일 04:00 예약 또는 [변경사항 점검하기] -> Polarion 수집(SRS 전체·이슈 전체) -> 스냅샷 비교 -> 변경 이벤트
변경 이벤트 -> 분석 대상 고르기 -> 후보 압축(Exact -> BM25, TC·매뉴얼 제외) -> Claude Skill(격리 작업 폴더) -> 근거 검증 -> SQLite -> /qa-agent 대시보드
/qa-agent 대시보드 -> 사람이 [기존 TC 검토]·[검증 TC 초안 만들기] -> TC 와 비교(요청 실행) -> SQLite
변경 이벤트 -(바뀐 것 없음)-> 변경사항 없음(AI 호출 0회) -> /qa-agent 대시보드
Polarion 수집 -(실패·0건·급감)-> 스냅샷 기준 유지 -> 다음 실행에서 다시 비교
Claude Skill -(실패)-> 이벤트 보존 -> 다음 실행에서 다시 분석
Claude Skill -(사용량 한도)-> 남은 AI 중지·초기화 시각 표시 -> 초기화 뒤 다시 분석
```

### 이 기능에서 쓰는 말

| 용어 | 뜻 |
|---|---|
| 제품 설정 | `config/products/<slug>.yaml`. 제품마다 다른 Polarion 프로젝트·조회식·필드 이름·연구소 결과 값·Checklist 형식을 적는다 |
| 공통 모델 | Polarion 원본 필드 이름을 제품 설정으로 바꿔 만든 공통 모양의 SRS(`SpecificationItem`)·이슈(`IssueItem`)·댓글(`IssueComment`) 기록이다. 분석 엔진은 원본 필드 이름을 모른다 |
| 연구소 결과 | 이슈의 연구소 검토 결과. VXvue 원본 필드는 `rndReviewResult` 이고, 제품 설정의 대응표로 공통 값(`FIXED`, `SPEC`, `NOT_BUG`, `DUPLICATE`, `PENDING`, `NO_ACTION`)으로 바꾼다 |
| 이슈 스냅샷 | 그날 읽은 이슈 전체를 저장한 파일(`data/daily_qa/snapshots/<slug>/issues/<날짜>.json`)이다 |
| 기준 스냅샷 | 비교할 전날 스냅샷이 없어 오늘 것만 저장한 상태다. 이때는 이벤트를 만들지 않는다 |
| 변경 이벤트 | 스냅샷 비교로 찾은 변경 하나(`qa_change_events` 한 줄)다. 종류(`event_type`), 바뀌기 전·후 값, 바뀐 필드, AI 분석이 필요한지와 그 이유를 담는다 |
| 분석 종류 | 이벤트를 받아 돌리는 분석이다. 신규 이슈(`NEW_ISSUE`), 수정 완료 이슈(`FIXED_ISSUE`), Spec 판정 이슈(`SPEC_DECISION`), 새 댓글(`COMMENT`), 사양 변경(`SPEC_COVERAGE`)이 있다 |
| 요청 실행 | 사람이 버튼이나 명령으로 한 가지만 부탁한 실행이다. 기존 TC 검토(`TC_CHECK`), 검증 TC 초안(`TC_DRAFT`), 매뉴얼 점검이 있다. 이때만 TC·매뉴얼을 AI 에 보낸다 |
| 결론 단계 | 화면에 보이는 결론이다. `사양과 다름`, `검토 필요`, `근거 부족`, `참고`, `문제 없음` 다섯 가지다(REQ-QAINTEL-033) |
| 후보 압축 | 이슈 전체를 AI 에 넘기지 않고, 코드가 Exact → BM25 검색으로 관련 후보만 골라 넣는 것이다 |
| Coverage | 기존 Checklist·TC 가 바뀐 사양의 핵심 동작과 Expected Result 를 실제로 검증하는지다 |
| 변경사항 없음 | 수집은 성공했고 변경 이벤트가 하나도 없는 실행 결과(`NO_CHANGE`)다 |

## 2. 범위

### 포함

- 예약 실행(평일·공휴일 제외)과 화면의 수동 실행
- SRS·이슈 전체 수집, 스냅샷 저장·비교, 변경 이벤트 저장과 재시도
- 다섯 가지 자동 분석과 근거 검증
- 사람이 요청할 때만 도는 기존 TC 검토·검증 TC 초안·매뉴얼 점검과 초안 Excel
- `/qa-agent` 대시보드, 분석 상세 화면, 점검 기록 보기 화면, 기간 분석 조회 화면
- 대시보드 위쪽의 수동 업로드 지식 문서 목록(업로드 날짜 포함)
- 제품 설정으로 다른 제품을 붙이는 구조(제품별 데이터 분리)

### 제외

- Polarion 에 쓰기. 이슈 닫기, 필드 수정, 댓글 달기 같은 일은 하지 않는다(REQ-DAILY-002).
- 원본 TC·Checklist 파일 수정. 초안은 별도 Excel 로만 만든다.
- 승인·거절·근거 추가 필요·검토자 입력·질문 답변 화면. 1차 개편에서 화면에 보이지 않는다. 옛 기록은 표에 그대로 남는다.
- 사용을 종료한 단일 이슈 분석. 현재 화면·API는 상위 SPEC의 REQ-QAAGENT-016을 따른다.

### REQ-QAINTEL-001 예약 실행과 공휴일 건너뛰기

**하는 일** 제품별 자동 점검 모드(REQ-QAINTEL-038)에 맞춰 아침에 점검 프로세스를 띄운다. 주말과 대한민국 공휴일에는 띄우지 않고 로그만 남긴다.

**언제** 앱 안의 예약 기능이 `config.yaml` 의 `daily_qa.schedule` 요일·시각(기본 `mon-fri`, `04:00`, 한국 시간)에 깨어난다.

**순서**

1. 활성 제품 목록(`daily_qa.products`, 없으면 `daily_qa.product` 하나)마다 예약을 하나씩 등록한다. 예약 이름은 `qa_agent_<slug>` 이다(예: `qa_agent_vxvue`).
2. 깨어나면 오늘 날짜가 공휴일인지 로컬 공휴일 표(`config/holidays/kr.yaml`)와 추가 휴일(`daily_qa.schedule.extra_holidays`)로 확인한다. 외부 AI 나 웹 검색으로 공휴일을 판단하지 않는다.
3. 공휴일이면 별도 프로세스를 띄우지 않는다. 앱 로그에 `qa_agent_skipped reason=holiday product=<slug> date=<날짜> name=<공휴일 이름>` 을 남긴다.
4. 공휴일이 아니면 REQ-DAILY-001 과 같이 `scripts/run_daily_qa.py --product <slug>` 를 분리된 별도 프로세스로 띄운다. FastAPI 웹 프로세스 안에서 분석을 돌리지 않는다.

> **주의** 공휴일 표에 올해가 없으면 고정 공휴일(신정·삼일절·어린이날·현충일·광복절·개천절·한글날·성탄절)만 보고, 앱 로그에 `qa_agent_holiday_table_missing year=<연도>` 경고를 남긴다. 음력 공휴일과 대체공휴일은 매년 표에 더해야 한다.

**설정**

| 키 | 기본값 | 뜻 |
|---|---|---|
| `daily_qa.schedule.enabled` | `true` | `false` 면 정시 예약·예약 만회·사용량 한도 뒤 자동 재개를 모두 막는다. 제품별 화면 설정으로 켤 수 없다. [변경사항 점검하기]은 가능하다 |
| `daily_qa.products` | `[daily_qa.product]` | 예약을 등록할 제품 이름 목록 |
| `daily_qa.schedule.skip_holidays` | `true` | 공휴일에 예약 실행을 건너뛸지 |
| `daily_qa.schedule.holiday_calendar` | `kr` | 공휴일 표 이름(`config/holidays/<이름>.yaml`) |
| `daily_qa.schedule.extra_holidays` | `[]` | 회사 휴무일처럼 표에 없는 쉬는 날(`YYYY-MM-DD`) |

**지킬 것**

- 공휴일 건너뛰기는 예약 실행에만 적용한다. 사람이 [변경사항 점검하기]를 누르면 공휴일에도 돈다(REQ-QAINTEL-021).
- 예약 시각에 앱이 꺼져 있었으면 앱이 다시 돌 때 오늘 몫을 한 번 띄운다(REQ-QAINTEL-035).
- 예약 시각은 업무 시간 전인 04:00 이다(2026-10-14 에 07:30 에서 바꿈).

  이유: 점검은 Claude Team 계정의 5시간 사용량을 함께 쓴다. 2026-10-14 07:30 실행 한 번이 그 사용량을 다 써서 같은 계정의 챗봇·화면 AI 기능이 12:30 까지 막혔다. 04:00 에 돌면 사용량 창이 업무 시작 전(09:00)에 끝난다.
- 서버와 담당자 PC 가 같은 점검을 두 번 하지 않게, 예약은 한 곳에서만 켠다. 2026-10-13 부터 운영 서버가 맡고, 담당자 PC 는 `config.local.yaml` 에서 `daily_qa.schedule.enabled: false` 로 끈다.

  이유: 두 곳이 모두 돌면 같은 변경을 두 계정의 사용량으로 두 번 분석하고 요약 메일도 두 번 간다.

### REQ-QAINTEL-002 제품 설정과 공통 모델

**하는 일** Polarion 원본 필드 이름과 연구소 결과 값을 제품 설정에서 읽어 공통 모델로 바꾼다. 분석 엔진·이벤트 감지·저장·대시보드는 원본 필드 이름(`oldId`, `descriptionKR`, `rndReviewResult`, `occurrenceCause`, `actionDetails` 등)을 모른다.

**입력** 제품 설정 `config/products/<slug>.yaml` 의 두 절이다.

| 절 | 담는 것 |
|---|---|
| `alm` | Polarion 프로젝트(`project_id`), 조회식(`queries.srs`, `queries.issue`), 필드 이름(`fields.srs.*`, `fields.issue.*`), 관계 이름(`relations.*`), 연구소 결과 대응표(`rd_result_mapping`) |
| `qa_intelligence` | 사용 여부, QA 규칙 판(`rules.supported_rev`), 제품 규칙 Skill(`rules.product_skill`), Regression 축, Checklist 형식(`checklist`), 무시할 댓글 모양(`comment_noise_patterns`) |

**순서**

1. 제품 설정을 읽어 제품 프로필을 만든다. `alm` 절이 없으면 `config.yaml` 의 `daily_qa.polarion.project_id`·`srs_query`·`issue_query` 를 쓴다(예전 설정과 호환).
2. 필드 이름을 적지 않은 항목은 Polarion 표준 필드 이름(`id`, `title`, `status`, `severity`, `description`, `created`, `updated`, `linkedWorkItems`, `comments`)을 쓴다. 제품 고유 필드(Legacy 번호, 연구소 결과, 재현 절차, 발생 원인, 조치 내용, 발생·목표 버전)는 제품 설정에 적은 것만 읽는다.
3. 한 항목에 이름을 여러 개 적으면 앞에서부터 값이 있는 첫 필드를 쓴다.

   > **예시** VXvue 는 SRS 본문을 `[descriptionKR, description]` 으로 적는다. 한국어 본문이 없으면 `description` 을 쓴다.

4. 연구소 결과 원본 값을 대응표로 공통 값으로 바꾼다. 대응표에 없는 값은 `OTHER`, 빈 값은 `UNSET` 이다. 원본 값도 함께 남긴다.

| 공통 값 | 뜻 | VXvue 원본 값 |
|---|---|---|
| `FIXED` | 프로그램이 고쳐졌다 | `lab_fixed` |
| `SPEC` | 사양대로 동작한다 | `lab_inspec` |
| `NOT_BUG` | 결함이 아니다 | `lab_nobug` |
| `DUPLICATE` | 다른 이슈와 같다 | `lab_duplicate` |
| `PENDING` | 보류 | `lab_pending` |
| `NO_ACTION` | 조치 없음 | `lab_noact` |

**결과** 공통 모델 기록이다.

| 기록 | 필드 |
|---|---|
| SRS | `id`, `old_id`(Legacy 번호), `title`, `status`, `updated`, `is_category`, `text` |
| 이슈 | `id`, `title`, `status`, `severity`, `rd_result`(공통 값), `rd_result_raw`, `description`, `reproduction_step`, `occurrence_cause`, `action_details`, `occurred_versions`, `target_versions`, `linked_ids`, `comment_ids`, `comments`, `created`, `updated` |
| 댓글 | `id`, `created`, `text`(2000자까지) |

> **참고** SRS 기록의 필드 이름은 이전 스냅샷 파일과 같다. 그래서 개편 전에 저장한 스냅샷도 그대로 비교 기준으로 쓸 수 있다.

**지킬 것**

- 제품 고유 필드 이름과 연구소 결과 원본 값은 제품 설정과 제품 어댑터(`app/modules/daily_qa/product_adapter.py`) 한 곳에만 둔다.

### REQ-QAINTEL-003 SRS 전체 수집과 구조화한 비교

**하는 일** 매 실행 SRS 전체를 읽고 마지막 정상 스냅샷과 비교해 신규·변경·삭제를 찾는다. 본문이 바뀌면 바뀐 문장까지 좁힌다.

**언제** 매 실행의 SRS 수집 단계(`collect_srs`).

**순서**

1. REQ-DAILY-002 의 SRS 순서대로 읽는다. 조회식은 제품 프로필의 `queries.srs` 다.
2. 비교 필드는 Legacy 번호, 제목, 상태, 본문이다. 수정 시각만 바뀐 것은 변경이 아니다.
3. 값을 비교하기 전에 공백과 줄바꿈을 한 칸으로 줄인다. 공백·줄바꿈만 다른 것은 변경이 아니다.
4. 본문은 ALM-QA-Automation `srs-spec` 이 사양서 PDF 를 만들 때와 같은 규칙으로 글자로 바꾼다. 그래야 그 도구의 과거 스냅샷(REQ-QAINTEL-029)과 비교해도 바뀌지 않은 SRS 가 바뀐 것으로 보이지 않는다.

   - 다른 Work Item 을 가리키는 표시(`polarion-rte-link`)는 `번호 - 제목` 으로 푼다. 제목은 같은 수집의 SRS 제목이다. 찾지 못하면 `번호 (참조 대상 확인 불가)` 다.
   - Polarion 서버 경로의 장식 아이콘(`/polarion/…` 이미지)은 지운다. 첨부 이미지는 `[이미지: <파일 이름>]` 으로 남긴다.

   > **예시** 본문의 `<span class="polarion-rte-link" data-item-id="VP-678">` 는 `VP-678 - Status Bar` 가 된다.

5. 본문이 바뀌었으면 문장 단위로 나눠 더해진 문장(`added_sentences`)과 빠진 문장(`removed_sentences`)을 남긴다.
6. 스냅샷을 `data/daily_qa/snapshots/<slug>/srs/<날짜>.json` 에 저장한다(시험 실행은 저장하지 않는다).

**결과** 변경마다 SRS 번호, 변경 종류(신규·변경·삭제), 바뀐 필드(`changed_fields`), 바뀌기 전·후 값, 바뀐 문장이다.

> **참고** 이 제품의 새 폴더에 스냅샷이 아직 없으면, 개편 전 위치(`data/daily_qa/snapshots/<날짜>.json`)의 스냅샷을 비교 기준으로 읽는다. 이 호환은 `daily_qa.product` 로 적힌 제품에만 적용한다. 파일은 옮기지 않는다.

### REQ-QAINTEL-004 이슈 전체 수집과 이슈 스냅샷

**하는 일** 매 실행 이슈 전체를 읽어 이슈 스냅샷으로 저장한다. 신규 여부는 수정 시각이 아니라 스냅샷 비교로 정한다.

**언제** 매 실행의 이슈 수집 단계(`collect_issues`).

**순서**

1. 제품 프로필의 `queries.issue`(VXvue 는 `type:issue`)로 모든 이슈를 쪽 단위로 읽는다. 요청 방식은 REQ-DAILY-002 와 같다(GET 만).
2. 이슈마다 공통 모델로 바꾼다(REQ-QAINTEL-002).
3. 댓글은 필요한 이슈만 읽는다.
   - 이슈 응답에 댓글 관계(`relations.comments`)의 댓글 번호가 있으면, 번호가 어제와 달라진 이슈만 댓글 본문을 읽는다.
   - 댓글 번호가 없으면 수정 시각이 어제와 다른 이슈만 읽는다.
   - 어제 스냅샷에 없던 이슈(신규)는 읽는다. 기준 스냅샷 실행은 댓글 본문을 읽지 않는다.
   - 한 실행에서 댓글을 읽는 이슈 수는 `daily_qa.intelligence.comment_fetch_limit`(기본 300)까지다. 넘은 이슈는 다음 실행에서 읽는다.
4. 댓글을 읽지 않았거나 읽다가 실패한 이슈는 어제 스냅샷의 댓글을 그대로 옮겨 적는다. 실패한 이슈는 `comments_error` 로 표시하고, 그 이슈의 댓글 비교는 이번 실행에서 하지 않는다.
5. 스냅샷을 `data/daily_qa/snapshots/<slug>/issues/<날짜>.json` 에 저장한다. 파일 머리에 수집 시각(`collected_at`)을 적는다.

**결과** 이슈 스냅샷 한 파일. 이슈 수집 단계에 전체 이슈 수, 댓글을 읽은 이슈 수, 댓글 읽기 실패 수가 남는다.

**설정**

| 키 | 기본값 | 뜻 |
|---|---|---|
| `daily_qa.intelligence.comment_fetch_limit` | `300` | 한 실행에서 댓글을 읽는 이슈 수 상한 |
| `daily_qa.intelligence.issue_drop_ratio` | `0.5` | 어제보다 이 비율 넘게 줄면 비정상으로 본다(REQ-QAINTEL-009) |

**지킬 것**

- 댓글 원문은 2000자까지만 스냅샷에 둔다. 스냅샷은 SRS 스냅샷과 같이 저장소 밖의 `data/` 에만 있고 Git 에 올리지 않는다(NFR-PRIV-002, NFR-DAILY-002).

  이유: 새 댓글 분석이 실패하면 다음 실행에서 같은 댓글로 다시 분석해야 한다.

### REQ-QAINTEL-005 변경 이벤트 만들기

**하는 일** 어제와 오늘의 공통 모델을 필드별로 비교해 변경 이벤트를 만든다. 이슈 하나에서 이벤트가 여러 개 나올 수 있다.

**순서**

1. SRS 비교 결과(REQ-QAINTEL-003)마다 이벤트 하나를 만든다.
2. 이슈는 번호로 맞대어 아래 표대로 이벤트를 만든다. 값은 공백을 줄인 뒤 비교한다.

| 이벤트 | 조건 | AI 분석 |
|---|---|---|
| `ISSUE_CREATED` | 어제 스냅샷에 없던 이슈 | 필요 |
| `ISSUE_CONTENT_UPDATED` | 제목 또는 설명이 바뀜 | 필요 |
| `ISSUE_REPRODUCTION_UPDATED` | 재현 절차가 바뀜 | 필요 |
| `ISSUE_RD_RESULT_CHANGED` | 연구소 결과 원본 값이 바뀜 | 공통 값에 따라 다름 (REQ-QAINTEL-010) |
| `ISSUE_ROOT_CAUSE_CHANGED` | 발생 원인이 바뀜 | 공통 값에 따라 다름 |
| `ISSUE_ACTION_DETAILS_CHANGED` | 조치 내용이 바뀜 | 공통 값에 따라 다름 |
| `ISSUE_COMMENT_ADDED` | 어제 없던 댓글이 생김 | 의미 있는 댓글이 있을 때만 |
| `ISSUE_STATUS_ONLY_CHANGED` | 상태만 바뀌고 위 항목은 그대로 | 필요 없음 |
| `ISSUE_METADATA_CHANGED` | 심각도·발생 버전·목표 버전·연결 항목이 바뀜 | 필요 없음 |
| `ISSUE_REMOVED` | 어제 있었는데 오늘 조회되지 않음 | 필요 없음 |
| `SRS_CREATED` | 새 SRS | 필요 |
| `SRS_UPDATED` | SRS 비교 필드가 바뀜 | 필요 |
| `SRS_REMOVED` | 어제 있었는데 오늘 없음 | 필요 없음. 삭제 SRS 를 가리키는 TC 는 코드가 찾는다(REQ-QAINTEL-028) |

3. 새 댓글이 "의미 있는 댓글"인지 코드가 먼저 거른다. 글자 수가 `daily_qa.intelligence.comment_min_chars`(기본 15)보다 짧거나, 진행 상태 문장(예: "확인했습니다", "진행 중")만 있으면 의미 없는 댓글이다.
   - 진행 상태 문장은 공통 기본 목록으로 가린다. 제품 설정의 `comment_noise_patterns` 는 이 기본 목록에 더한다(기본 목록을 대신하지 않는다).

   > **예시** VXvue 가 `재확인 부탁드립니다` 를 더하면 "재확인 부탁드립니다"와 기본 목록의 "확인 부탁드립니다" 가 모두 의미 없는 댓글이다.
4. 상태가 다른 변경과 함께 바뀌면 `ISSUE_STATUS_ONLY_CHANGED` 를 만들지 않는다. 상태 변화는 `ISSUE_METADATA_CHANGED` 의 바뀐 필드에 들어간다.

**결과** 이벤트마다 아래 값이다.

| 필드 | 뜻 |
|---|---|
| `product` | 제품 slug |
| `run_id` | 이벤트를 만든 실행 |
| `entity_type` | `issue` 또는 `srs` |
| `entity_id` | 이슈·SRS 번호 |
| `event_type` | 위 표의 이벤트 이름 |
| `before`, `after` | 바뀐 필드의 바뀌기 전·후 값 |
| `changed_fields` | 바뀐 필드 이름(공통 모델 이름) |
| `analysis_required` | AI 분석이 필요한지 |
| `reason` | 필요하거나 필요 없는 이유 한 문장 |
| `created_at` | 만든 시각 |

**지킬 것**

- 이벤트 감지는 공통 모델의 필드 이름만 쓴다. 제품 고유 필드 이름을 모른다.

### REQ-QAINTEL-006 이벤트 저장과 재시도

**하는 일** 변경 이벤트를 SQLite 표 `qa_change_events` 에 저장하고, AI 분석이 실패하거나 미뤄진 이벤트는 다음 실행에서 다시 분석한다.

**순서**

1. 스냅샷을 먼저 저장하고, 저장에 성공한 뒤에 이벤트를 저장한다. 이벤트 저장이 실패하면 방금 저장한 오늘 스냅샷을 지워 다음 실행이 같은 변경을 다시 찾게 한다.
2. 같은 제품·대상·이벤트 종류이고, 바뀌기 전·후 값과 비교 기준 스냅샷 날짜가 같은 이벤트가 이미 있으면 다시 저장하지 않는다. 같은 날 다시 돌려도 겹치지 않는다.

   > **예시** `VP-100` 이 수정됨 → 다시 열림 → 다시 수정됨으로 바뀌면, 두 번째 수정도 새 `ISSUE_RD_RESULT_CHANGED` 이벤트다. 비교 기준 스냅샷 날짜가 다르기 때문이다. 수정 완료 이슈 분석도 다시 돈다.

   이미 있던 이벤트는 이번 실행의 새 이벤트로 세지 않는다(REQ-QAINTEL-007).
3. 분석 상태(`analysis_status`)는 아래 가운데 하나다.

| 값 | 뜻 |
|---|---|
| `not_required` | AI 분석이 필요 없는 이벤트 |
| `pending` | 분석을 기다린다. 상한 초과·규칙 판 불일치·토큰 없음으로 돌리지 못한 것도 여기 남는다 |
| `done` | 분석이 끝났다. 만든 Finding 번호를 함께 남긴다 |
| `failed` | 분석 작업이 실패했다. 다음 실행에서 다시 한다 |
| `abandoned` | `daily_qa.intelligence.event_max_attempts`(기본 3)번 실패해 더 시도하지 않는다 |

4. 이벤트 하나가 분석 두 가지를 부를 수 있다. 예를 들어 수정 완료 이슈의 새 댓글은 새 댓글 분석과 수정 완료 이슈 분석을 부른다. 자동 실행은 이 두 분석을 작업 하나로 합쳐 돌린다(REQ-QAINTEL-010). 이벤트는 아직 끝나지 않은 분석 목록(`remaining_analyses_json`)을 가진다.

   - 분석 하나가 성공하면 그 분석만 목록에서 뺀다. 목록이 비어야 `done` 이다.
   - 분석 하나가 실패하면 이벤트는 `failed` 이고, 다음 실행은 목록에 남은 분석만 다시 돌린다. 성공한 분석은 다시 돌지 않는다.
   - 실패 횟수(`attempts`)는 실행 하나에 한 번만 올린다. 같은 실행에서 두 분석이 모두 실패해도 1이다.
   - 합쳐 돈 분석은 결과도 함께 적는다. 수정 완료 이슈 분석이 성공하면 새 댓글 분석도 끝난 것으로, 실패하면 둘 다 실패로 적는다.
5. 다음 실행은 `pending`·`failed` 이벤트를 오늘 이벤트와 함께 분석 대상으로 올린다. 분석에는 오늘 스냅샷의 최신 값을 쓴다. 대상이 오늘 스냅샷에 없으면 `abandoned` 로 바꾼다. 이때는 실패 횟수를 올리지 않는다.
6. 지난 날에 만든 대기 이벤트는 실행 한 번에 `daily_qa.intelligence.backlog_max_events`(기본 10)건까지만 올린다. 오래된 이벤트부터 고른다. 오늘 만든 이벤트는 이 상한에 들지 않는다. 같은 날 다시 도는 실행(사용량 한도 뒤 재개, [변경사항 점검하기])도 오늘 이벤트는 모두 올린다.

   > **예시** 지난 날 대기 이벤트가 33건이고 오늘 이벤트가 5건이면, 오늘 5건과 가장 오래된 대기 10건만 분석한다. 남은 23건은 `pending` 그대로 두고 다음 실행들이 10건씩 이어 간다.

   이유: 2026-10-14 실행은 오늘 바뀐 것이 5건인데 지난 날 대기분까지 40개 이슈를 한 번에 분석했다. 그 실행이 Claude 5시간 사용량을 다 써서 남은 분석도 멈췄다.

   올리지 않은 대기 이벤트는 상태와 실패 횟수를 바꾸지 않는다. 몇 건을 올리고 몇 건을 남겼는지는 `audit.json` 의 `backlog`(`waiting`·`taken`)에 남긴다. 값이 0 이하면 지난 날 대기 이벤트를 올리지 않는다.

   > **예외** 종료일이 지난 날인 기간 실행(REQ-QAINTEL-027)은 이 대기열을 다루지 않는다. 지난 스냅샷에 대상이 없다고 `abandoned` 로 바꾸지도 않는다.

**결과** 이벤트 표의 한 줄, 실행 폴더의 `change_events.json`(이번 실행이 찾은 이벤트 전체. 이미 저장돼 있어 다시 넣지 않은 이벤트도 들어 있다).

> **참고** 개편 전의 이슈 기준 시각(`issues_last_success_at`)·처리한 이슈 기록(`issues_processed`)은 더 쓰지 않는다. 상태 표에 남아 있어도 지우지 않는다. 미뤄 둔 사양 변경(`spec_change_pending`)이 있으면 첫 실행에서 `SRS_UPDATED` 대기 이벤트로 바꾸고 비운다.

### REQ-QAINTEL-007 변경이 없거나 상태만 바뀐 실행

**하는 일** AI 가 필요 없는 변경만 있거나 변경이 하나도 없으면 Claude 를 부르지 않는다.

**순서**

1. 이벤트가 있어도 모두 `analysis_required` 가 거짓이면 AI 작업을 만들지 않는다. 이벤트는 기록으로 저장한다.

   > **예시** 이슈 `VP-100` 의 상태만 `open` 에서 `in_progress` 로 바뀌고 댓글·연구소 결과·발생 원인·조치 내용·재현 절차·본문이 그대로면 `ISSUE_STATUS_ONLY_CHANGED` 이벤트만 남고 Claude 호출은 0회다.

2. SRS 수집과 이슈 수집이 모두 성공했고, 새 이벤트도 다시 분석할 대기 이벤트도 없으면 실행 결과는 `NO_CHANGE` 다. 화면에는 "변경사항 없음"으로 보인다. Claude 호출 수는 0이다.
   - 이미 저장돼 있어 다시 넣지 않은 이벤트는 새 이벤트가 아니다(REQ-QAINTEL-006 순서 2).
   - 수집을 건너뛰었거나(Polarion 설정 없음) 실패했으면 변경을 확인하지 못한 것이다. 실행 결과는 `PARTIAL`(일부 실패)이다.
3. 매뉴얼 누락 후보 점검(REQ-DAILY-006)이 그날 돌 차례여도 새 변경이 없는 실행(`NO_CHANGE`, `BASELINE`)에서는 돌리지 않는다. 다음 변경이 있는 실행으로 미룬다(상태 값 `<slug>:manual_check_due`).

**결과** 실행 결과 `NO_CHANGE`(변경사항 없음), 이벤트 단계 비고 "AI 분석이 필요한 변경이 없습니다".

### REQ-QAINTEL-008 첫 실행 기준 스냅샷

**하는 일** 이슈 스냅샷을 처음 만드는 실행은 기준만 만들고 분석하지 않는다. 기존 이슈 전체를 신규로 보지 않는다.

**순서**

1. 비교할 이슈 스냅샷이 없으면 오늘 이슈 스냅샷만 저장하고 이슈 이벤트를 만들지 않는다.
2. SRS 도 같다. 비교할 SRS 스냅샷이 없으면 기준만 저장한다.
3. 두 번째 정상 실행부터 변경을 분석한다.

**결과** 이번 실행에 이벤트가 없고 기준을 하나라도 새로 만들었으면 실행 결과는 `BASELINE`(기준 스냅샷 생성)이다. 단계 비고에 "기준 스냅샷만 저장(비교 대상 없음)"이 남는다.

### REQ-QAINTEL-009 수집 실패 때 기준을 옮기지 않기

**하는 일** 수집이 믿을 수 없으면 오늘 스냅샷을 저장하지 않고 이벤트도 만들지 않는다. 다음 실행은 마지막 정상 스냅샷과 비교한다.

**순서** 아래 가운데 하나면 그 수집 단계는 실패다. 스냅샷과 이벤트를 저장하지 않는다.

| 경우 | 단계 비고 |
|---|---|
| Polarion 요청 실패(쪽 넘기기 도중 실패 포함) | REQ-DAILY-002 의 오류 문장 |
| SRS 0건 | "SRS 조회 결과가 0건입니다. 조회식·권한을 확인하세요." |
| 이슈 0건 | "이슈 조회 결과가 0건입니다. 조회식·권한을 확인하세요." |
| 이슈 수가 어제의 `1 - issue_drop_ratio` 보다 적음 | "이슈 수가 어제 <어제>건에서 오늘 <오늘>건으로 급감했습니다. 조회 결과를 믿을 수 없어 기준을 옮기지 않습니다." |
| 스냅샷 파일 쓰기 실패 | "스냅샷을 저장하지 못했습니다: <오류 종류>" |

> **참고** 한 이슈의 댓글만 읽지 못한 경우는 수집 실패가 아니다. 그 이슈는 어제 댓글을 옮겨 적고 다음 실행에서 다시 읽는다(REQ-QAINTEL-004).

AI 분석만 실패한 경우는 스냅샷을 정상으로 저장하고, 이벤트를 `failed` 로 남겨 다음 실행에서 다시 분석한다(REQ-QAINTEL-006).

### REQ-QAINTEL-010 분석 대상 고르기

**하는 일** 이벤트를 분석 종류로 나눈다. 같은 대상·같은 분석 종류는 한 번만 분석하고, 관련 이벤트 번호를 모두 묶는다.

**순서** 이슈의 오늘 연구소 결과(공통 값)를 보고 아래 표대로 고른다.

| 이벤트 | `FIXED` | `SPEC`·`NOT_BUG` | 그 밖 |
|---|---|---|---|
| `ISSUE_CREATED` | 신규 이슈 분석 | 신규 이슈 분석 | 신규 이슈 분석 |
| `ISSUE_RD_RESULT_CHANGED` | 수정 완료 이슈 분석 | Spec 판정 이슈 분석 | 기록만 |
| `ISSUE_ROOT_CAUSE_CHANGED`, `ISSUE_ACTION_DETAILS_CHANGED` | 수정 완료 이슈 분석 | Spec 판정 이슈 분석 | 기록만 |
| `ISSUE_CONTENT_UPDATED`, `ISSUE_REPRODUCTION_UPDATED` | 수정 완료 이슈 분석 | Spec 판정 이슈 분석 | 신규 이슈 분석(다시 분석) |
| `ISSUE_COMMENT_ADDED`(의미 있는 댓글) | 새 댓글 분석 + 수정 완료 이슈 분석 | 새 댓글 분석 | 새 댓글 분석 |
| `SRS_CREATED`, `SRS_UPDATED` | 사양 변경 분석(REQ-QAINTEL-031) | | |

"기록만" 인 이벤트는 `analysis_required` 가 거짓이고, 이유에 "이 연구소 결과에 맞는 분석이 없어 기록만 남김" 이 적힌다.

같은 이슈가 한 실행에서 수정 완료 이슈 분석과 새 댓글 분석에 함께 걸리면 수정 완료 이슈 분석 하나로 합친다.

1. 새 댓글 분석 대상에서 그 이슈를 뺀다. 그 이슈의 댓글 이벤트는 수정 완료 이슈 분석 대상에 붙인다.
2. 수정 완료 이슈 분석 입력에 새 댓글(`new_comments`, 의미 있는 새 댓글만)을 넣는다.
3. 결과는 REQ-QAINTEL-006 4번처럼 두 분석에 함께 적는다.

이유: 2026-10-14 실행에서 새 댓글 분석 25건 가운데 24건이 같은 실행의 수정 완료 이슈 분석과 같은 이슈였다. 같은 이슈 본문·댓글·사양 후보를 두 번 읽었다.

> **예외** 버튼으로 요청한 실행(REQ-QAINTEL-016·032)은 합치지 않는다. 한 이슈에 새 댓글 분석만 남아 있으면(수정 완료 분석은 앞선 실행에서 끝남) 새 댓글 분석만 돈다.

**결과** 분석 종류별 대상 목록. 한 실행의 작업 묶음 수 상한(NFR-DAILY-001) 안에서 신규 이슈 → 수정 완료 → Spec 판정 → 새 댓글 → 사양 변경 순으로 돌린다. 상한을 넘은 대상의 이벤트는 `pending` 으로 남는다.

### REQ-QAINTEL-011 후보 압축

**하는 일** 분석마다 AI 에 넘길 후보를 코드가 먼저 고른다. 이슈 전체·TC 전체·사양 전체를 넘기지 않는다.

> **주의** TC 후보와 매뉴얼 문단 후보는 요청 실행(REQ-QAINTEL-016·032)에만 넣는다. 자동 실행의 작업 입력과 작업 폴더 `context/` 에는 TC 색인(`tc_index.jsonl`)과 매뉴얼(`manuals/`)을 두지 않는다.

**순서**

1. 검색어를 코드가 뽑는다. 이슈·SRS 번호, Legacy 번호, 연결 항목, Command 번호, DICOM Tag, 따옴표 문구, 오류 코드 모양을 정규식으로 찾는다.
2. 검색은 기존 Exact → BM25 단계 검색(`app/retrieval/hybrid.py`)을 쓴다. 식별자가 정확히 일치한 후보가 앞자리를 차지하고, 남은 자리를 BM25 가 채운다. 점수를 섞지 않는다.
3. 후보 종류와 개수는 아래와 같다.

| 후보 | 어디서 | 개수 설정(기본) |
|---|---|---|
| 비슷한 과거 이슈 | 오늘 이슈 스냅샷(자기 자신 제외) | `daily_qa.intelligence.issue_candidates`(8) |
| 사양 | 오늘 SRS 스냅샷 | `daily_qa.intelligence.spec_candidates`(6) |
| 사양서 조각 | Knowledge 에 등록한 사양서(기존 문서 로더 `app/core/knowledge_documents.py`) | `daily_qa.intelligence.spec_doc_candidates`(4) |
| TC (요청 실행만) | TC 색인(REQ-DAILY-014) | `daily_qa.tc_candidate_limit`(15) |
| 매뉴얼 문단 (요청 실행만) | 지식 사본의 매뉴얼 텍스트 | 3 |

4. 비슷한 과거 이슈는 새 이슈와 발생 버전 또는 목표 버전이 같은 후보를 앞에 둔다. 현재 검증 중인 버전의 중복을 먼저 보기 위해서다.
5. 후보마다 "왜 걸렸는지"(`'VP-5500' 정확 일치`, `용어 유사도 0.42`, `연결 항목`)를 함께 넘긴다.
6. 사양서 문서를 읽지 못하면 SRS 후보만으로 진행하고, 읽지 못한 문서 이름을 작업 입력과 단계 비고에 남긴다.
7. CLI 호출 안내에도 입력 후보를 먼저 비교하도록 적는다. 근거가 부족하거나 서로 충돌할 때 전체 색인을 추가로 검색할 수 있다. 후보 수·본문·근거 검사는 줄이지 않는다. 같은 작업에서 이미 읽은 공통 출력 형식은 재사용한다.

**결과** 작업 입력 파일(`in/<작업 ID>.json`). 마스킹한 뒤 격리 작업 폴더에 쓰고, 같은 파일을 실행 폴더 `sent/` 에 남긴다(REQ-DAILY-021).

### REQ-QAINTEL-012 신규 이슈 분석

**하는 일** 새로 등록된 이슈마다 중복 여부, 사양 대비 판단, 과거 이슈와의 관계, QA 권고를 정리한다. Skill `qa-new-issue-analysis`.

**입력** 이슈(제목·설명·재현 절차·Expected·Actual·오류 문구·연결 SRS·발생·목표 버전), 비슷한 과거 이슈 후보, 사양 후보, 사양서 조각. TC 후보는 넣지 않는다.

**순서**

1. 중복 분석. 후보 가운데 같은 증상·같은 조건의 이슈를 찾는다.

| 판정 | 뜻 |
|---|---|
| `STRONG_DUPLICATE` | 조건·증상·결과가 같은 이슈가 있다 |
| `POSSIBLE_DUPLICATE` | 비슷하지만 조건이나 결과가 일부 다르다 |
| `NO_DUPLICATE_FOUND` | 후보 가운데 중복이 없다 |

   중복 후보가 있으면 이슈 번호, 중복으로 본 근거, 차이점, 그 이슈의 과거 처리 결과를 함께 적는다. 과거 비슷한 이슈가 `SPEC` 으로 처리됐으면 "기존 유사 Issue가 Spec으로 처리된 이력이 있음" 을 표시한다.

2. 사양 분석. 연결 SRS 만 믿지 않고 사양 후보 전체와 비교한다.

| 판정 | 뜻 |
|---|---|
| `SPEC_VIOLATION` | 실제 결과가 최신 사양과 다르다 |
| `CONSISTENT_WITH_SPEC` | 실제 결과가 사양대로다 |
| `SPEC_UNDEFINED` | 사양이 이 동작을 정하지 않았다. 연구소·기획에 확인할 질문을 적는다 |
| `SPEC_AMBIGUOUS` | 사양 문장이 여러 뜻으로 읽힌다 |
| `INSUFFICIENT_EVIDENCE` | 판단할 근거가 모자란다 |

   사양이 없으면 결함이나 정상 동작으로 정하지 않고 `SPEC_UNDEFINED` 로 둔다.

3. 과거 이슈 분석. 아래 표시를 후보로만 붙인다. 확정 사실처럼 쓰지 않는다.

| 표시 | 뜻 |
|---|---|
| `POSSIBLE_REGRESSION` | 과거 `FIXED` 이슈가 다시 생겼을 수 있다 |
| `HISTORICAL_SPEC_DUPLICATE` | 과거 `SPEC`·`NOT_BUG` 로 처리된 이슈가 다시 등록됐을 수 있다 |
| `HISTORICAL_DUPLICATE_REREGISTERED` | 과거 `DUPLICATE` 로 처리된 이슈가 다시 등록됐을 수 있다 |
| `HISTORICAL_DECISION_CONFLICT` | 비슷한 과거 이슈들의 처리 결과가 서로 다르다 |

4. QA 권고. 사람이 할 다음 조치와 확인할 점을 적는다.

**결과** Finding 하나(분석 종류 `NEW_ISSUE`, 대상 = 이슈 번호, 판정 = 사양 판정). 중복·사양·과거 이슈·권고는 Finding 의 구획(`sections`)에 있다.

**지킬 것**

- TC 초안을 만들지 않는다. 만들면 코드가 Finding 을 버린다(REQ-QAINTEL-017).

### REQ-QAINTEL-013 수정 완료 이슈 분석

**하는 일** 연구소가 고쳤다고 한 이슈의 원인과 조치를 검토하고, 최신 사양과 맞는지, 어디까지 다시 봐야 하는지 짧게 정리한다. QA 규칙의 Skill S04(Fix Verification)에 해당한다. Skill `qa-fixed-issue-analysis`.

> **참고** 검증 TC 초안은 자동으로 만들지 않는다. 사람이 이 분석 화면에서 [검증 TC 초안 만들기]를 누르면 REQ-QAINTEL-032 가 만든다.

**언제** REQ-QAINTEL-010 표에서 "수정 완료 이슈 분석" 인 이벤트가 있을 때.

**입력** 이슈 본문, 발생 원인, 조치 내용, 연구소 댓글(최근 20개), 사양 후보, 사양서 조각, 비슷한 과거 이슈, 제품 설정의 Regression 축. 새 댓글 분석을 합친 이슈(REQ-QAINTEL-010)는 새 댓글(`new_comments`)도 넣는다. TC 후보는 넣지 않는다.

**순서**

1. 원인 검토 → 조치 검토 → 최신 사양과 맞는지 → 바뀐 범위 → 부작용·Regression 범위 → QA 할 일 순서로 쓴다.
2. 사양 판정은 아래 가운데 하나다.

| 판정 | 뜻 |
|---|---|
| `CONSISTENT_WITH_SPEC` | 조치 결과가 최신 사양과 맞다 |
| `PARTIALLY_CONSISTENT` | 일부만 맞다 |
| `CONTRADICTS_SPEC` | 조치 결과가 최신 사양과 다르다 |
| `SPEC_UNDEFINED` | 사양이 정하지 않았다 |
| `INSUFFICIENT_EVIDENCE` | 근거가 모자란다 |

3. Regression 축은 코드가 제품 설정(`qa_intelligence.regression_axes`)에서 정한다. 모델은 축마다 해당 여부와 이유만 채운다. 해당하지 않는 축도 "해당 없음" 으로 남긴다.
4. 요약은 한두 문장, QA 할 일은 3줄까지 쓴다.
5. 입력에 새 댓글이 있으면 그 댓글이 원인·조치·사양 판정에 주는 영향을 `detail` 에 함께 적는다. QA 가 할 일이 생기면 `action` 에 넣는다. 새 댓글 분석 Finding 은 따로 만들지 않는다.

**결과** Finding 하나(분석 종류 `FIXED_ISSUE`, 판정 = 사양 판정). 초안은 없다.

**지킬 것**

- 이 분석이 초안이나 TC Coverage 를 내면 코드가 그 부분만 빼고 "자동 분석이라 초안을 뺐습니다" 메모를 남긴다(REQ-QAINTEL-017).

### REQ-QAINTEL-014 Spec 판정 이슈 분석

**하는 일** 연구소가 "사양대로" 또는 "결함 아님" 으로 판정한 이슈를 사양과 과거 이슈에 비춰 다시 본다. 연구소 판정을 그대로 믿지 않는다. Skill `qa-spec-decision-analysis`.

**입력** 이슈 본문, 연구소 댓글, 발생 원인, 조치 내용, 사양 후보, 사양서 조각, 비슷한 과거 이슈.

**순서**

1. 연구소가 무엇을 근거로 사양이라고 했는지 정리한다.
2. 사양 근거를 판정한다.

| 판정 | 뜻 |
|---|---|
| `SUPPORTED_BY_SPEC` | 사양이 연구소 판정을 뒷받침한다 |
| `PARTIALLY_SUPPORTED` | 일부만 뒷받침한다 |
| `SPEC_AMBIGUOUS` | 사양 문장이 여러 뜻으로 읽힌다 |
| `SPEC_NOT_FOUND` | 뒷받침하는 사양을 찾지 못했다 |
| `CONTRADICTS_SPEC` | 사양이 연구소 판정과 다르다 |

3. 과거 비슷한 증상이 `FIXED` 였는데 이번에 `SPEC` 으로 처리됐거나, 그 반대면 `HISTORICAL_DECISION_CONFLICT` 를 표시한다.

**결과** Finding 하나(분석 종류 `SPEC_DECISION`). TC 초안을 만들지 않는다.

### REQ-QAINTEL-015 새 댓글 분석

**하는 일** 어제 없던 댓글만 읽어 QA 판단에 영향이 있는 정보인지 나눈다. 댓글 전체를 매일 다시 분석하지 않는다. Skill `qa-comment-analysis`.

**언제** 의미 있는 새 댓글이 달린 이슈 가운데, 같은 실행의 수정 완료 이슈 분석에 합쳐지지 않은 이슈(REQ-QAINTEL-010).

**입력** 새 댓글(의미 있는 댓글만), 이슈 요약, 이전 댓글 최근 5개, 같은 제품·이슈의 가장 최근 분석 요약(이번 실행 제외, 600자까지).

- 이슈 연결 번호와 새 댓글의 정확한 SRS 번호로 현재 수집한 사양을 찾아 2건·건당 1,500자까지 넣는다. 본문이 빈 사양 번호와 잘린 본문을 표시한다. 알려진 관련 이슈는 누락 사양으로 취급하지 않고, 유형을 확인하지 못한 번호는 별도로 표시한다. 새 댓글에 나온 번호를 먼저 본다.
- 댓글 작성자 ID는 원본과 화면에 저장한다. AI 입력의 댓글과 변경 이벤트에서는 뺀다. 이름이나 소속을 추측하지 않는다.
- 요약은 누가 어떤 이슈에서 무엇을 말했고 QA가 무엇을 확인해야 하는지 한두 문장으로 쓴다. 사양과 비교하지 못했으면 그 한계를 적는다.
- 확인한 자료와 확인하지 못한 자료는 `sections.checked.confirmed`·`unconfirmed` 목록으로 구분한다. 입력에 있다는 이유만으로 확인했다고 쓰지 않는다. 비어 있거나 형식이 틀린 목록은 검증 기록에 남긴다.

**순서**

1. 댓글마다 요약, 분류, 기존 QA 분석에 주는 영향, 추가로 확인할 점을 적는다.

| 분류 | 뜻 |
|---|---|
| `ROOT_CAUSE_INFORMATION` | 원인 정보 |
| `RESOLUTION_INFORMATION` | 조치 정보 |
| `REPRODUCTION_INFORMATION` | 재현 조건 정보 |
| `SPEC_CLAIM` | 사양이라는 주장 |
| `REQUIREMENT_INFORMATION` | 요구사항 정보 |
| `QA_ACTION_REQUIRED` | QA 가 할 일 |
| `OTHER_SIGNIFICANT_INFORMATION` | 그 밖의 의미 있는 정보 |
| `NOT_SIGNIFICANT` | 진행 상태 같은 의미 없는 내용 |

2. 모든 댓글이 `NOT_SIGNIFICANT` 면 Finding 을 저장하지 않는다.

**결과** Finding 하나(분석 종류 `COMMENT`, 판정 = 가장 앞 댓글의 분류).

### REQ-QAINTEL-016 기존 TC 검토 (사양 변경 Coverage 분석, 요청할 때만)

**하는 일** 바뀐 SRS 하나에 대해 과거 이슈 이력과 기존 Checklist·TC 가 그 변경을 이미 충분히 다루는지 보고, 모자라면 기존 TC 수정안이나 신규 Checklist TC 초안을 낸다. Skill `qa-spec-coverage-analysis`. 상위 SPEC 의 사양 변경 영향 검토(REQ-DAILY-003)를 대신한다.

**언제** 사람이 사양 변경 분석(REQ-QAINTEL-031) 상세 화면에서 [기존 TC 검토]을 누를 때만 돈다(`POST /qa-agent/findings/<번호>/tc-check`). CLI 는 `scripts/run_daily_qa.py --on-demand tc-check --finding <번호>` 다. 자동 실행에서는 돌지 않는다.

이유: TC 는 사람이 넣는 자료라 최신이 아닐 수 있다. 자동으로 비교하면 틀린 결론이 나오고 토큰도 많이 쓴다.

요청 실행은 아래처럼 돈다(REQ-QAINTEL-032 와 같다).

1. 저장된 최신 SRS·이슈 스냅샷을 쓴다. Polarion 을 새로 읽지 않는다.
2. 원래 분석을 만든 변경 이벤트로 작업 하나를 만든다. TC 후보와 매뉴얼 문단 후보를 넣는다.
3. 결과는 새 Finding(분석 종류 `TC_CHECK`)으로 저장하고 `sections.source_finding` 에 원래 분석 번호를 적는다. 원래 분석과 이벤트 상태는 바꾸지 않는다.
4. 메일을 보내지 않는다. 실행 잠금·사용량 한도·실행당 작업 상한은 자동 실행과 같다.

**입력**

- 변경: SRS 번호, 변경 종류, 바뀐 필드, 바뀌기 전·후 값, 바뀐 문장(REQ-QAINTEL-003)
- 관련 과거 이슈: 코드가 아래 순서로 고른 후보. 각 후보에 코드가 붙인 관계 단서(과거 `FIXED`, 과거 `SPEC`·`NOT_BUG`, 최근 `daily_qa.intelligence.recent_fixed_days`(기본 90)일 안의 `FIXED`)가 있다.
  1. SRS 번호·Legacy 번호 정확 일치(연결 항목 또는 본문)
  2. BM25(SRS 제목과 바뀐 문장)
- TC 후보: 코드가 아래 순서로 고른 후보. 각 후보에 걸린 이유가 있다. 영향성평가 Checklist 파일(`qa_intelligence.checklist.template_name_contains`)의 행을 같은 순위 안에서 앞에 둔다.
  1. SRS 번호로 연결된 TC
  2. Legacy 번호로 연결된 TC
  3. 관련 과거 이슈 번호가 적힌 TC
  4. BM25 로 찾은 같은 기능·Workflow 의 TC
- 매뉴얼 문단 후보(제목과 바뀐 문장 기준)
- 요청 실행에는 관련 이슈의 재현 절차를 Precondition·Step·Expected·Actual·Log/Data로 구분해 넣는다. 긴 요약 뒤에 있는 Expected·Actual도 비교할 수 있어야 한다.

**순서**

1. 무엇이 바뀌었는지 정리한다.
2. 관련 이슈가 있는지, 각 이슈가 어떤 관계인지 적는다. 이슈가 있다고 TC Coverage 가 있다고 보지 않는다.

| 관계 | 뜻 |
|---|---|
| `EXISTING_DEFECT` | 그 동작의 기존 결함 |
| `PAST_FIXED` | 과거 수정 완료 이슈 |
| `PAST_SPEC` | 과거 Spec 판정 이슈 |
| `SAME_FUNCTION_REGRESSION` | 같은 기능의 Regression |

3. TC 마다 Title·Precondition·Test Step·Expected Result·Test Data 를 바뀐 사양과 비교한다. SRS 번호가 같다는 이유만으로 덮는다고 보지 않는다. TC 마다 조치를 정한다.

| 조치 | 뜻 |
|---|---|
| `KEEP` | 그대로 둔다 |
| `UPDATE_EXISTING` | 거의 덮지만 Step 이나 Expected 가 옛 사양 기준이다. 고칠 곳을 적는다 |

관련 이슈 Expected와 기존 TC Expected가 충돌하면 제품 QA 규칙 §17에 따라 아래 중 하나를 기록한다. 유효 사양과 제공된 관찰 자료로 판단한다.

근거가 부족해 판단을 보류할 때의 저장값과 화면 표시 이름은 다음과 같다. 아래 표의 마지막 행은 이 이름을 쓴다.

```text
사양 확인 필요
```

| 분류 | 뜻 |
|---|---|
| `Issue만 수정 필요` | 기존 TC Expected가 사양에 맞고 이슈 Expected를 고쳐야 한다 |
| `기존 TC 수정 필요` | 이슈 Expected에 근거가 있고 기존 TC Expected를 고쳐야 한다 |
| `Issue + TC 모두 수정 필요` | 양쪽 Expected를 고쳐야 한다 |
| 위 표시 이름 예시의 분류 | 근거가 부족하거나 사양이 충돌해 어느 쪽도 정할 수 없다 |

TC 결과에 분류·이유·대상 이슈 번호(`expected_conflict.classification`, `reason`, `issue_id`)를 함께 저장하고 상세 화면의 TC 표에 표시한다. 충돌 대상 이슈도 관련 번호(`related_ids`)에 남긴다.

Generator·Console 상태와 Viewer Actual이 제공되면 함께 비교한다. 관찰 자료가 없으면 추정하지 않는다.

> **주의** 충돌 분류는 수정 제안이다. 완료 TC의 결과·ID·행·Sheet·Issue 이력을 보존하고 기존 Pass/Fail을 바꾸지 않는다.

4. Coverage 를 판정한다.

| 판정 | 뜻 |
|---|---|
| `FULLY_COVERED` | 기존 TC 가 바뀐 요구사항의 핵심 동작과 Expected 를 검증한다 |
| `PARTIALLY_COVERED` | 관련 TC 는 있지만 새 조건·새 상태 변화·새 Expected·경곗값·연동 가운데 빠진 것이 있다 |
| `NOT_COVERED` | 바뀐 내용을 검증하는 TC 가 없다 |
| `SPEC_REVIEW_REQUIRED` | 사양이 불명확해 Expected 를 정할 수 없다 |

5. 아래 경우를 경고(`alerts`)로 표시한다.

| 경고 | 뜻 |
|---|---|
| `ISSUE_WITHOUT_TC` | 관련 이슈는 있는데 그것을 검증하는 TC 가 없다 |
| `TC_EXPECTED_OUTDATED` | 관련 TC 는 있지만 Expected 가 바뀌기 전 사양 기준이다 |
| `FIXED_ISSUE_WITHOUT_REGRESSION_TC` | 과거 수정 완료 이슈와 새 SRS 가 이어지는데 Regression TC 가 없다 |
| `SPEC_ISSUE_BEHAVIOR_CHANGED` | 과거 Spec 판정 이슈에서 정한 동작이 최신 SRS 와 다르다 |

6. `PARTIALLY_COVERED`·`NOT_COVERED` 이고 사양 근거가 충분할 때만 신규 TC 초안(`CREATE_NEW`)을 쓴다. 기존 TC 수정으로 충분하면 초안을 쓰지 않는다. 초안 관점은 변경과 관계있는 것만 고른다.

| 관점 | 뜻 |
|---|---|
| `DIRECT_SPEC` | 바뀐 사양 자체 |
| `STATE_TRANSITION` | 상태 변화 |
| `PERSISTENCE` | 저장·다시 불러오기 |
| `BOUNDARY` | 경곗값 |
| `NEGATIVE` | 잘못된 입력 |
| `REGRESSION` | 기존 동작 |
| `INTEGRATION` | 연동 |
| `CONFIGURATION` | 설정 |
| `ENVIRONMENT` | 환경 |

   초안마다 왜 필요한지(`rationale`)를 적는다.

7. `SPEC_REVIEW_REQUIRED` 면 초안을 만들지 않고 "Checklist TC 생성 보류" 와 확인할 점을 적는다.

**결과** Finding 하나(분석 종류 `TC_CHECK`, 판정 = Coverage). 구획에 변경 내용, 이슈 Coverage, Checklist Coverage, 부족한 점, 경고, 권고 TC 변경이 있다. 관련 이슈·TC·초안의 연결은 `related_ids` 로 복원할 수 있다.

**안 될 때**

| 경우 | 응답 |
|---|---|
| 원래 분석이 사양 변경 분석이 아님 | 400 "사양 변경 분석에서만 기존 TC 검토를 할 수 있습니다." |
| 없는 분석 번호 | 404 "Finding 이 없습니다." |
| 다른 실행 중 | 409 "점검이 이미 실행 중입니다." |

**지킬 것**

- 같은 버튼을 다시 눌러도 같은 대상·판정·초안 제목의 Finding 이 열려 있으면 저장하지 않는다(REQ-DAILY-018).
- 개편 전에 자동으로 만든 Coverage Finding(분석 종류 `SPEC_COVERAGE`, Skill `qa-spec-coverage-analysis`)은 지우지 않고 그대로 보인다.

### REQ-QAINTEL-017 분석 결과 근거 검증

**하는 일** Claude 가 돌려준 결과의 번호와 근거가 실제 자료에 있는지 코드가 확인한다. 없는 번호는 사용자에게 보이지 않는다.

**순서**

1. 결과 파일 전체의 형식은 REQ-DAILY-007 과 같이 먼저 검사한다. 형식이 틀리면 한 번 더 실행한다.
2. 이슈 번호(중복 후보·과거 이슈·관련 이슈)는 오늘 이슈 스냅샷에 있어야 한다. 대상 이슈 자신을 중복 후보로 낸 것도 뺀다.
3. SRS 번호는 오늘 SRS 스냅샷의 번호나 Legacy 번호여야 한다.
4. TC 는 TC 색인의 TC ID 나 `파일 / 시트 / N행` 위치여야 한다.
5. 사양서 조각 근거는 작업 입력으로 준 조각 번호(`ref`)여야 한다. 댓글 근거는 작업 입력의 댓글 번호여야 한다.
6. 맞지 않는 항목은 결과에서 빼고, 뺀 항목과 이유를 Finding 의 검증 기록(`sections.validation`)에 남긴다.
7. 판정을 뒷받침해야 하는데 근거가 하나도 남지 않으면 Finding 을 버린다. 근거가 없음을 뜻하는 판정(`SPEC_UNDEFINED`, `SPEC_AMBIGUOUS`, `INSUFFICIENT_EVIDENCE`, `SPEC_NOT_FOUND`, `SPEC_REVIEW_REQUIRED`, `NO_DUPLICATE_FOUND`, `SPEC_UNCLEAR`)은 근거 없이도 남기되 신뢰도를 `Review Needed` 보다 높이지 않는다.
8. 중복 판정이 `STRONG_DUPLICATE`·`POSSIBLE_DUPLICATE` 인데 남은 후보가 없으면 `INSUFFICIENT_EVIDENCE` 로 바꾼다.
9. TC 초안 규칙

   - 신규 이슈·Spec 판정·댓글·현재 이슈 전체 점검이 초안을 내면 Finding 을 버린다.

   - 자동 실행의 수정 완료 이슈 분석·사양 변경 분석이 초안이나 TC 비교 구획을 내면 그 부분만 빼고 메모를 남긴다.

   - 검증 TC 초안 요청(REQ-QAINTEL-032)에서 대상 이슈의 오늘 연구소 결과가 `FIXED` 가 아니면 Finding 을 버린다.

   - 사양 판정이 `SPEC_UNDEFINED`·`INSUFFICIENT_EVIDENCE`·`SPEC_AMBIGUOUS` 이거나 Coverage 가 `FULLY_COVERED`·`SPEC_REVIEW_REQUIRED` 면 초안을 빼고 "Checklist TC 생성 보류" 를 남긴다.
10. 조치 문장이 QA 규칙 §55 금지 조치(이슈 닫기, TC 덮어쓰기, 결과·이력 삭제)를 담으면 Finding 을 버린다(REQ-DAILY-007 과 같다).
11. 기존 TC Expected 충돌 분류는 네 분류 중 하나이고 이유와 오늘 스냅샷의 이슈 번호가 있어야 한다. 맞지 않으면 충돌 필드만 빼고 원문과 이유를 검증 기록에 남긴다. 분류를 다른 값으로 바꾸지 않으며 신뢰도를 `Review Needed`로 낮춘다. 구형 결과에 필드가 없어도 허용한다.

**결과** 저장한 Finding, 버린 Finding 수(단계 비고 "규칙 위반으로 버린 Finding N건"), Finding 별 검증 기록.

### REQ-QAINTEL-018 초안 Excel

**하는 일** 이번 실행의 검증 TC 초안과 Coverage 조치를 영향성평가 Checklist 와 같은 열 순서의 Excel 한 파일(`impact_checklist_draft.xlsx`)로 만든다. REQ-DAILY-019 의 형식을 넓힌다.

**순서**

1. `Checklist 초안` 시트에는 신규 초안(검증 TC 초안 요청의 초안, 기존 TC 검토의 `CREATE_NEW`)만 넣는다. 열 이름과 순서는 제품 설정의 Checklist 형식(`qa_intelligence.checklist.headers`)이고, 원본 Checklist 가 있으면 머리글 서식과 열 너비를 복사한다.
2. `Coverage` 시트에는 SRS 변경마다 TC 별 조치(`KEEP`, `UPDATE_EXISTING`, `CREATE_NEW`, `SPEC_REVIEW_REQUIRED`), 이유, 추천 수정, 관련 이슈, Finding 번호를 넣는다.
3. `Review` 시트에는 Finding 별 판정·요약·근거 위치·신뢰도를 넣는다.

**결과** 실행 폴더의 `impact_checklist_draft.xlsx`. 이번 실행에 초안이나 기존 TC 검토 Finding 이 하나라도 있을 때만 만든다. 자동 실행은 초안이 없으므로 보통 만들지 않는다.

### REQ-QAINTEL-019 QA Agent 대시보드

**하는 일** `/qa-agent` 한 화면에서 마지막 실행 결과, 다음 자동 실행, 오늘 바뀐 것의 요약, 최신 분석 결과를 빠르게 본다.

**언제** 브라우저로 `/qa-agent` 를 연다. 옛 주소 `/daily-qa` 는 `/qa-agent` 로 넘긴다.

**화면 구성**

1. 맨 위: 수동 업로드 지식 문서 목록(REQ-QAINTEL-022).
2. 실행: 마지막 실행(시각·결과), 실행 결과 요약, 다음 자동 실행 시각(주말·공휴일 제외), [변경사항 점검하기] 버튼. 그 서버에서 예약을 껐으면(`daily_qa.schedule.enabled: false`) 다음 자동 실행 자리에 "예약 꺼짐 (이 서버는 자동 실행하지 않음)" 을 보인다.
3. 오늘 변경 요약: 마지막 실행의 신규 이슈, Fixed(연구소 결과가 `FIXED` 로 바뀐 이슈), Spec(`SPEC`·`NOT_BUG` 로 바뀐 이슈), 댓글 추가, SRS 변경 수.
4. 분석결과 구역: 검색·필터 한 줄과 결과 카드 목록. 필터와 카드 모양은 결과 페이지와 같고(REQ-QAINTEL-046), 이슈마다 가장 최근 결과 한 장씩 맨 위 50건만 보인다. 더 보려면 [전체 결과·검색]을 연다. 카드에는 결론 단계, 분석 종류, 대상 번호·제목, 두 줄 요약, QA 할 일 3줄까지, [상세보기](REQ-QAINTEL-033)가 있다. `문제 없음` 카드도 접지 않고 다른 카드와 같이 보인다. 설정(`daily_qa.savings.enabled`)이 켜져 있든 꺼져 있든 같은 목록이다.
5. 최근 실행 목록: 실행마다 결과와 [점검 기록 보기] 링크.

> **예시** `검토 필요 · 사양 변경 분석` / `[VP-516] Display X-ray Image` / "Reject 문구가 '영상 표시 마크' 표로 바뀌었다." / QA 할 일 ① Q/R 수신 영상 표시 확인 ② FTM 영상 확인

**설정** 제품이 하나면 그 제품을 고른다. 여럿이면 주소의 `?product=<이름>` 으로 고른다. 조회 함수는 모두 제품을 받는다.

**지킬 것**

- 승인·거절·근거 추가 필요·검토자 입력·질문 답변은 보이지 않는다.
- 사용을 종료한 단일 이슈 분석의 버튼과 링크는 제공하지 않는다(REQ-QAAGENT-016).

> **참고** 실행 구역의 제목은 `점검 실행 · <제품>` 이다. 마지막 실행, 실행 결과, 다음 자동 실행, 분석 기간, [변경사항 점검하기]이 이 구역에 있다.

### REQ-QAINTEL-020 분석 상세 화면과 점검 기록 보기 화면

**하는 일** 분석 결과 하나를 위에서 아래로 한 번에 읽는다. 이슈 원문과 분석 뒤에 바뀐 점을 먼저 보고, 그다음에 AI 판단과 QA 할 일을 본다. 탭은 없다. 실행 하나의 단계·이벤트·내려받을 파일도 본다.

> **예시** 수정 완료 이슈(VP-1000)의 화면은 이 순서로 읽힌다. 이름과 시각은 모두 지어낸 값이다.

```text
[VP-1000] 동물용 Sequence 값이 그대로 전송됨                          원문 열기
김예시 · 등록 2026-09-21 16:37 · 최근 업데이트 2026-10-14 18:09 · reviewed · 연구소 FIXED
분석(2026-10-14 13:35) 이후 변경 1건 · 재분석 대기
왜 분석했나: 2026-10-13 17:20 새 댓글
이슈 본문: 재현 절차 ... / 발생 원인 ... / 조치 내용 ...
AI 판단 (원인 설명과 수정이 사양에 맞는가): 요약 한 줄 · 판정 사양 미정의 · 신뢰도 확인 필요
QA 할 일: 3개 이내
댓글: 1) 2026-10-13 17:20 · 이예시 · 분석에 사용   2) 2026-10-14 18:09 · 이예시 · 분석 이후
```

**화면 순서**

| 순서 | 구획 | 내용 | 자료가 없을 때 |
|---|---|---|---|
| 1 | 머리 | `[번호] 제목`과 [원문 열기]. 둘째 줄을 크게 해서 작성자 이름, 등록일, 최근 업데이트, 상태, 연구소 결과를 보인다 | 이름이 없으면 `이름 미확인 (ID)`, ID도 없으면 `이슈 작성자 정보 없음` |
| 2 | 최신성 | 분석 뒤에 바뀐 것이 있으면 `분석(<시각>) 이후 변경 <N>건 · 재분석 대기` 배너를 보인다. 화면에 표시만 하고 AI를 부르지 않는다 | 이슈 원문과 이벤트를 모두 알 수 없으면 배너를 보이지 않는다 |
| 3 | 분석 이유 | `왜 분석했나: <한국 시각> 새 댓글`처럼 분석을 만든 이벤트를 같은 시각·같은 이름은 한 번만 적어 한 줄로 보인다 | 저장된 이벤트가 없으면 `변경 이벤트가 저장되지 않았습니다.` |
| 4 | 이슈 본문 | 설명, 재현 절차, 발생 원인, 조치 내용, 발생 버전, 목표 버전. 8줄을 넘는 글은 8줄까지만 보이고 나머지는 [펼치기]에 둔다 | `원문 스냅샷 없음` |
| 5 | AI 판단 | 분석 종류별 질문, 그 답을 담은 결론 한 줄, 판정, 신뢰도, 근거 3개까지 | 이전 형식 결과는 `이전 형식 결과`와 저장된 요약·상세만 보인다 |
| 6 | QA 할 일 | 3개까지, 그 아래에 `확인하지 못한 자료` | 없으면 해당 줄을 두지 않는다 |
| 7 | 댓글 | 이슈의 댓글 전체를 보인다. 시각을 아는 댓글은 시간순이고, 시각을 모르는 댓글은 그 뒤에 저장된 순서대로 놓는다. 분석에 쓴 댓글에는 `분석에 사용`과 해석·QA 영향을, 분석 뒤에 달린 댓글에는 `분석 이후`를 붙인다 | 이슈 원문이 없으면 변경 이벤트에 저장된 댓글만 보인다. 본문을 저장한 적이 없는 댓글은 `본문 미수집`이다 |
| 8 | 근거 자료 | 판단 근거 전체, 관련 과거 이슈, 선택 버전 TC 비교, 회귀 축 표. 분석 종류별 구획은 아래 표와 같다 | 근거가 없으면 `근거 없음` |
| 9 | 분석 기록 | 접혀 있다. 모델, 추론 정도, 실행 번호, 분석 메모 원문, 확인한 자료 구분, 근거 검증 기록(뺀 항목과 이유), 이 분석을 만든 변경 이벤트 | 확인 자료 구분이 없는 결과는 그 사실을 이 구획에 알린다 |
| 10 | 처리 상태 | 상태·처리자·메모 저장과 처리 이력. 넓은 화면에서는 오른쪽에 붙어 있다 | |

**분석 종류별 AI 판단**

5번 구획의 질문과 보이는 값은 분석 종류마다 다르다. 판정 값은 이름만 바꿔 보이고, AI가 내놓는 결과 형식은 바꾸지 않는다.

| 분석 종류 | 화면 질문 | 보이는 값 |
|---|---|---|
| 신규 이슈 | 사양으로 보면 이슈가 맞는가 | 아래 판정 이름 표. 중복 후보가 있으면 `중복 의심`을 덧붙인다 |
| 수정 완료 이슈 | 원인 설명과 수정이 사양에 맞는가 | 원인 검토와 수정 검토 요약, 판정, 회귀 위험 축 중 `해당`인 축의 개수 |
| 새 댓글 | 새 댓글이 QA 판단을 바꾸는가 | 댓글 분류와 QA 영향 |
| Spec 판정 이슈 | 연구소 설명이 사양으로 뒷받침되는가 | 저장된 판정 |
| 사양 변경 | 바뀐 사양을 TC가 덮는가 | 저장된 Checklist 범위 판정. TC 비교를 하지 않은 분석이면 그 사실 |
| 종류가 비어 있는 이전 형식 | (질문 없음) | `이전 형식 결과`, 저장된 요약과 상세 |

신규 이슈의 판정 이름은 다음과 같다. 왼쪽이 저장된 판정 값(`verdict`), 오른쪽이 화면에 보이는 이름이다.

```text
SPEC_VIOLATION        이슈로 보임
CONSISTENT_WITH_SPEC  사양상 정상, 이슈 아닐 수 있음
SPEC_UNDEFINED        사양 미정의, 기획 확인 필요
SPEC_AMBIGUOUS        사양이 모호함, 기획 확인 필요
INSUFFICIENT_EVIDENCE 근거 부족, 판단 보류
위에 없는 값           저장된 값 그대로 + 검토 필요 표시
```

`중복 의심`은 중복 검토 판정이 `STRONG_DUPLICATE`·`POSSIBLE_DUPLICATE`이거나 과거 이슈 표시가 `HISTORICAL_SPEC_DUPLICATE`·`HISTORICAL_DUPLICATE_REREGISTERED`일 때 붙는다.

**읽는 규칙**

- 화면을 여는 일은 AI를 부르지 않는다.
- 이슈 본문과 댓글은 제품의 가장 최근 이슈 스냅샷(`data/daily_qa/snapshots/<제품>/issues/<날짜>.json`)에서 읽는다. 파일 수정 시각이 같으면 다시 읽지 않는다.
- 분석 뒤 변경은 같은 이슈의 대기 이벤트가 분석 시각 뒤에 생겼거나, 이슈의 최근 업데이트 시각이 분석 시각보다 늦을 때다.
- 이슈 스냅샷은 댓글 본문을 읽지 않은 날에 댓글 번호만 남긴다. 그런 빈 댓글은 변경 이벤트에 저장된 같은 번호의 원문으로 시각·본문·작성자를 채운다. 원문도 없으면 `본문 미수집`으로 보이고, 시각을 모르는 댓글로 보아 시각을 아는 댓글 뒤에 놓는다. 이벤트에만 있거나 해석만 저장된 댓글도 줄로 남긴다.
- 판정이 저장되지 않은 결과는 판정 자리에 `판정 저장 안 됨`을 보인다.
- 이슈 본문 읽기 결과는 제품 폴더마다 가장 최근 스냅샷 파일 하나만 기억한다. 새 파일이 생기면 바꾼다.
- 댓글 작성자 이름은 제품·이슈별 작성자 표(`qa_issue_reporters`)에서 같은 작성자 번호의 이름을 찾아 보인다. 표에 없으면 `이름 미확인 (ID)`다.
- 이슈 작성자와 댓글 작성자의 번호·이름은 화면에 보이기만 한다. AI에 보내는 입력에는 넣지 않는다.
- 분석 결과의 원문, 최초 분석 시각, 모델, QA 처리 이력은 바꾸지 않는다. 이 화면이 바꾸는 것은 배치뿐이다.
- 사양에 근거가 없는 Expected나 판정을 화면이 만들어 내지 않는다. 판정이 아직 저장되지 않았으면 그렇다고 보인다.
- 1366px와 1920px 폭에서 가로 넘침이 없어야 한다. 자바스크립트가 실패해도 이슈 본문과 AI 판단을 읽을 수 있어야 한다.
- 이슈 번호가 아닌 사양 번호가 대상인 분석(사양 변경, 기존 TC 검토, 삭제된 SRS)은 4번 구획 이름이 `사양 내용`이고 이슈 원문과 댓글 구획을 두지 않는다.

**근거 자료(8번)의 분석 종류별 구획**

| 분석 종류 | 구획 |
|---|---|
| 신규 이슈 | Summary, Duplicate Analysis, Specification Analysis, Historical Analysis, QA Recommendation, Evidence |
| 수정 완료 이슈 | Root Cause Review, Resolution Review, Specification Consistency, Regression Risk(초안이 있을 때만 Verification TC) |
| 검증 TC 초안(요청) | 수정 완료 이슈와 같고 Verification TC 가 있다 |
| Spec 판정 이슈 | Summary, R&D Claim, Specification Evidence, Historical Decisions, QA Analysis, Evidence |
| 새 댓글 | New Comment, Classification, Impact, Evidence |
| 사양 변경 | 관련 과거 이슈 |
| 기존 TC 검토(요청)·개편 전 Coverage | Specification Change, Historical Issue Coverage, Checklist Coverage, Coverage Gap, Recommended TC Changes |

- 개편 전 Finding 은 판정·요약·근거·초안만 보인다. 옛 결과를 다시 분석하거나 저장 내용을 바꾸지 않는다.
- 점검 기록 보기(`/qa-agent/runs/<실행 ID>`)는 처음 보는 사람이 위에서부터 읽으면 무슨 일이 있었는지 알 수 있게 아래 순서로 보인다.

  1. **결과 한 문장**: 상태 색과 결과 배지를 보인다. 실패가 있으면 실패한 일을 먼저 쓰고, 수집 실패를 변경 0건이나 성공으로 설명하지 않는다.

  2. **QA 담당자 할 일**: 문제가 있을 때 원인별로 확인하거나 관리자에게 요청할 일을 보인다. 성공 실행에는 이 상자가 없다.

  3. **핵심 숫자 3개**: 아래 표시 이름 예시의 카드 3개로 보인다. 바뀐 것은 이벤트 수, AI가 분석한 것은 분석 작업의 완료 수이며 규칙 점검 결과 수와 구분한다. 수집 실패로 변경을 확인하지 못했으면 바뀐 것은 `-` 다.

  4. **확인할 결과**: REQ-QAINTEL-033의 결론 단계 중 사양과 다름 → 검토 필요 → 근거 부족 순으로 10개까지 짧게 보인다. 같은 단계는 최신 결과가 먼저다. 나머지 개수와 해당 실행만 필터한 [모두 보기] 링크를 보인다. 문제 없음·참고는 개수만 보인다. 모두 보기 목록은 50개씩 나누고 개편 전 결과도 포함한다.

  5. **자세히(접힘)**: 기존 숫자, 진행 흐름 네 칸, 단계별 설명, 변경 이벤트, 모든 분석 결과, 내려받기, 실행 번호·시각·메일 상태를 보존한다. 실패한 단계만 별도 상자에서 펼친다. 내려받을 파일은 뜻을 쓴다(예: `srs_diff.json` → "SRS 변경 내용").

핵심 숫자 카드에 쓰는 화면 표시 이름은 다음과 같다.

```text
바뀐 것
AI가 분석한 것
확인 필요
```

|---|---|
| Polarion 연결 실패 | 오늘 변경을 확인하지 못했다고 알린다. 관리자에게 서버의 Polarion 연결·주소·네트워크 확인을 요청하고 해결 후 다시 실행한다. `ConnectError`만으로 DNS 실패를 단정하지 않는다 |

### REQ-QAINTEL-021 변경사항 점검하기

**하는 일** 대시보드의 [변경사항 점검하기] 버튼으로 예약 실행과 같은 점검을 바로 돌린다.

**순서**

1. 버튼은 `POST /qa-agent/runs` 에 제품 이름을 보낸다.
2. 서버는 그 제품의 실행 잠금(`data/daily_qa/<slug>/run.lock`)을 확인한다. 잠금이 있고 6시간이 지나지 않았으면 409 "점검이 이미 실행 중입니다." 로 답한다.
3. 잠금이 없으면 예약 실행과 같은 함수(`launch_detached`)로 분리된 별도 프로세스를 띄우고 바로 답한다. 웹 프로세스는 분석을 기다리지 않는다.
4. 실행 프로세스는 SQLite 실행 기록에 현재 단계와 갱신 시각을 남긴다. 단계는 준비, SRS 수집, 이슈 수집, TC 색인, 이벤트, 사양–TC 연결 점검, AI 분석, 결과 저장, 메일이다. AI 분석은 이번 실행에서 준비한 작업의 전체 수와 끝낸 작업 수(`n/N`)를 남긴다. 재시도는 같은 작업으로 센다. 한도에 걸려 남은 작업은 끝낸 것으로 세지 않는다.
5. 화면은 `GET /qa-agent/status` 를 3초마다 읽는다. API는 실행 번호, 시작 시각, 현재 단계, 작업 수, 지난 초, 점검 기록 보기 주소를 준다. 진행 원과 단계·지난 시간을 보이며 다른 사람이 실행 중일 때 새로 연 화면에서도 같다. 준비 중에는 0건을 완료로 오해하지 않도록 시작 응답 뒤 새 실행 기록을 기다린다.
6. 메일을 보내는 동안에도 실행 중으로 보인다. 메일까지 끝나면 진행 원을 멈추고 성공·일부 실패·실패·한도 결과 한 줄과 점검 기록 보기 링크를 보인다. 접속 실패는 완료로 처리하지 않고 연결 확인 중이라고 알린 뒤 다시 읽는다.
7. 실행 잠금이 사라졌는데 시작 후 30초가 지난 기록이 계속 `RUNNING`이면 상태 조회 때 중단 실패로 기록한다. 이미 끝난 실행의 결과는 바꾸지 않는다. 시작 요청 뒤 정상 상태 조회 10회 동안 새 실행을 확인하지 못해도 진행 원을 멈추고 확인 안내를 보인다.
8. [현재 이슈 전체 점검], [기존 TC 검토], [검증 TC 초안]도 제품별 같은 진행 표시를 쓴다. CLI로 요청한 매뉴얼 점검도 대시보드에서 같은 기록을 읽는다. 실행 중에는 그 제품의 요청 버튼을 잠근다. TC 요청은 메일을 보내지 않고 결과 저장 뒤 끝난다.

**지킬 것** 진행 기록은 제품과 실행 번호별로 저장한다. 다른 제품의 진행을 섞지 않으며 결과·이벤트·스냅샷을 진행 기록으로 덮어쓰지 않는다. 1366px·1920px 화면에서 단계 문구·시간·링크를 읽을 수 있어야 한다.

**결과** 202 `{"status": "launched", "pid": <번호>}`.

**안 될 때**

| 경우 | 응답 |
|---|---|
| 이미 실행 중 | 409 "점검이 이미 실행 중입니다." |
| `daily_qa.enabled` 가 false | 409 "점검 기능이 꺼져 있습니다 (daily_qa.enabled)." |
| Polarion 설정 없음(종료일이 오늘인 실행) | 409 "Polarion 설정(POLARION_HOST / POLARION_TOKEN / 프로젝트)이 없습니다." |
| 모르는 제품 | 404 "등록된 제품이 아닙니다." |

> **참고** 종료일이 지난 날인 기간 실행은 Polarion 을 읽지 않고 저장 스냅샷만 쓴다(REQ-QAINTEL-027). 그래서 Polarion 설정이 없어도 띄운다.

**지킬 것**

- 수동 실행용 분석 코드를 따로 두지 않는다. 예약 실행과 같은 CLI·같은 파이프라인이다.
- 버튼 검사와 별개로 실행 프로세스의 잠금(REQ-DAILY-001)이 동시 실행을 막는다. 버튼과 예약이 겹치면 늦게 시작한 쪽이 종료 코드 3 으로 끝난다.

| 파일 | 파일 이름 |

### REQ-QAINTEL-025 Claude 사용량 한도와 실행 예외

**하는 일** Claude 세션(5시간) 한도·주간 한도·인증 실패로 AI 분석을 못 하면 남은 AI 작업을 멈추고, 언제 초기화되는지 화면·수동 실행 응답·메일에 알린다. 한도가 풀리면 밀린 분석을 이어서 한다. 변경 감지는 한도와 상관없이 계속한다.

**언제** Claude 작업이 실패하고 실패 문장이 한도·인증 문제일 때. 예약 실행, [변경사항 점검하기], 한도가 풀린 뒤 다시 도는 실행(catch-up) 모두 같다.

**순서**

1. 실패 문장에서 한도 종류와 초기화 시각을 코드가 읽는다(`app/modules/daily_qa/claude_limits.py`).

| 종류 | 알아보는 문장(예) | 초기화 시각 |
|---|---|---|
| 세션 한도(`SESSION`) | `5-hour limit reached ∙ resets 3pm`, `usage limit reached\|<유닉스 초>`(6시간 안에 풀리는 것) | 문장의 시각 |
| 주간 한도(`WEEKLY`) | `Weekly limit reached ∙ resets Oct 6, 9am` | 문장의 날짜·시각 |
| 한도(종류 모름, `UNKNOWN`) | 시각이 없는 한도 문장 | 모름 |
| 인증 실패(`AUTH`) | `OAuth token has expired`, `Invalid API key`, `API Error: 401`, 줄 맨 앞의 `401 Unauthorized` | 없음. 토큰을 바꿀 때까지 |
| CLI 없음(`CLI_MISSING`) | Claude CLI 를 찾을 수 없음 | 없음. 설치할 때까지 |

   작업 결과 문장 안의 `HTTP 401`, `unauthorized` 같은 말은 인증 실패로 보지 않는다.

   이유: 인증 실패는 토큰을 바꿀 때까지 AI 를 막는다. DICOM·HTTP 이슈를 분석한 결과에 401 이 들어 있다고 AI 가 오래 멈추면 안 된다.

2. 한도가 걸린 작업은 다시 돌리지 않는다. 그 실행에서 아직 돌지 않은 AI 작업도 돌리지 않는다.
3. 분석 대상 이벤트는 `pending` 으로 남기고 실패 횟수를 올리지 않는다.

   이유: 한도는 이벤트 탓이 아니다. 횟수를 올리면 멀쩡한 이벤트가 포기(`abandoned`)로 바뀐다.

4. 한도 정보를 상태 값 `<slug>:claude_limit` 에 저장한다. 다음 실행은 초기화 시각 전이면 Claude 를 부르지 않고 AI 단계를 `Claude 사용량 한도` 로 남긴다. 사전 점검 단계는 `일부 실패`(`partial`)이고 비고에 한도 설명이 들어간다. 인증 실패·CLI 없음은 토큰(또는 CLI)이 바뀔 때까지 같다. 초기화 시각을 모르면 다음 실행이 한 번 다시 시도한다.

5. 일일 모드에서 한도(세션·주간)의 초기화 시각을 알면, 초기화 `catchup_delay_minutes`(기본 5)분 뒤에 한 번 다시 돈다. 초기화가 며칠 뒤여도 같다. 대기 중인 분석이 없으면 AI를 부르지 않는다. 앱 안의 감시 예약(`qa_agent_limit_catchup`, 10분마다)이 시각이 지난 제품을 [변경사항 점검하기]과 같은 함수로 띄운다.

   - 주간 모드·자동 점검 중지·`daily_qa.schedule.enabled: false` 에서는 자동 재개를 하지 않는다(REQ-QAINTEL-038). 주간 모드의 대기 작업은 다음 주 첫 업무일 또는 사용자의 [변경사항 점검하기]에서 이어 간다.

   - 그 제품의 다른 실행이 돌고 있어 띄우지 못하면 catch-up 기록을 지우지 않는다. 10분 뒤 감시 예약이 다시 띄운다.
   - 토큰 없이 Claude CLI 로그인으로 부르는 PC 는 토큰 지문이 늘 같다. 그래서 사전 점검이 로그인을 다시 확인하면 남아 있던 인증 실패 기록을 지우고 분석을 이어 간다(REQ-DAILY-001 4번).
6. 주간 사용량 한도는 자동 재개하지 않는다. 선택한 일일·주간 모드의 예약 실행은 변경 감지와 이벤트 저장만 하고, 초기화 뒤 첫 실행이 밀린 이벤트를 상한(NFR-DAILY-001) 안에서 분석한다. 상한을 넘은 것은 다음 실행으로 넘어간다.

### REQ-QAINTEL-027 기간을 정한 수동 실행

**하는 일** [변경사항 점검하기] 때 시작일과 종료일을 달력으로 골라 그 기간의 변경을 분석한다. 기본값은 시작일 전날, 종료일 오늘이다. 종료일만 주면 시작일은 종료일 전날이다.

**언제** 대시보드의 실행 구역에서 두 날짜를 고르고 [변경사항 점검하기]를 누른다. CLI 는 `--since YYYY-MM-DD --until YYYY-MM-DD` 다.

**순서**

1. 비교 기준은 시작일 날짜(또는 그 전 가장 가까운) 스냅샷이다. 시작일 전에 스냅샷이 하나도 없으면 가장 오래된 스냅샷을 기준으로 삼는다.
2. 종료일이 오늘이면 Polarion 을 새로 읽어 오늘 스냅샷을 저장한다(보통 실행과 같다).
3. 종료일이 지난 날이면 새로 읽지 않는다. 그날(또는 그 전 가장 가까운) 저장 스냅샷과 기준을 비교하고, 스냅샷을 저장하지 않는다.

   - 사양–TC 연결 점검(REQ-DAILY-005) 같은 다른 단계도 종료일 이전 스냅샷만 쓴다. 종료일 뒤 스냅샷은 쓰지 않는다.
   - 대기·실패 이벤트(재시도 대기열, REQ-QAINTEL-006)는 다루지 않는다. 이 실행이 새로 저장한 이벤트만 분석한다.
4. 매일 실행이 이미 찾은 끝 상태는 다시 이벤트로 만들지 않는다. 그래서 이미 분석한 변경은 다시 분석하지 않는다. 같은 대상의 저장된 이벤트와 아래처럼 비교한다.

   - 필드 변경: 바뀐 필드마다 그 대상의 가장 최근 값과 같으면 이미 안다. 제목이 이틀째, 본문이 사흘째 바뀌었어도 기간 실행의 이벤트 하나를 매일 실행의 두 이벤트로 알아본다.
   - 새 댓글: 새 댓글 번호를 모두 이미 본 댓글 이벤트가 담고 있으면 이미 안다.
   - 신규: 같은 대상의 신규 이벤트가 있으면 이미 안다. 그 뒤 상태가 바뀌었어도 같다.
   - 삭제: 그 대상의 마지막 신규·삭제 이벤트가 삭제면 이미 안다.
5. 나머지는 예약 실행과 같다(같은 CLI, 같은 파이프라인, 같은 잠금).

**안 될 때**

| 경우 | 응답 |
|---|---|
| 날짜 모양이 틀림 | 400 "날짜는 YYYY-MM-DD 로 입력하세요." |
| 종료일이 오늘보다 늦음 | 400 "종료일은 오늘보다 늦을 수 없습니다." |
| 시작일이 종료일보다 늦음 | 400 "시작일이 종료일보다 늦습니다." |
| 종료일이 지난 날인데 그날 이전 SRS 스냅샷이 없음 | 400 "<종료일> 이전에 저장된 SRS 스냅샷이 없어 이 기간은 분석할 수 없습니다. 가장 오래된 스냅샷: <날짜>" (스냅샷이 하나도 없으면 "저장된 SRS 스냅샷이 없습니다.") |
| 종료일 이전 저장 스냅샷이 없음(CLI 로 직접 실행) | 수집 단계 `실패` "<날짜> 이전 저장 스냅샷이 없습니다." |

- 이슈 스냅샷이 그 기간에 없으면 SRS 변경만 분석한다. 이슈 수집 단계는 `실패` 이고 실행 결과는 `일부 실패` 다. [변경사항 점검하기] 응답(202)의 `warning` 에 "이 기간에는 저장된 이슈 스냅샷이 없어 SRS 변경만 분석합니다." 를 붙인다.
- 화면의 시작일 달력은 가장 오래된 SRS 스냅샷 날짜보다 앞을 고를 수 없다.

### REQ-QAINTEL-029 ALM-QA-Automation 의 과거 SRS 스냅샷 가져오기

**하는 일** ALM-QA-Automation 의 사양서 자동화(`apps/srs-spec`)가 날짜마다 남긴 SRS 스냅샷을 이 시스템의 SRS 스냅샷으로 바꿔 넣는다. 그러면 이 시스템을 쓰기 전 기간도 기간 실행(REQ-QAINTEL-027)으로 분석할 수 있다.

> **예시** `srs-spec/snapshots/2026-08-31/VXvue/VP-1277.json` 같은 파일 437개가 `data/daily_qa/snapshots/vxvue/srs/2026-08-31.json` 하나가 된다. 그 뒤 [변경사항 점검하기]에서 2026-08-31 ~ 2026-09-22 를 고르면 그 사이 SRS 변경을 분석한다.

**언제** 담당자가 ALM-QA-Automation 이 있는 PC 에서 `scripts/import_alm_srs_history.py` 를 실행할 때. 여러 번 돌려도 결과가 같다.

**입력**

| 값 | 뜻 |
|---|---|
| `--source` | `srs-spec` 의 스냅샷 폴더. 날짜 폴더(`YYYY-MM-DD`) 아래에 ALM 프로젝트 폴더가 있다. 비우면 `daily_qa.alm_history.srs_snapshot_dir` |
| `--product` | 제품 이름. 그 제품 설정의 `alm.project_id` 폴더만 읽는다 |
| `--dry-run` | 쓰지 않고 날짜마다 무엇을 할지만 보인다 |

**순서**

1. 날짜 폴더마다 그 제품 프로젝트 폴더의 JSON(SRS 하나에 파일 하나)을 모두 읽는다.
2. 원본 필드(`description_kr_raw`·`description_raw`·`old_id`·`title`·`status`·`updated`·`is_category`)를 Polarion 응답 모양으로 되돌린다. 그 뒤 매일 실행과 같은 함수로 공통 모델로 바꾼다(REQ-QAINTEL-002·003). 본문 링크 풀기도 같다.
3. 끝에 다른 글자가 붙어 읽지 못하는 파일은 되살릴 수 있을 때만 되살린다.

   - 파일 앞부분이 온전한 JSON 하나이고, 그 뒤에 붙은 글자가 앞 JSON 의 끝부분과 글자 그대로 같으면 앞 JSON 을 쓴다.
   - 그 밖의 깨진 파일은 되살리지 않는다.

   > **예시** 2026-09-07·09-21 은 `srs-spec` 이 같은 날 두 번 동시에 돌아, 짧은 쓰기 뒤에 긴 쓰기의 마지막 100여 글자(`"type": "srs", "uid": …}`)가 남았다. 남은 글자가 앞 JSON 의 끝과 같아 앞 JSON 이 그날의 온전한 기록이다.

4. 그 날짜의 `manifest.json` 이 적은 개수(`expected_total`)와 읽은 개수가 다르거나, 되살리지 못한 파일이 하나라도 있으면 그 날짜를 건너뛴다.

   이유: 일부만 넣으면 빠진 SRS 가 그날 삭제된 것으로 보인다.

5. 이 시스템에 그 날짜 스냅샷이 이미 있으면 덮어쓰지 않는다. 매일 실행이 직접 읽은 것을 먼저 믿는다.
6. 수집 시각은 `manifest.json` 의 `generated_at` 이다. 스냅샷에 출처 `alm_qa_automation` 을 적는다. 되살린 파일이 있으면 그 이름을 스냅샷의 `restored_files` 에 적는다.

**결과** 날짜마다 `가져옴`·`이미 있음`·`건너뜀(<이유>)` 한 줄과 합계. 되살린 날짜는 `가져옴 437건 (되살린 파일 10개)` 처럼 보인다. 종료 코드는 건너뛴 날짜가 있어도 0, 설정·폴더 오류면 2 다.

**지킬 것**

- `srs-spec` 폴더에는 쓰지 않는다. 읽기만 한다.
- 이슈 기록은 가져오지 않는다. ALM-QA-Automation 의 이슈 내보내기(`apps/issue-export`)는 요청한 이슈의 지금 상태만 남기고 날짜별 이슈 전체를 남기지 않는다. 이슈 스냅샷은 이 시스템의 첫 매일 실행부터 쌓인다(REQ-QAINTEL-008).
- 서버에서 기간 실행을 하려면 가져온 스냅샷 파일을 서버의 같은 폴더에 둬야 한다(배포 절차는 `docs/modules/daily-qa.md`).

### REQ-QAINTEL-030 이슈 기록이 없는 기간의 현재 상태 기준 점검

**하는 일** 이슈 스냅샷이 없는 기간에도 사양 변화와 이슈가 맞는지 본다. 기간 동안 이슈가 어떻게 바뀌었는지는 알 수 없으므로, 지금 이슈 전체를 기간의 SRS 변화와 맞춰 본다. 결과에는 "이슈 변경 기록이 없어 현재 상태 기준으로 점검했다"는 알림이 붙는다.

> **예시** 2026-08-31 ~ 2026-09-22 를 고르고 [현재 이슈 전체 점검]을 누른다. 그 기간에 SRS 96건이 바뀌었고 그 SRS 에 연결된 이슈가 371건이다. 이슈 371건과 Spec 판정 이슈 26건이 점검 대상이 된다.

**언제** 대시보드 실행 구역의 [현재 이슈 전체 점검] 버튼(`POST /qa-agent/issue-audit`, `product`·`since`·`until`). CLI 는 `scripts/run_daily_qa.py --issue-audit --since YYYY-MM-DD --until YYYY-MM-DD` 다.

이 절의 용어:

| 용어 | 뜻 |
|---|---|
| 점검 대상 묶음 | 코드가 이슈 하나를 아래 표의 A·B·D 가운데 하나로 나눈 것 |
| 요약 카드 | AI 에 보내는 이슈 요약. 제목·상태·연구소 결과·생성일·수정일·Expected·Actual·발생 원인·조치 내용(앞부분)과 의미 있는 마지막 댓글 2개 |

**순서**

1. 이슈 전체를 지금 상태로 읽는다. 종료일이 오늘이면 Polarion 에서 새로 읽어 오늘 스냅샷으로 저장하고, 지난 날이면 그날(또는 그 전 가장 가까운) 저장 이슈 스냅샷을 쓴다.
2. 시작일 기준 SRS 스냅샷과 종료일 SRS 를 비교해 기간 안에 바뀐 SRS 를 찾는다(REQ-QAINTEL-027 과 같은 기준).
3. 이슈마다 연결된 SRS 를 찾는다. 이슈의 연결 항목(`linked_ids`)과, 제목·본문·재현 절차에 정확히 적힌 SRS 번호만 쓴다. 제목이 비슷하다고 연결하지 않는다.
4. 코드로 이슈를 나눈다. AI 를 쓰지 않는다. 위에서부터 처음 맞는 줄로 정한다.

   | 묶음 | 조건 | 볼 것 |
   |---|---|---|
   | A-수정 | 연결 SRS 가 기간 안에 바뀌었고 연구소 결과가 `FIXED` | 수정 뒤 사양이 바뀌어 이슈의 Expected 가 새 사양과 맞는지(QA 규칙 §43). TC 는 보지 않는다 |
   | A-사양 | 연결 SRS 가 기간 안에 바뀌었고 연구소 결과가 `SPEC`·`NOT_BUG` | 바뀐 사양이 연구소 판정을 뒷받침하는지 |
   | A-기타 | 연결 SRS 가 기간 안에 바뀌었고 그 밖의 연구소 결과 | 바뀐 사양이 이슈의 Expected 와 맞는지 |
   | B | 연결 SRS 가 바뀌지 않았고 연구소 결과가 `SPEC`·`NOT_BUG` | 지금 사양이 연구소 판정을 뒷받침하는지. SRS 마지막 수정이 이슈 마지막 수정보다 앞서면 "판정 뒤 SRS 가 바뀌지 않음" 신호를 붙인다(QA 규칙 §11) |
   | D | 기간 안에 생성된 이슈(위에 해당하지 않음) | 관련 사양 후보와 맞는지 |
   | 대상 아님 | 나머지 | AI 에 보내지 않고 건수만 남긴다 |

5. 이슈마다 점검 이벤트(`ISSUE_AUDIT`) 하나를 저장한다. 바뀐 뒤 값에 묶음, 연결 SRS, 기간 안 SRS 변화(더한 문장·뺀 문장)를 적는다.

   - 같은 이슈·같은 상태·같은 SRS 변화의 이벤트는 다시 넣지 않는다. 그래서 같은 기간을 다시 눌러도 바뀐 조합만 분석한다.
   - 사용량 한도에 걸린 이벤트는 대기로 남고, 다음 실행(예약·[변경사항 점검하기]·한도 초기화 뒤 다시 실행)이 이어서 분석한다. 실행마다 남은 점검 이벤트 수를 단계 비고에 보인다.

6. AI 분석(`qa-issue-spec-audit` Skill)은 토큰을 아끼려고 다음처럼 묶는다.

   - SRS 하나와 그 SRS 에 연결된 이슈 요약 카드를 한 작업에 넣는다. SRS 내용은 작업마다 한 번만 넣는다. 한 작업의 이슈는 `daily_qa.intelligence.audit_batch_size`(기본 10)건까지다.

   - SRS 는 바뀐 문장과 이슈 내용에 가까운 문단 3개만 넣는다. 바뀌지 않은 SRS 도 가까운 문단만 넣는다.

   - TC 후보는 넣지 않는다(사용자 결정 2026-10-02). 모델이 TC 영향을 쓰면 코드가 빼고 기록을 남긴다.

   - QA 규칙은 Skill 이 정한 절(§6·7·10·11·38·43)만 읽는다.

   - 점검 작업은 `daily_qa.intelligence.audit_model` 모델로 부른다. 비우면 `ai.claude.models.light` 다.

   - 결과가 `충돌`·`부분 일치` 인 이슈도 현재 분석의 근거와 QA 할 일을 상세 화면에서 확인한다. 사용을 종료한 단일 이슈 분석으로 이동하는 링크는 없다.

7. 판정은 이슈마다 하나다.

   | 판정 값 | 화면 이름 |
   |---|---|
   | `CONSISTENT_WITH_SPEC` | 일치 |
   | `PARTIALLY_CONSISTENT` | 부분 일치 |
   | `CONTRADICTS_SPEC` | 충돌 |
   | `INSUFFICIENT_EVIDENCE` | 근거 부족 |

   A-수정 이슈의 TC 영향은 이 점검에서 정하지 않는다. 필요하면 사람이 관련 사양 변경 분석에서 [기존 TC 검토]을 누른다.

**결과**

- 점검 기록 보기와 요약 메일 맨 위에 알림 한 줄이 보인다. "이 기간에는 이슈 변경 기록이 없어 이슈 변화를 현재 상태 기준 점검으로 대신했습니다. 기간 중 상태 변화와 중간 댓글은 알 수 없습니다."
- 그 아래에 이슈 전체 수, 기간 안 생성 수, 기간 안 수정 수, 묶음별 수, 대상 아님 수가 보인다.
- 판정 카드마다 `현재 상태 기준(기간 이력 없음)` 표시가 붙는다.

**안 될 때**

| 경우 | 사용자에게 보이는 것 |
|---|---|
| 기간에 SRS 스냅샷이 없음 | REQ-QAINTEL-027 과 같은 400 문구 |
| 종료일이 오늘인데 Polarion 설정이 없음 | "Polarion 설정(POLARION_HOST / POLARION_TOKEN / 프로젝트)이 없습니다."(409) |
| 종료일이 지난 날인데 그날 이전 이슈 스냅샷이 없음 | "<종료일> 이전 이슈 스냅샷이 없어 현재 이슈 전체 점검을 할 수 없습니다. 종료일을 오늘로 고르세요."(400) |
| 다른 실행 중 | "점검이 이미 실행 중입니다."(409) |

**지킬 것**

- verified·closed 이슈가 판정 기준이다. `in_review`·`in_progress`·`open`·`reopened` 이슈는 카드에 "참고만" 표시를 붙이고 Expected 근거로 쓰지 않는다(지침 §6).
- 연구소 댓글이나 조치 내용만으로 `일치` 를 내지 않는다(QA 규칙 §7). 실제로 전체를 보지 않았으면 "전수조사 완료"라고 쓰지 않는다(QA 규칙 §10).
- 실행당 작업 상한(`daily_qa.max_tasks_per_run`)은 이 점검에도 적용된다. 넘은 묶음은 대기로 남아 다음 실행이 이어 간다. 점검 전체 건수에는 따로 상한을 두지 않는다.

### REQ-QAINTEL-031 사양 변경 분석 (자동)

**하는 일** 새로 생기거나 바뀐 SRS 마다 무엇이 바뀌었는지, QA 가 확인할 것이 있는지, 관련 과거 이슈가 있는지 짧게 정리한다. TC·Checklist·매뉴얼은 보지 않는다. Skill `qa-spec-change-summary`.

> **예시** VP-767 에 "Reload 뒤에도 목록 상태를 유지한다." 가 더해졌다. 카드에는 `검토 필요` 와 "Reload 뒤 목록 유지 조건이 생겼다." 가, 할 일에는 "Reload 뒤 목록 유지 확인" 이 보인다.

**언제** REQ-QAINTEL-010 표에서 `SRS_CREATED`·`SRS_UPDATED` 이벤트가 있을 때. 예약·[변경사항 점검하기]·기간 실행이 모두 같다.

**입력** SRS 번호·본문, 바뀐 필드, 바뀌기 전·후 값, 더한 문장·뺀 문장, 관련 과거 이슈 후보(REQ-QAINTEL-016 입력의 이슈 후보와 같은 순서), 연관 사양·사양서 조각.

**순서**

1. 바뀐 것(`sections.change`): 한두 문장 요약과 바뀐 요구사항 문장 5개까지.
2. 관련 과거 이슈(`sections.related_issues`): 후보 가운데 관계있는 것만 5개까지. 관계는 `EXISTING_DEFECT`·`PAST_FIXED`·`PAST_SPEC`·`SAME_FUNCTION_REGRESSION` 이다.
3. 판정은 아래 넷 가운데 하나다.

   | 판정 | 뜻 | 결론 단계 |
   |---|---|---|
   | `NO_QA_IMPACT` | 서식·오탈자·표현만 바뀌었다 | 문제 없음 |
   | `QA_CHECK_NEEDED` | 동작·조건·값이 바뀌어 QA 가 확인할 것이 있다 | 검토 필요 |
   | `CONFLICTS_WITH_PAST_DECISION` | 과거 Spec 판정이나 수정 결과가 새 사양과 다르다 | 사양과 다름 |
   | `SPEC_UNCLEAR` | 바뀐 문장이 여러 뜻으로 읽혀 Expected 를 정할 수 없다 | 검토 필요 |

4. 요약은 한두 문장, QA 할 일은 3줄까지 쓴다.

**결과** SRS 변경마다 Finding 하나(분석 종류 `SPEC_COVERAGE`, Skill `qa-spec-change-summary`). 화면에서 [기존 TC 검토]을 누를 수 있다(REQ-QAINTEL-016).

**지킬 것**

- 작업 입력에 TC 후보·매뉴얼 후보를 넣지 않고, 작업 폴더 `context/` 에 TC 색인·매뉴얼을 두지 않는다.
- 관련 과거 이슈는 오늘 이슈 스냅샷에 있는 번호만 남긴다. TC 비교 구획이나 초안이 오면 빼고 메모를 남긴다(REQ-QAINTEL-017).
- 바뀐 것의 요약(`sections.change.summary`)이 비었거나 문장이 아니면 결과를 버린다.

### REQ-QAINTEL-032 검증 TC 초안 (요청할 때만)

**하는 일** 수정 완료 이슈 하나에 대해 기존 TC 가 원인을 다시 잡는지 보고, 잡지 못하는 것만 검증 TC 초안으로 만든다. Skill `qa-verification-tc-draft`.

**언제** 사람이 수정 완료 이슈 분석(REQ-QAINTEL-013) 상세 화면에서 [검증 TC 초안 만들기]를 누를 때(`POST /qa-agent/findings/<번호>/tc-draft`). CLI 는 `scripts/run_daily_qa.py --on-demand tc-draft --finding <번호>` 다.

**순서**

1. REQ-QAINTEL-016 의 요청 실행 순서 1~4 와 같다. 입력은 수정 완료 이슈 분석의 입력에 TC 후보를 더한 것이다.
2. 기존 TC 마다 원인을 덮는지와 이유(`sections.tc_coverage`)를 적는다.
3. 검증 TC 초안은 기존 형식(`DraftTc`: `kind`, `srs_no`, `change`, `change_detail`, `title`, `precondition`, `test_step`, `expected_result`, `test_data`)을 쓴다. `kind` 는 `수정확인` 또는 `Regression` 이다. 관점(`perspective`)은 `DIRECT_FIX`·`REGRESSION`·`STATE_TRANSITION`·`BOUNDARY`·`NEGATIVE`·`INTEGRATION` 가운데 하나다.

**결과** Finding 하나(분석 종류 `TC_DRAFT`, `sections.source_finding` = 원래 분석 번호, 초안 목록). 초안 Excel(REQ-QAINTEL-018)이 생긴다.

**안 될 때**

| 경우 | 응답 |
|---|---|
| 원래 분석이 수정 완료 이슈 분석이 아님 | 400 "수정 완료 이슈 분석에서만 검증 TC 초안을 만들 수 있습니다." |
| 다른 실행 중 | 409 "점검이 이미 실행 중입니다." |
| 사용량 한도 중 | AI 를 부르지 않고 단계가 `limit` 으로 끝난다. 원래 분석은 그대로다 |

**지킬 것**

- 사양 판정이 `SPEC_UNDEFINED`·`INSUFFICIENT_EVIDENCE` 면 초안을 만들지 않는다. 대신 "Checklist TC 생성 보류" 와 확인할 점을 남긴다.
- 오늘 연구소 결과가 `FIXED` 가 아닌 이슈에 초안을 내면 코드가 Finding 을 버린다.
- 최신 SRS·사양서 근거가 없으면 초안을 빼고 "Checklist TC 생성 보류" 를 남긴다. 기존 TC만으로 Expected 를 확정하지 않는다.
- 과거 자동 분석 결과와 요청 결과는 분석 종류·원래 분석 번호로 구분한다. 같은 버튼에서 같은 대상·판정·초안이 열려 있으면 다시 저장하지 않는다(REQ-DAILY-018).

### REQ-QAINTEL-033 결론 단계와 짧은 카드

**하는 일** 분석마다 다른 판정 값을 다섯 가지 결론으로 줄여, 카드 한 장만 보고 다음 행동을 정하게 한다.

**순서**

1. 판정 값을 아래 표로 결론 단계에 맞춘다. 표에 없는 값은 `검토 필요` 다.

   | 결론 단계 | 판정 값 |
   |---|---|
   | 사양과 다름 | `SPEC_VIOLATION`, `CONTRADICTS_SPEC`, `CONFLICTS_WITH_PAST_DECISION` |
   | 검토 필요 | `PARTIALLY_CONSISTENT`, `PARTIALLY_SUPPORTED`, `SPEC_UNDEFINED`, `SPEC_AMBIGUOUS`, `SPEC_NOT_FOUND`, `QA_CHECK_NEEDED`, `SPEC_UNCLEAR`, `PARTIALLY_COVERED`, `NOT_COVERED`, `SPEC_REVIEW_REQUIRED`, `QA_ACTION_REQUIRED`, `SPEC_CLAIM`, `REQUIREMENT_INFORMATION`, 표에 없는 값 |
   | 근거 부족 | `INSUFFICIENT_EVIDENCE` |
   | 참고 | `ROOT_CAUSE_INFORMATION`, `RESOLUTION_INFORMATION`, `REPRODUCTION_INFORMATION`, `OTHER_SIGNIFICANT_INFORMATION` |
   | 문제 없음 | `CONSISTENT_WITH_SPEC`, `SUPPORTED_BY_SPEC`, `FULLY_COVERED`, `NO_QA_IMPACT`, `NOT_SIGNIFICANT` |

2. QA 할 일은 권고(`sections.recommendation.actions`·`checks`) → 확인할 점(`sections.qa_analysis.checks`) → 조치 문장(`action`, 줄마다 하나) 순서로 찾아 3줄까지 보인다.
3. 점검 기록 보기 화면의 목록은 결론 단계 순서(사양과 다름 → 검토 필요 → 근거 부족 → 참고 → 문제 없음)로, 같은 단계는 최신이 먼저다. `문제 없음` 은 접어 둔다. 대시보드와 결과 페이지의 목록은 이 순서와 접기를 쓰지 않고 REQ-QAINTEL-046의 정렬을 따른다.

**지킬 것**

- 카드에 칩 줄(기존 Issue 수, 조치 수, 경고 이름 등)을 두지 않는다. 그 정보는 상세 화면의 근거 자료와 분석 기록에 있다.
- 판정·신뢰도·댓글 분류는 한국어로 보이고 원래 코드는 도움말에 남긴다. 새 댓글 요약의 작성 기준은 REQ-QAINTEL-015를 따른다. 다른 분석 종류의 요약 규칙은 이번 변경에서 바꾸지 않는다.
- 조치 문장(`action`)은 Finding 표에 칸이 없어 `sections.action` 에 함께 저장한다. 저장하지 않으면 카드의 할 일이 비어 보인다.

### REQ-QAINTEL-034 매뉴얼 점검 (요청할 때만)

**하는 일** 최근 7일 사양 변경이 매뉴얼에 반영됐는지 본다(REQ-DAILY-006 의 점검과 같은 Skill `qa-manual-completeness`).

**언제** 사람이 `scripts/run_daily_qa.py --on-demand manual-check` 를 실행할 때만 돈다. 화면 버튼은 두지 않는다(사용자 결정 2026-10-02). 예약·[변경사항 점검하기]·주간 요일·매뉴얼이 바뀐 날에도 자동으로 돌지 않는다.

이유: 매뉴얼은 사람이 넣는 자료라 최신이 아닐 수 있다.

**결과** 단계 `F` 의 결과와 Finding. 자동 실행의 단계 `F` 는 늘 `not_due` 이고 비고는 "매뉴얼 점검은 자동으로 돌지 않습니다." 로 시작한다. 예전의 미룬 점검 상태(`manual_check_due`)는 읽지도 쓰지도 않는다.

### REQ-QAINTEL-035 놓친 오늘 예약 실행 만회

**하는 일** 예약 시각(기본 04:00)에 앱이 꺼져 있었거나 PC가 절전 중이었으면, 앱이 다시 돌 때 오늘 몫의 예약 실행을 한 번 띄운다.

> **예시** 평일 04:00에 서버가 꺼져 있었고 08:01에 다시 켜져 앱이 떴다. 앱은 08:02쯤 오늘 예약이 아직 돌지 않은 것을 알고 예약 실행을 띄운다. 그날 다시 띄우지는 않는다.

**언제** 앱이 시작되고 1분 뒤에 한 번 확인하고, 그 뒤 10분마다 확인한다(감시 예약 `qa_agent_missed_schedule`).

**순서**

1. 활성 제품마다 오늘(한국 시간)이 제품별 모드의 실행일(REQ-QAINTEL-038)인지, 지금이 예약 시각보다 늦은지 본다. 둘 중 하나라도 아니면 아무것도 하지 않는다. 자동 점검 중지 또는 서버 예약 비활성화 상태에서도 실행하지 않는다.
2. 오늘 예약을 이미 처리했는지 제품별 상태 기록(`<slug>:scheduled_date`, 한국 시간 날짜)으로 본다. 오늘 날짜가 적혀 있으면 아무것도 하지 않는다.
3. 처리하지 않았으면 REQ-QAINTEL-001 의 예약 실행과 같은 함수를 부른다. 공휴일 건너뛰기, 실행 잠금, Polarion 설정 확인이 그대로 적용된다. 앱 로그에 `qa_agent_missed_schedule product=<slug> date=<날짜> time=<예약 시각>` 을 남긴다.
4. 실행을 띄웠거나 휴일·기존 필수 설정 확인으로 오늘 몫을 처리했으면 상태 기록에 오늘 날짜를 적는다. 다른 실행이 진행 중이거나 자동 점검 중지·선택한 모드의 실행일 아님·서버 예약 비활성화면 적지 않는다. 같은 날 다시 켰을 때 오늘 만회를 확인할 수 있다.

**지킬 것**

- 정시 예약(REQ-QAINTEL-001)도 실행을 띄운 뒤 같은 상태 기록에 오늘 날짜를 적는다. 그래서 정시에 돈 날에는 만회 실행이 없다.
- 정시 예약과 만회 확인이 같은 순간에 깨어나도 실행은 하나만 뜬다. 두 경로는 한 잠금 안에서 상태 기록을 확인하고 적는다.
- 지난 날의 놓친 예약은 만회하지 않는다. 오늘 몫만 띄운다.

이유: 다음 실행이 마지막으로 저장한 스냅샷과 비교하므로 놓친 날의 변경도 그 실행이 함께 찾는다(REQ-QAINTEL-003·004).

- [변경사항 점검하기]·기간 실행·catch-up 실행은 상태 기록을 바꾸지 않는다. 사람이 아침에 [변경사항 점검하기]를 눌렀어도 그날 예약 실행은 따로 돈다. 앱이 04:00에 켜져 있을 때와 같다.

**설정**

| 키 | 기본값 | 뜻 |
|---|---|---|
| `daily_qa.schedule.run_missed` | `true` | `false` 면 놓친 예약을 만회하지 않는다. 정시 예약만 돈다 |
| `daily_qa.schedule.enabled` | `true` | `false` 면 정시 예약과 함께 만회 감시도 등록하지 않는다(REQ-QAINTEL-001) |

> **주의** 이 기능을 처음 설치한 날에는 상태 기록이 비어 있다. 예약 시각이 지난 평일에 설치하면 그날 예약 실행이 한 번 뜬다.

### REQ-QAINTEL-036 진행 중인 실행 중단

**하는 일** 사용자가 진행 표시의 [분석 중단]으로 현재 제품의 공유 실행을 중단한다. 다른 사용자가 시작한 실행도 현재 실행이면 중단할 수 있다.

**언제** 실행 번호가 있는 실행이 진행 중일 때. 메일 발송을 이미 시작한 실행은 중단할 수 없다.

**순서**

1. `POST /qa-agent/runs/<실행 번호>/cancel?product=<제품>` 을 받는다. 해당 제품의 현재 실행인지 DB 와 실행 잠금으로 확인한다.
2. 잠금의 실행 번호·제품·PID·프로세스 시작 식별값과 운영체제의 실제 Python 실행 명령을 대조한다. 이 저장소의 `scripts/run_daily_qa.py --product <제품>` 실행만 허용한다.
3. DB 에 중단 요청 시각과 이유를 한 번 기록하고 202(`status: cancelling`)을 돌려준다. 상태 조회는 `current_run_id` 와 `cancel_requested` 를 보여 준다.
4. 실행 프로세스가 요청을 확인한다. Claude 를 기다리는 동안에도 확인하며, 자신이 실행한 Claude 하위 프로세스만 종료한다. Polarion 요청 중이면 현재 요청이 끝난 뒤 다음 단계로 넘어가기 전에 중단한다.
5. 이미 수집·저장한 자료와 Finding·사용량·완료 작업 수를 보존한다. 끝낸 분석의 이벤트는 완료로 남기고, 아직 끝내지 못한 분석은 대기로 남긴다. 실패 횟수는 중단 때문에 늘리지 않는다.
6. 상태를 `CANCELLED`(사용자 중단)로 저장하고 잠금을 해제한다. 진행 원은 멈추고 중단 결과·진행 숫자·상세 링크를 보여 준다. 중단 실행은 메일을 보내지 않는다.

**안 될 때**

| 경우 | 응답 |
|---|---|
| 없는 실행 또는 다른 제품의 실행 | 404 |
| 이미 완료한 실행, 현재 실행이 아님, 잠금·PID·시작 식별값·실행 명령 불일치 | 409. 상태를 바꾸지 않는다 |
| 메일 발송 시작 뒤 | 409. 진행을 계속 조회한다 |
| 중단 요청을 반복함 | 실행 중이면 같은 202. 중단을 마쳤으면 200(`status: CANCELLED`) |

**지킬 것** PID 만으로 외부 프로세스를 종료하지 않는다. PID 가 다른 프로세스에 다시 쓰이면 중단을 거절한다. Linux 와 Windows 에서 같은 DB 요청을 쓰며, 중단 요청과 메일 발송 시작은 동시에 확정되지 않게 한다. 웹 서비스는 중단하거나 재시작하지 않는다.

Windows에서 소유한 하위 프로세스까지 종료할 준비가 실패하면 Claude를 시작하지 않는다. 실행이 끝나거나 중단돼도 해당 실행이 만든 하위 프로세스만 정리한다.

### REQ-QAINTEL-037 같은 분석 결과 다시 쓰기

**하는 일** 작업 묶음의 입력과 분석 조건이 모두 같으면 검사를 통과한 성공 결과를 다시 쓴다. Claude 호출과 새 토큰 사용은 0이며 원본 실행을 확인할 수 있다.

**순서**

1. 제품·분석 종류·요청 실행 모드, 모델·추론 정도, 대상 본문·댓글·변경 전후 값·후보·사용자 답변을 비교한다. 사양과 검색 가능한 색인, 제품 규칙·Skill·출력 형식의 내용도 같은지 확인한다.
2. 실행·작업·이벤트 번호만 비교에서 제외한다. 대상과 근거 번호, 후보 순서, 현재 유효 상태는 보존한다. 작업 묶음 전체가 같은 경우만 다시 쓴다.
3. 저장본이 있으면 현재 작업 번호로 읽고 현재 형식과 근거를 다시 검사한다. 맞지 않으면 Claude 로 새로 분석한다.
4. 현재 실행과 이벤트에 결과를 연결한다. 원본 실행·작업·Finding 번호를 기록하고 이전 승인 상태는 옮기지 않는다.
5. 작업 묶음이 성공하고 모든 Gate 가 `PASS` 인 결과만 다시 쓴다. 실패·중단·한도·미해결 질문·제거된 근거·근거 부족·접근 불가 결과는 제외한다. 비교용 해시가 없는 과거 결과는 자동으로 편입하지 않는다.

> **참고** 완료한 작업 뒤에 다른 작업이 실패하거나 전체 실행이 중단돼도 완료한 작업의 성공 결과는 보존하고 다시 쓸 수 있다.

**결과** 재사용한 작업 수와 Finding 수, 원본 실행 링크를 실행 결과에 표시한다. 재사용 횟수와 새 Claude 호출·사용량은 따로 센다. 중단 요청은 재사용 전에도 확인한다.

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `daily_qa.result_cache.enabled` | `true` | 같은 성공 결과를 다시 쓴다. 설정이 없을 때도 켜진다 |

**지킬 것** 공용 응답 저장본(`ai_cache`)에서 일일 QA 결과를 따로 구분한다. 모델은 기존 설정을 유지한다. 저장본이 없거나 검사를 통과하지 못하면 기존 분석 경로를 따른다.

**안 될 때** 저장본 조회·저장에 문제가 생기면 감사 기록에 남긴다. 조회 실패는 새 분석으로 진행하고, 저장 실패는 이미 성공한 분석 결과를 유지한다.

### REQ-QAINTEL-038 자동 점검 일일·주간·중지 설정

**하는 일** 관리자가 QA Agent 화면의 [자동 분석·메일 사용]과 [현재 검증 진행 중]을 저장해 제품별 자동 분석과 요약 메일 주기를 정한다. 사내 웹 화면에서 변경할 수 있다.

| 자동 분석·메일 사용 | 현재 검증 진행 중 | 자동 분석과 메일 |
|---|---|---|
| 켜짐 | 켜짐 | 매 업무일 예약 시각에 실행한다 |
| 켜짐 | 꺼짐 | 매주 첫 업무일 예약 시각에 한 번 실행한다 |
| 꺼짐 | 어느 값이든 | 자동 분석과 메일 전송을 중지한다 |

**입력** 제품과 두 참·거짓 값(`enabled`, `validation_period`)을 받는다. 처음 저장하기 전에는 둘 다 참으로 간주해 기존 일일 동작을 유지한다. 화면의 두 체크박스와 [저장]으로 적용한다.

**순서**

1. `GET /qa-agent/automation-policy?product=<제품>`은 현재 설정을 JSON으로 반환한다. `POST /qa-agent/automation-policy`는 제품과 두 값을 폼으로 받고 저장 후 해당 제품의 대시보드로 303 이동한다. 체크하지 않은 값은 거짓이다.
2. 설정은 공용 DB에 제품별로 저장한다. 변경 시각·요청 위치·두 값을 변경 이력에 남긴다. 읽기와 변경 모두 일반 웹 접속을 허용한다. 설정 탭의 저장 제한(관리자 로그인 또는 서버 직접 접속, REQ-AICALL-007·REQ-WEB-008)은 그대로 유지한다.
3. 업무일은 한국 시간의 월~금에서 등록된 공휴일과 추가 휴일을 뺀 날짜다. 주간 모드는 월요일이 쉬는 날이면 같은 주의 다음 업무일에 실행한다. 그 주에 업무일이 없으면 실행하지 않는다.
4. 다음 실행 시각·놓친 예약 만회·정시 실행이 같은 정책을 사용한다. 주간 만회는 그 주 첫 업무일의 놓친 예약만 당일에 한 번 처리한다. 지난 실행일의 예약은 만회하지 않는다(REQ-QAINTEL-035).
5. 한도(세션·주간) 뒤 자동 재개는 일일 모드에서만 가능하다(REQ-QAINTEL-025·049). 주간 모드의 대기 분석은 다음 주 첫 업무일 또는 사용자의 [변경사항 점검하기]에서 이어 간다. 중지 상태에서는 자동 재개를 하지 않는다.
6. 서버의 `daily_qa.schedule.enabled: false`는 모든 자동 실행 경로에서 우선 적용한다. 제품 설정을 켜도 담당자 PC의 `config.local.yaml`에 저장된 예약 비활성화를 바꾸지 않는다.
7. [변경사항 점검하기]은 자동 점검 중지 중에도 분석할 수 있다. 메일을 보내기 직전에 현재 설정을 다시 읽으며 중지 중에는 메일을 생략하고 이유를 실행 기록에 남긴다.

**결과** 화면에 저장한 두 값, 현재 모드, 다음 자동 실행 시각 또는 중지 이유를 표시한다. 주간 한도 대기는 다음 주 예약 또는 수동 실행에서 이어 간다는 안내를 표시한다.

**지킬 것** 중지로 바꿔도 진행 중인 분석을 강제로 종료하지 않는다. 다음 자동 실행과 다음 메일부터 막는다. 진행 중인 실행의 종료는 [분석 중단](REQ-QAINTEL-036)을 사용한다. 기존 기록·대기 이벤트·결과·수신자는 설정 변경으로 지우거나 바꾸지 않는다.

### REQ-QAINTEL-039 사용량 한도 증거 캡처

**하는 일** 서버의 Claude 계정이 세션(5시간) 한도나 주간 한도에 걸리면, 그 순간의 Claude CLI `/usage` 화면을 실제 터미널 창에서 찍어 PNG로 남긴다. 팀 공유폴더(`99. AI 사용량 한도 초과`)에 올릴 증거 사진으로 쓴다.

> **예시** `스크린샷 2026-10-14 202600_Claude13_세션한도.png` 에 `Current session 100% used` 와 초기화 시각이 보인다. 같은 이름의 `.txt` 에 그 화면의 글자가 그대로 들어 있다.

**언제** 일일 점검이 Claude 한도를 감지한 순간(REQ-QAINTEL-025 의 `_hit_limit`)이다. 시험 실행(`--dry-run`)과 인증 실패·CLI 없음에는 찍지 않는다. 사람이 `scripts/capture_limit_evidence.py` 로 직접 찍을 수도 있다.

**순서**

1. 점검과 같은 인증정보로 화면 없는 가상 디스플레이(`Xvfb`)에 실제 터미널 프로그램(`xterm`)을 띄우고, 그 안에서 Claude CLI 를 연다. 표시 시간대는 한국 시간(`TZ=Asia/Seoul`)이다.
2. 폴더 신뢰 확인이 나오면 "Yes" 를 고른다. 입력 칸이 뜨면 `/usage` 를 입력한다. 키 입력은 `xdotool` 이 실제 키보드 입력처럼 보낸다.
3. 사용량 패널이 그려지면 터미널 창의 픽셀을 그대로 PNG로 저장한다(`import -window`). 같은 순간의 화면 글자는 CLI 원본 출력(`script`)을 터미널 화면으로 다시 그려(`pyte`) 얻는다.
4. 화면 글자에서 `Current session` 또는 `Current week` 가 `100% used` 인지 확인한다. 둘 다 100% 가 아니면 증거 폴더에 넣지 않고 이유를 로그에 남긴다.
5. 증거 폴더(`data/limit_evidence/`)에 PNG 와 `.txt` 를 저장한다. `.txt` 에는 화면 글자, 감지한 한도 문장 원문, 한국 시간, 계정 표시가 들어간다. 토큰 값은 넣지 않는다.
6. 사람이 웹 화면 `/claude/limit-evidence` 에서 목록과 사진을 본다.
7. 담당자 PC 의 Windows 예약 작업(`scripts/sync_limit_evidence.ps1`, 10분마다)이 파일을 받아 공유폴더의 임시 파일에 복사한다. 해시를 확인한 뒤 최종 이름으로 바꾸며, 기존 파일이 다르면 다시 복사한다.

이유: 공유폴더에 쓰려면 담당자의 Windows 계정이 필요하다. 그 비밀번호를 공용 서버에 두지 않으려고, 이미 로그인된 PC 가 복사를 맡는다.

**결과**

| 항목 | 내용 |
|---|---|
| 파일 이름 | `스크린샷 YYYY-MM-DD HHMMSS_<계정>_<세션한도·주간한도>.png` 와 같은 이름의 `.txt`. 시각은 한국 시간이다 |
| 계정 표시 | 설정값이 없으면 CLI 로그인 이메일 앞부분(`Claude13@vieworks.com` → `Claude13`) |
| 한도 이름 | 화면에서 100% 인 쪽. 세션이 100% 면 `세션한도`, 아니고 주간이 100% 면 `주간한도` |
| 웹 화면 | `/claude/limit-evidence` 에 최신 순 목록과 사진. `/claude/limit-evidence.json` 은 같은 목록의 JSON |

**설정**

| 키 | 기본값 | 뜻 |
|---|---|---|
| `daily_qa.limit_evidence.enabled` | `true` | `false` 면 찍지 않는다 |
| `daily_qa.limit_evidence.account_label` | `""` | 파일 이름의 계정 표시. 비우면 CLI 로그인 이메일 앞부분 |
| `daily_qa.limit_evidence.timeout_seconds` | `60` | 터미널을 띄우고 패널이 보일 때까지 기다리는 최대 시간 |

**안 될 때**

| 상황 | 동작 |
|---|---|
| `Xvfb`·`xterm`·`xdotool`·`import` 중 하나가 없음 | 찍지 않고 `limit_evidence_skipped reason=tools_missing` 로그 |
| 제한 시간 안에 패널이 안 보임 | 띄운 프로그램을 모두 끝내고 `reason=timeout` 로그 |

| 다른 점검 프로세스가 찍는 중 | 기다리지 않고 건너뛴다 |

**지킬 것** 캡처가 실패해도 한도 처리와 점검은 그대로 이어 간다. 사진은 그리거나 고치지 않는다. 터미널 창을 찍은 그대로 둔다. `/usage` 만 입력하므로 Claude 토큰을 쓰지 않는다.

### REQ-QAINTEL-040 분석 입력 크기와 규칙 반복 읽기 줄이기

**하는 일** 같은 근거를 반복 전달하거나 규칙을 여러 번 찾는 양을 줄인다. 분석 대상, 후보 원문, 근거 위치, 모델과 판정 기준은 유지한다.

**순서**
1. 변경 분석·현재 이슈 점검의 작업을 만든 뒤, 입력 JSON이 `daily_qa.intelligence.max_input_chars`(기본 60,000자)를 넘으면 이슈 사이에서 나눈다. 기존 건수 상한도 유지한다.
2. 입력의 같은 후보 내용은 `shared_candidates`에 한 번 넣는다. 각 이슈의 후보에는 `shared_candidate` 참조와 그 이슈의 `match`를 남긴다. 내용이나 위치가 다른 후보는 합치지 않는다. 입력 사본만 바꾸며 원본 자료는 유지한다.
3. 공통·제품·작업 Skill과 출력 형식을 프롬프트에 넣는다. 제품 Skill의 `guide-sections.json`에 해당 작업의 절 번호가 있으면 가이드 원문에서 그 절과 하위 절을 미리 넣는다. 이미 넣은 자료를 다시 읽지 않도록 안내한다.
4. 누락된 절이나 추가 조건에 필요한 원문은 기존 읽기 경로로 확인한다. 절 목록이 없는 제품은 기존 규칙 조회를 유지한다.
5. 실행 기록에 작업별 입력 글자 수와 단일 대상의 기준 초과 여부를 남긴다. 분할 뒤 실행당 작업 수 제한을 적용하고 남은 이벤트는 다음 실행으로 넘긴다.

> **예외** 한 이슈만으로 입력 기준을 넘으면 원문을 자르지 않고 한 작업으로 유지한다. 글자 수는 토큰 수나 구독 사용량 예측값이 아니다.

### REQ-QAINTEL-041 실행 전 대기 분석 안내

**하는 일** 날짜를 고르는 화면에서 저장된 대기 분석이 함께 실행된다는 사실과 그 규모를 알 수 있다.

**순서**
1. `GET /qa-agent/run-preview`는 제품과 시작일·종료일을 검증하고 저장된 대기·실패 이벤트만 읽는다. Polarion·AI 호출, 이벤트·실행 기록 저장은 하지 않는다.

3. 현재 이슈 전체 점검은 저장된 미완료 전체 점검 이벤트를 별도로 안내한다. 새로 선정될 이슈 수는 실행 후 확정한다고 표시한다.
4. 두 버튼 아래에 전체 대기 이벤트 수, 선택·보류 건수, 종류별 대상 수와 건수 기준 묶음 수를 표시한다. 입력 크기에 따른 추가 분할·작업 수 상한·새 변경 수집으로 달라질 수 있다고 알린다.
5. 날짜 변경 때 갱신하고 늦게 도착한 이전 응답은 표시하지 않는다. 조회 실패를 0건으로 표시하지 않고 확인하지 못했다고 안내한다. 실행 버튼의 기존 동작은 유지한다.


### REQ-QAINTEL-042 절약 모드와 선택 분석

**하는 일** 기간을 고르면 AI 없이 대상부터 준비하고, 사용자가 선택한 대상만 분석한다.

- `daily_qa.savings.enabled`가 true이면 수동 준비는 AI 없이 수집·대상 확인만 한다. 예약 실행은 REQ-QAINTEL-048에 따라 두 분석을 모두 수행하고, 호출 직전 사용률이 기준에 닿으면 REQ-QAINTEL-043에 따라 멈춘다. 기본은 false로 기존 설치를 보존한다.
- 목적은 `spec`(사양 변경과 검증 범위), `issues`(신규·업데이트 이슈와 QA 대응), `all`(둘 다)이다. 수동 준비 화면은 자동 전체 선택을 하지 않는다.
- 준비한 대상은 제품·기간·자료/규칙/설정 지문과 함께 저장한다. 생성 30분 경과, 제품 불일치, 자료 변경, 선택 밖 대상은 실행 전에 거절한다.
- 대상 선택은 `상세 분석` 화면(`/qa-agent/select?product=<제품>`)에서 한다. 점검 화면(`/qa-agent`)에는 준비 버튼과 한 줄 안내만 둔다. 안내는 `준비된 대상 <N>건 · 상세 분석 열기` 또는 `준비 목록 만료 · 다시 준비하세요`이고, 자바스크립트 없이도 보인다. 준비가 끝나면 진행 표시에 `상세 분석 열기` 링크가 나온다. 상단 메뉴에서는 `사양·이슈 변경 점검`이 켜진 채로 둔다.
- `상세 분석` 화면은 선택 목록, `선택 대상 분석`, `선택 1건 Opus 재검토`, 오늘 호출 횟수와 호출을 멈추는 사용률 기준 안내를 보인다. 목록의 각 행은 체크박스(행 왼쪽)·번호·제목·분석 종류·작성자·이슈 업데이트(한국 시간)·분석 이유를 담고, 행 어디를 눌러도 선택된다. 분석 이유는 그 대상을 고른 변경 이벤트 이름(예: `신규 이슈`, `SRS 변경`)이다.

> **예시** 이슈 VP-200 행은 `[ ] VP-200 · 검색 오류 · 수정 완료 이슈 · 홍길동 · 2026-10-14 17:42 (한국 시간) · 연구소 결과 변경`처럼 보인다. 사양 변경 대상은 작성자가 없으므로 작성자 칸을 비운다.

- 준비 후 30분이 지난 목록은 체크박스 없이 `준비 목록 만료 (준비 2026-10-14 17:41 한국 시간) · 다시 준비하세요`로 보이고, 분석 버튼은 누를 수 없다. 서버는 30분이 지난 선택을 지금처럼 거절한다.
- 선택하지 않은 대상과 사용률 기준 때문에 실행하지 못한 대상은 미분석으로 남긴다. 사양·이슈별 저장 자료의 실제 비교 시작일과 종료일, 요청 기간 중 확인하지 못한 범위를 준비 화면·실행 기록·메일에 표시한다. 자료가 부족하면 전체 기간 완료로 표시하지 않는다.
- 절약 모드에서도 한도가 풀리면 대기 중인 분석을 자동으로 이어서 한다(REQ-QAINTEL-049). 형식 실패의 자동 AI 재시도는 하지 않는다. 메일은 기존 수신자·주기를 쓰며 미분석·대기를 완료와 구분한다.
- 화면 조회·검색·필터·설정·준비 목록은 Claude를 호출하지 않는다(호출 0회).

### REQ-QAINTEL-043 사용률 기준 호출 제어와 모델

**하는 일** 호출 횟수 대신 Claude 계정의 실제 사용률을 보고 새 호출을 할지 정한다. 사용률이 낮으면 필요한 분석을 끝까지 호출한다.

**언제** 절약 모드의 분석 호출 직전마다 확인한다.

**순서**

1. 직전 호출이 돌려준 사용률(이번 실행의 마지막 `rate_limit` 값)을 본다. 이번 실행에 호출이 아직 없으면 마지막으로 저장한 측정값(REQ-AICALL-006)을 쓴다.
2. 5시간 사용률이 `daily_qa.usage_guard.five_hour_percent`(기본 80) 이상이거나 주간 사용률이 `daily_qa.usage_guard.seven_day_percent`(기본 90) 이상이면 새 호출을 하지 않는다. 남은 대상은 대기로 둔다.
3. 멈추면 REQ-QAINTEL-049의 알림과 이어 하기가 이어진다.

**설정** 두 기준은 모두 50~100의 정수다. 범위 밖이거나 숫자가 아니면 기본값을 쓴다. 한 실행에서 다루는 작업 수는 `daily_qa.max_tasks_per_run`(기본 30)이 계속 정한다. 호출 횟수 상한(`daily_qa.savings.per_run`·`per_day`)은 읽지 않는다.

**안 될 때** 사용률을 읽지 못하거나, 저장값의 초기화 시각이 이미 지났으면(그 창은 새로 시작됐다) 그 값은 없는 것으로 본다. 사용률을 모르는 것만으로 호출을 막지 않고, 요약 메일에는 `사용률 미확인`이라고 쓴다.

> **예시** 5시간 사용률이 7%, 7%, 7%로 돌려받으면 대상 8건을 모두 호출한다. 40%, 79%, 80%로 돌려받으면 세 번째 호출 뒤에 멈추고 나머지 5건은 대기로 남는다.

- 캐시 재사용은 호출 0회다. 시작한 CLI의 실패·취소·사용량 불명은 호출 기록에 남기고, 시작하지 않은 것이 확인된 호출만 기록에서 뺀다. 호출 기록은 메일의 사용량(REQ-QAINTEL-048)이 읽는다.
- 호출당 두 턴의 단일 응답 방식은 그대로다.
- 일반 분석은 이 기능 전용 Sonnet 5.5·medium 설정을 사용한다. 댓글·이슈 점검 모델 배정은 유지한다. Opus 상세 재검토는 사용자가 선택한 대상만 실행한다.
- 이 정책은 챗봇·매뉴얼·TC 별도 요청의 모델 설정을 바꾸지 않는다. 사용량 조회에서는 인증 갱신용 AI 호출을 하지 않는다.

### REQ-QAINTEL-044 사용자 지침과 분석 품질 보존

**하는 일** 비용 최적화 뒤에도 사용자 지침 프롬프트와 QA 규칙 MD를 분석 기준으로 사용한다.

- 지침 프롬프트는 마스킹 후 전문을 전달한다. QA 규칙은 요구되는 절과 하위 절 원문을 보존하고, 필요하면 원문 전체를 추가 확인할 수 있어야 한다.
- 지침을 임의 요약해 대체하거나 필수 검토 항목·근거·Regression 축을 비용 때문에 삭제하지 않는다.
- 지침 파일 또는 필수 규칙을 확인할 수 없으면 분석 완료로 처리하지 않는다. 사용된 파일 해시를 실행 기록에 남긴다. 필수 검토 항목·Gate 판정·회귀 축 판단·선택 TC 비교가 빠진 결과는 보존하되 완료나 재사용 대상으로 처리하지 않는다. 관련 TC가 없으면 확인 범위와 보완 방법을 남긴다.
- 단일 구조화 응답 경로는 초기 기본값에서 끈다. 같은 자료의 필수 근거·충돌·예외 누락 검증을 통과한 경우에만 사용한다.
- 토큰 합계는 입력·캐시 생성·캐시 읽기·출력 합이다. 추론은 출력에 포함하므로 다시 더하지 않는다.

### REQ-QAINTEL-045 검증 버전과 두 분석의 역할

**하는 일** 사양 변경 분석과 이슈 분석을 선택한 검증 버전의 Checklist TC와 함께 검토한다. 절약 모드에서 적용하며 REQ-QAINTEL-012·013·014·015·016·031·032의 TC 제외·별도 요청 제한보다 이 요구사항을 우선한다. 절약 모드를 끈 설치는 기존 제한을 유지한다.

1. 자동 점검과 메일 설정에서 등록된 변경사항 Checklist의 실제 시트 이름을 선택한다. 파일과 시트를 함께 저장하며, `V1.1.0`이 하나일 때 처음 선택한다. 없거나 중복이면 선택 필요로 표시한다.
2. 사양 분석은 기간의 SRS 변경을 관련 이슈·선택한 TC와 비교한다. 검증이 빠졌으면 기존 TC 보완 또는 체크리스트 초안을 제안한다. 관련 이슈 존재만으로 검증됐다고 판단하지 않는다.
3. 이슈 분석은 기간의 신규·내용·원인·조치·연구소 결과·중요 댓글 변경을 검토한다. 연구소의 사양 주장과 문서 수정 주장을 원문과 대조하고 QA 대응·수정 확인 방법·TC 보완점을 제안한다.
4. 선택 시트가 없거나 읽지 못하면 다른 버전으로 대신하지 않는다. TC 확인 불가를 표시하고 전체 검토 완료로 처리하지 않는다.
5. 초안은 원문 사양을 근거로 작성하고 Step과 Expected 번호를 맞춘다. 사양이 불명확하면 확인할 질문을 남긴다. 원본 Excel과 이슈 상태는 바꾸지 않는다.

### REQ-QAINTEL-046 대상별 결과 연결과 결과 탐색

> **예외** 대시보드와 결과 페이지의 목록은 REQ-QAINTEL-033의 판정별 카드 정렬·접기보다 이 요구사항의 정렬을 우선한다. 설정에 따라 달라지지 않는다.

**하는 일** 기간을 넓혀도 유효한 기존 분석을 AI 호출 없이 표시하고 이슈·사양 결과를 검색한다.

- 제품·분석 종류·원문·검색 가능한 근거·지침·선택한 TC 버전이 같으면 대상별 기존 결과를 연결한다. 기간·묶음·실행 번호만 달라진 경우는 새 분석 이유가 아니다. 다른 변경 전후 비교와 과거 자료 기준은 구분한다.
- 실패·부분 결과·미확인 자료·미해결 질문은 검증 완료 결과로 재사용하지 않는다. 비교 기록이 없는 과거 결과는 이력으로 표시하며 최신 여부 미확인으로 구분한다.
- 분석결과 목록을 전체·이슈 분석·사양 분석으로 나눈다. 제품·기간·작성자·이슈/사양 번호·내용 검색·판정·처리 상태로 필터하고 50개씩 나눈다. 조건은 결과 수와 페이지를 계산하기 전에 적용한다.
- 조건은 두 묶음이고 적용 순서가 다르다.
  1. 어느 분석을 볼지 고르는 조건(분석 기간, 검색어, 분석 종류와 `이전 형식`, 작성자, 번호, 실행 번호)을 먼저 적용한다. 그 안에서 이슈마다 가장 최근 분석 한 건을 고른다.
  2. 이슈의 지금 상태를 말하는 조건(AI 판정과 `검토 필요` 칩, 처리 상태와 `미처리` 칩, `분석 이후 변경` 칩)을 고른 한 건에 적용한다. 새 분석에 덮인 옛 결과가 이 조건으로 되살아나지 않는다.

> **예시** 이슈 VP-1에 지난주 분석(`검토 필요`)과 어제 분석(`문제 없음`)이 있다. 기간을 지난주로 좁히면 지난주 분석이 보인다. `검토 필요` 칩을 누르면 VP-1은 목록에서 빠진다. 가장 최근 분석이 `문제 없음`이기 때문이다.

- `이전 분석 N건`의 N은 그 이슈(번호가 정확히 같은 것)의 분석 전체에서 지금 카드를 뺀 수다. 링크는 번호가 정확히 같은 결과만 조건 없이 모두 연다. `VP-728` 링크에 `VP-7287` 결과는 섞이지 않는다. 검색창과 번호 입력은 번호의 일부만 맞아도 찾는다.
- 목록은 이슈 하나에 카드 한 장이다. 같은 이슈의 분석이 여러 건이면 가장 최근 분석을 보이고 `이전 분석 N건` 링크가 같은 이슈의 모든 결과를 연다. `모든 결과 보기`로 바꾸면 분석 한 건이 카드 한 장이다. 실행 번호로 연 목록은 처음부터 모든 결과를 보인다.
- 카드 첫 줄은 이슈 작성자 이름(`qa-reporter`)과 이슈 업데이트 시각(`qa-updated`, 한국 시간과 `N시간 전`)을 굵게 보인다. 사양 분석 카드에는 작성자와 이슈 업데이트가 없다. 둘째 줄은 분석 종류 태그, 판정 색, 처리 상태를 한 줄로 보인다. 종류가 비어 있는 옛 결과는 `이전 형식` 태그를 달고 기본 목록에도 들어간다.
- 분석한 뒤 이슈가 바뀌었으면 `분석 이후 변경` 배지를 단다. 판정 기준은 분석 상세 화면(REQ-QAINTEL-020)과 같다. 분석 시각 뒤에 생긴 대기 이벤트가 있거나 이슈 업데이트 시각이 분석 시각보다 늦으면 바뀐 것이다. 비교할 자료가 없으면 배지를 달지 않는다.
- 카드에 `왜 분석했나` 한 줄(새 댓글·신규 이슈 등록·상태 변경)을 보인다. 저장된 변경 이벤트에서 읽으며 이벤트가 없으면 줄을 만들지 않는다. 요약은 두 줄까지만 보이고 QA 할 일은 3개까지다. 전체 글은 상세 화면에서 읽는다.
- 대시보드와 결과 페이지는 같은 조회 조건을 쓴다. 검색창 하나(이슈·사양 번호, 제목, 작성자 이름·ID, 요약, 분석 메모)와 빠른 칩(`검토 필요`·`미처리`·`분석 이후 변경`·`이슈`·`사양`·`이전 형식`), 정렬, `자세한 조건`(기간·작성자·판정·처리 상태)이다. 빠른 칩은 같은 칩을 다시 누르면 풀린다.
- `분석 이후 변경` 칩은 이슈 스냅샷을 읽어야 판정되므로 SQL 조건으로 쓰지 못한다. 나머지 조건을 DB에서 먼저 적용한 뒤 그 행을 파이썬에서 판정하고 50개씩 나눈다. 결과 수와 페이지 수도 판정을 거친 뒤의 값이다.
- `작성자별로 묶기`는 카드를 작성자 이름 아래에 묶는다. 순서는 예약 점검 메일(REQ-QAINTEL-048)의 확인할 이슈와 같다. 작성자는 이름순(ID가 없는 쪽이 맨 뒤)이고 같은 작성자 안에서는 이슈 업데이트가 최신인 이슈가 앞이다.
- 목록을 보는 일은 Claude 를 호출하지 않는다(REQ-QAINTEL-042).
- 이슈 최초 작성자 ID와 표시 이름을 원본에서 읽는다. 담당자·댓글 작성자와 구분한다. 이름이 없으면 이름 미확인과 ID를 보이고, 작성자 정보 갱신은 AI 재분석을 만들지 않는다.
- 원본 분석 시각·모델·결과 ID를 보존한다. 재사용을 새 분석으로 표시하지 않는다.
- 기본 정렬은 이슈의 최신 업데이트 순이다. 작성자별·이슈 번호별·분석 시각순 정렬을 선택할 수 있다. 이슈 업데이트 일시와 AI 분석 일시를 구분해 한국 시간으로 표시하며 업데이트 정보가 없는 항목은 미확인으로 표시한다.

### REQ-QAINTEL-047 분석 판정과 QA 처리 상태

> **예외** REQ-QAINTEL-019·020의 기존 승인·거절 양식은 추가하지 않는다. 이 요구사항의 QA 처리자 이름과 상태 기록을 별도로 제공한다.

**하는 일** AI가 무엇을 판단했는지와 사람이 업무를 마쳤는지를 구분한다.

- 분석 판정은 `사양과 다름`, `검토 필요`, `근거 부족`, `참고`, `문제 없음`이다. REQ-QAINTEL-033의 판정 연결을 유지하고 설명을 화면에 제공한다.
- 처리 상태는 `미처리`, `진행 중`, `확인 완료`, `보류`다. 사람이 변경하며 변경 시각·담당자·메모를 이력으로 남긴다. 참고하거나 조치할 것이 없는 결과도 확인 후 완료로 둘 수 있다.
- 완료는 해당 분석의 QA 처리 완료다. 이슈 종료·실제 장비 검증 PASS·사양 적합성을 대신하지 않는다. AI 판정과 과거 처리 이력은 바꾸지 않는다.
- 새로운 근거로 분석 결과가 생기면 새 결과는 미처리이며 과거 결과의 완료 상태를 자동 복사하지 않는다. 유효 결과 재사용은 원본의 처리 상태를 보여준다.
- 상세는 REQ-QAINTEL-020의 순서(이슈 본문 → AI 판단 → QA 할 일 → 댓글 → 근거 자료 → 분석 기록 → 처리 상태)로 위에서 아래로 읽는다. 미확인 자료는 QA 할 일 아래에 보이고 필수 검토 항목과 회귀 축은 보존한다.

### REQ-QAINTEL-048 두 분석의 예약 실행과 요약 메일

**하는 일** 예약 주기에 수집한 사양 변경과 이슈 변경을 한 번씩 검토하고 한 통으로 알린다.

- 수집·비교를 한 번 수행하고 사양 분석과 이슈 분석이 자료를 공유한다. 매일 전체 이슈를 새로 AI 분석하지 않는다. 유효 결과를 먼저 재사용하며 새 호출은 REQ-QAINTEL-043의 사용률 확인을 거친다.
- 일일 모드는 직전 정상 수집 이후의 변경, 주간 모드는 그동안의 변경을 대상으로 한다. 실제 비교 기간·버전·완료·재사용·미분석·실패를 구분한다. 사용률 기준 때문에 끝내지 못한 대상은 대기로 보존한다.
- 메일은 아래 표의 순서로 구성한다. 기존 수신자와 주기를 유지한다. 제목은 REQ-MAIL-001이 정한다.

> **예시** 제목: `[QA Agent] VXvue 10/15 점검 · 검토 필요 2건 · 대기 12건 · 일부 실패`

- 사용량이나 다음 실행 시각을 읽지 못해도 요약 메일은 나간다. 그 줄만 `사용량 기록 없음`으로 쓰거나 빠진다.
- AI를 돌리지 않고 대상 목록만 만든 실행의 메일은 제목에 `변경 목록 · AI 미분석`이 들어가고 본문 위쪽에 같은 안내가 보인다. 제목은 이때도 `[QA Agent] <제품>`으로 시작한다.
- 본문에 `audit.json`, `Gate G1` 같은 파일 이름·점검 코드와 `묶음`, `상한 초과로 미룸` 같은 내부 표현을 쓰지 않는다. 그런 내용은 점검 기록 화면에서 본다.
- 링크는 모두 설정 `daily_qa.review_base_url`로 만든 절대 주소다. 이 값이 비어 있으면 링크 대신 `서버 주소 미설정 · 설정 탭에서 입력`을 쓴다. 이유: 메일 프로그램은 `/qa-agent/…` 같은 상대 주소를 열 수 없다.
- HTML 본문은 표 기반 배치와 인라인 스타일만 쓴다(Outlook이 스타일 시트와 새 배치 방식을 무시하기 때문이다). 글 본문도 같은 순서로 쓴다.
- Claude 사용량 구획은 아래 "사용량 표시 규칙"을 따른다.
- 사내 원문과 상세 AI 판단 문장은 메일에 넣지 않는 REQ-DAILY-008의 원칙을 유지한다. 전체 결과는 제품·실행·종류 조건이 있는 웹 링크에서 확인한다.
- 변경 없음·기존 결과만 재사용·사용률 기준으로 멈춤을 구분한다. 미분석이 있으면 검토 완료로 보이지 않게 한다. 한도가 풀리면 대기분은 REQ-QAINTEL-049에 따라 자동으로 이어서 분석한다.
- 이슈 분석은 최초 작성자 ID별로 묶고 이름을 섹션 제목에 표시한다. 같은 이름의 서로 다른 사람은 ID로 구분한다. 각 작성자 안에서는 이슈 업데이트가 최신인 순서로 번호·업데이트 일시·판정·결과 링크를 보여준다. 이름이 없으면 이름 미확인과 ID를 표시한다.

**사용량 표시 규칙** 이번 실행의 호출 기록과 REQ-AICALL-006의 저장 값에서 읽는다(`reading_for_run`).

1. 5시간 사용량 줄: `실행 전 <a>% (<측정 시각> 측정) → 실행 후 <b>% (+<b-a>%p) · 초기화 <시각>`. 실행 전 값은 점검이 시작될 때 저장해 둔 가장 최근 측정값이고 측정 시각(한국 시간)을 함께 쓴다.
2. 실행 전 값이 없으면 `실행 전 값 미확인`이라고 쓰고 증가량은 쓰지 않는다. 값은 지어내지 않는다.
3. 증가량(`+<b-a>%p`)은 실행 전 값이 실행 시작 5시간 안에 측정됐고 같은 5시간 창일 때만 쓴다. 측정이 5시간보다 오래됐으면 측정 시각만 쓰고 증가량은 쓰지 않는다. 그 사이 창이 초기화됐으면 `(그 사이 초기화됨)`만 쓴다.
4. 주간 사용량 줄: `실행 후 <c>% · 초기화 <시각>`.
5. 이번 실행이 AI를 호출하지 않았으면 `이번 실행은 AI를 호출하지 않았습니다.`를 함께 쓴다. 호출 기록 자체를 읽지 못했으면 `사용량 기록 없음`이라고 쓴다.

### REQ-QAINTEL-049 한도 알림과 풀린 뒤 이어 하기

**하는 일** Claude 한도에 걸리거나 사용률 기준에 닿아 분석이 멈추면 관리자에게 메일 한 통을 보내고, 한도가 풀리면 대기 중인 분석을 자동으로 이어서 한다.

**언제** 분석 중 Claude 한도(세션·주간)에 걸렸을 때, 또는 호출 직전 확인(REQ-QAINTEL-043)에서 사용률 기준에 닿아 멈췄을 때.

**받는 사람** 설정 `notifications.admin_email`의 주소 1개다. 비어 있으면 `NOTIFY_EMAIL_TO`의 첫 주소를 쓴다. 둘 다 없으면 메일을 보내지 않고 점검은 그대로 이어진다.

**메일**

- 제목: `[QA Agent] <제품> Claude <한도 종류 또는 '사용률 <N>% 도달'> · 초기화 <KST 시각>`. 예: `[QA Agent] VXvue Claude 세션(5시간) 사용량 한도 · 초기화 2026-10-15 15:00`.
- 본문: 실행 번호, 남은 대기 건수, 증거 파일 이름(있을 때), 이번 실행의 사용량(실행 전·후 5시간·주간 사용률, 호출 수, 초기화 시각). 값을 읽지 못한 칸은 `사용률 미확인`으로 쓴다.
- 같은 한도 묶음(`limit_evidence.episode_key`가 같은 한도, 즉 종류와 초기화 시각이 같은 한도)에는 다시 보내지 않는다. 보낸 묶음은 `notifications` 표에 남겨 프로세스가 달라도 지켜진다.
- 사용률 기준으로 멈춘 경우의 묶음은 `USAGE:<창>:<초기화 시각>`이다. 같은 창이 초기화되기 전에는 한 번만 보낸다.
- 메일을 못 보내도 점검은 멈추지 않는다.

**이어 하기** 한도가 풀릴 초기화 시각 5분 뒤(`daily_qa.intelligence.catchup_delay_minutes`)에 이어 하도록 기록하고, 10분마다 도는 `qa_agent_limit_catchup`이 그 시각이 지난 제품의 점검을 다시 띄운다. 절약 모드에서도 동작한다. 자동 점검이 꺼졌거나(`off`), 주간 모드이거나, 예약 자체를 끈 서버에서는 이어 하지 않는다. 초기화 시각을 모르는 한도는 이어 하기 기록을 남기지 않는다.

> **주의** 이어 하기도 호출 직전 사용률 확인을 똑같이 거친다. 초기화 뒤에도 사용률이 기준 이상이면 다시 멈추고, 같은 묶음이라 메일은 다시 가지 않는다.
