이 문서는 `qa-verification-management-system`의 **ALM 변경 리포트** 기능이 어떻게 동작해야 하는가를 정의한다.

공통 사양(시스템 구성·전체 흐름·비기능·데이터·설정·오류·보안)은 상위 `SPEC.md`에 있고 여기서 되풀이하지 않는다.
절 번호는 상위 문서와 같은 뜻이다. 빠진 번호(3·4·6~10)는 공통 사양이라 상위 문서에 있다.

파일 경로는 모두 프로젝트 루트 기준으로 적는다(`specs/` 기준이 아니다). 검사기도 루트 기준으로 확인한다.

> **참고** 처음 읽는다면 1절 "이 기능은"과 흐름도, 5절 "요구사항 지도"를 먼저 본다. 수집·스냅샷·변경 이벤트는 [QA Intelligence Agent 기능 사양](qa-intelligence.md)의 카드를 그대로 쓴다. 이 문서는 그 기록을 사람이 읽는 리포트로 만드는 일과, AI 분석을 꺼도 수집을 계속하는 일을 정한다.

## 1. 목적

QA 담당자가 Polarion 을 직접 훑지 않아도, 정한 기간 동안 이슈와 SRS 가 언제 어떻게 바뀌었는지 날짜순으로 받아 본다. AI 분석을 꺼 둔 기간에도 기록이 빠지지 않는다.

성공 조건: 아무 기간을 골라도 그 사이 저장된 기록을 하루씩 비교한 변경 목록이 나오고, 매 업무일 아침 같은 목록이 메일로 온다.

### 이 기능은

- 서버가 매 업무일 04:00 에 이슈와 SRS 를 수집한다. AI 분석 설정(일일·주간·중지)과 상관없이 돈다. AI 는 부르지 않는다.
- QA 담당자는 `/qa-agent/changes` 화면에서 기간을 골라 이슈별·SRS별 변경을 날짜순으로 본다. 상태가 A에서 B로 갔다가 A로 돌아와도 보인다.
- 매 업무일 수집이 끝나면 직전 기록부터 오늘까지의 변경 리포트 메일이 자동으로 온다. 월요일 메일은 금요일부터 월요일까지를 담는다.
- 메일에는 번호·제목·바뀐 값·댓글 작성자와 시각만 넣는다. 댓글 본문과 이슈·SRS 본문은 화면에서 본다.
- 변경을 저장하는 때 AI 자동 분석이 꺼져 있었다면 그 변경은 다시 켜도 자동으로 분석하지 않는다. 꺼져 있던 동안의 변경은 사람이 [밀린 변경 분석]을 누를 때만 분석한다.

```flow
매 업무일 04:00 예약 -> Polarion 수집(SRS·이슈, AI 없음) -> 날짜별 스냅샷·변경 이벤트 -> 변경 리포트 메일
날짜별 스냅샷·변경 이벤트 -> 기간의 기록을 하루씩 비교 -> /qa-agent/changes 화면
날짜별 스냅샷·변경 이벤트 -(자동 분석 켜짐·분석일)-> AI 분석(specs/qa-intelligence.md) -> 요약 메일
날짜별 스냅샷·변경 이벤트 -(자동 분석 꺼짐)-> 밀린 변경 -> 사람이 [밀린 변경 분석] -> AI 분석
Polarion 수집 -(실패)-> 기준 유지 -> 수집 실패 알림 메일
```

### 이 기능에서 쓰는 말

| 용어 | 뜻 |
|---|---|
| 수집 실행 | AI 를 부르지 않고 SRS·이슈를 읽어 스냅샷과 변경 이벤트만 남기는 실행이다 |
| 기록 | 그날 저장한 SRS 스냅샷과 이슈 스냅샷이다(REQ-QAINTEL-003, REQ-QAINTEL-004). 날짜마다 하나다 |
| 변경 줄 | 대상 하나에서 어느 날 바뀐 것 하나다. 예: "10-19 상태 <이전> → <이후>" |
| 순 변화 | 기간의 첫 기록과 마지막 기록만 비교한 결과다. 중간에 바뀌었다가 돌아온 것은 보이지 않는다 |
| 확인 범위 | 리포트가 실제로 비교한 기록의 날짜와, 기록이 없어 하루 단위로 볼 수 없었던 날이다 |
| 밀린 변경 | 자동 분석이 꺼진 동안 자동 실행이 저장한, AI 분석이 필요한 새 이벤트다. 저장하는 순간의 설정으로 정한다 |
| 메일 기준 기록 | 자동 변경 리포트 메일이 끝으로 비교한 기록의 사본이다. 다음 자동 메일만 읽는다(REQ-ALMCHG-004) |

## 2. 범위

### 포함

- AI 분석 설정과 상관없이 매 업무일 도는 수집 실행
- 기간 안의 기록을 하루씩 비교한 이슈·SRS 변경 목록
- `/qa-agent/changes` 변경 리포트 화면
- 자동 변경 리포트 메일과 화면에서 보내는 수동 메일
- 저장 시점의 설정 기준 자동 분석과 [밀린 변경 분석] 버튼

### 제외

- Polarion 의 변경 이력(리비전)을 읽어 누가 언제 바꿨는지 찾는 일. 이 기능은 날짜별 기록을 비교하므로 하루 안의 여러 변경은 하나로 합쳐 보인다.
- 댓글 수정·삭제 감지. 새 댓글만 찾는다(REQ-QAINTEL-005).
- 변경 이벤트의 AI 분석 방법. [QA Intelligence Agent 기능 사양](qa-intelligence.md)을 따른다.
- LicenseManager 같은 다른 Polarion 프로젝트. 일일 점검에 등록된 제품만 다룬다(REQ-QAINTEL-002).
- Polarion 에 쓰기(REQ-DAILY-002).

## 5. 기능 요구사항

ID 규칙: `REQ-<CATEGORY>-NNN`. CATEGORY는 대문자·숫자, NNN은 세 자리다.
CATEGORY는 프로젝트 전체에서 이 문서만 쓴다. 한 번 부여한 ID는 재사용하거나 의미를 바꾸지 않는다.

| 카테고리 | 이름 | 설명 |
|---|---|---|
| ALMCHG | ALM 변경 리포트 | AI 와 나눈 매일 수집, 기간 변경 목록, 변경 리포트 화면·메일, 밀린 변경 분석 |

### 요구사항 지도

- 기록 쌓기: REQ-ALMCHG-001(매 업무일 수집 실행)
- 변경 목록 만들기: REQ-ALMCHG-002(기간 안 기록을 하루씩 비교)
- 받아 보기: REQ-ALMCHG-003(변경 리포트 화면), REQ-ALMCHG-004(변경 리포트 메일)
- AI 분석과 맞추기: REQ-ALMCHG-005(저장 시점의 설정 기준 분석과 [밀린 변경 분석])

### REQ-ALMCHG-001 매 업무일 수집 실행

#### 하는 일
AI 자동 분석 설정과 상관없이 매 업무일 아침 이슈와 SRS 를 수집해 날짜별 기록과 변경 이벤트를 남긴다. 그래서 AI 를 꺼 둔 기간에도 하루 단위 기록이 빠지지 않는다.

#### 언제
REQ-QAINTEL-001 의 예약 시각(기본 평일 04:00, 한국 시간)과 놓친 오늘 예약 만회(REQ-QAINTEL-035)다. 업무일의 뜻은 REQ-QAINTEL-038 과 같다.

#### 순서
1. 업무일마다 제품별로 점검 프로세스를 띄운다. 자동 분석 설정이 일일·주간·중지 어느 것이어도 띄운다.
2. 프로세스는 SRS 수집(REQ-QAINTEL-003), 이슈 수집(REQ-QAINTEL-004), 변경 이벤트 저장(REQ-QAINTEL-005, REQ-QAINTEL-006)까지 한다.
3. 오늘이 자동 분석 실행일인지 본다. 일일 모드는 모든 업무일, 주간 모드는 그 주 첫 업무일이 실행일이다(REQ-QAINTEL-038).
   - 실행일이면 같은 프로세스가 이어서 AI 분석을 한다.
   - 실행일이 아니거나 자동 분석이 꺼져 있으면 AI 를 부르지 않고 끝난다.
4. 수집이 끝나면 변경 리포트 메일을 보낸다(REQ-ALMCHG-004). AI 분석을 기다리지 않는다.
5. 실행 기록에 실행 종류를 남긴다. AI 를 부르지 않았으면 "수집만 실행"과 이유(자동 분석 꺼짐, 주간 모드의 분석일 아님)를 적는다.

#### 결과
날짜별 SRS·이슈 스냅샷, 변경 이벤트, 실행 기록이다. 수집만 한 실행의 결과는 수집 완료·변경사항 없음·기준 저장·수집 실패 가운데 하나다.

#### 설정
| 키 | 기본값 | 뜻 |
|---|---|---|
| `daily_qa.schedule.enabled` | `true` | `false` 면 수집 실행도 띄우지 않는다. 서버 전체의 자동 실행을 끄는 값이다(REQ-QAINTEL-001) |

#### 안 될 때
| 경우 | 처리 |
|---|---|
| Polarion 수집 실패·0건·급감 | REQ-QAINTEL-009 대로 기준 스냅샷을 옮기지 않는다. 변경 리포트 메일은 수집 실패 알림으로 보낸다(REQ-ALMCHG-004) |
| 이미 같은 제품의 실행이 돌고 있음 | REQ-DAILY-001 의 잠금대로 새로 띄우지 않고 로그를 남긴다 |

#### 지킬 것
- 수집만 한 실행은 Claude 를 한 번도 부르지 않는다. Claude 사용량도 쓰지 않는다.
- 주말과 공휴일에는 수집하지 않는다(REQ-QAINTEL-001). 그 사이 변경은 다음 업무일 기록에 합쳐진다.

### REQ-ALMCHG-002 기간 안 기록을 하루씩 비교

#### 하는 일
시작일과 종료일 사이에 저장된 기록을 날짜 순서대로 하루씩 비교해, 대상(이슈·SRS)마다 언제 무엇이 바뀌었는지 날짜순 목록을 만든다. 첫 기록과 마지막 기록만 비교하면 놓치는 중간 변경도 보인다.

> **예시** 상태가 10-17 에 A → B, 10-19 에 B → A 로 바뀌었다. 양 끝만 비교하면 변경이 없지만, 이 목록에는 두 줄이 모두 나온다.

#### 언제
변경 리포트 화면(REQ-ALMCHG-003), 변경 리포트 메일(REQ-ALMCHG-004), 기간을 정한 수동 실행의 변경 목록(REQ-QAINTEL-027)이 이 목록을 쓴다.

#### 입력
제품, 시작일, 종료일(`YYYY-MM-DD`, 한국 시간)이다.

#### 순서
1. 시작 기록은 시작일 또는 그 전 가장 가까운 기록이다. 마지막 기록은 종료일 또는 그 전 가장 가까운 기록이다. 그 사이에 저장된 기록을 날짜순으로 모두 모은다. SRS 와 이슈는 따로 모은다.
2. 이웃한 두 기록씩 비교한다. SRS 는 REQ-QAINTEL-003, 이슈는 REQ-QAINTEL-005 와 같은 기준으로 비교한다.
3. 변경 줄마다 날짜를 붙인다.
   - 필드 변경과 신규·빠짐은 뒤 기록의 수집 날짜다.
   - 새 댓글은 Polarion 이 준 댓글 작성 시각(한국 시간)이다.
4. 대상별로 변경 줄을 날짜순으로 놓는다. 대상끼리는 마지막 변경이 최근인 것부터 놓는다.
5. 기간 요약을 만든다. 변경 종류별 건수와, 대상마다 시작 기록 값에서 마지막 기록 값으로의 순 변화다.
6. 확인 범위를 만든다. 비교한 기록 날짜 목록, 기간 안 업무일 가운데 기록이 없는 날, 시작일 전 기록이 없었는지를 담는다.

#### 결과
변경 줄은 아래 값을 담는다.

| 칸 | 담는 것 |
|---|---|
| 날짜 | 위 3번의 날짜 |
| 대상 | 이슈·SRS 번호, 제목, Polarion 바로가기 주소 |
| 변경 종류 | 아래 표의 이름 |
| 이전 값 → 이후 값 | 상태, 담당자, 심각도, 연구소 결과, 발생·목표 버전 |
| 바뀐 곳 | 제목·설명·재현 절차·발생 원인·조치 내용은 바뀐 필드 이름. SRS 본문은 더해진 문장 수와 빠진 문장 수 |
| 댓글 | 작성자 이름(모르면 사용자 번호), 작성 시각, 본문 |

| 대상 | 변경 종류 |
|---|---|
| 이슈 | 신규 등록, 상태 변경, 담당자 변경, 댓글 추가, 내용 수정(제목·설명·재현 절차), 연구소 결과 변경, 발생 원인·조치 내용 변경, 기타 속성 변경(심각도·버전·연결 항목), 조회에서 빠짐 |
| SRS | 신규, 수정(제목·상태·본문·Legacy 번호), 조회에서 빠짐 |

#### 안 될 때
| 경우 | 사용자에게 보이는 것 |
|---|---|
| 날짜 모양이 틀림 | 400 "날짜는 YYYY-MM-DD 로 입력하세요." |
| 시작일이 종료일보다 늦음 | 400 "시작일이 종료일보다 늦습니다." |
| 기간이 366일을 넘음 | 400 "조회 기간은 366일까지입니다." |
| 종료일 이전 기록이 하나도 없음 | "이 기간에 저장된 기록이 없습니다." |
| 기록이 하나뿐임 | "비교할 기록이 하나뿐입니다(<날짜>). 다음 기록부터 변경이 보입니다." |
| 기간 안 업무일에 기록이 없음 | 확인 범위에 "<날짜> ~ <날짜> 기록 없음: 이 사이 변경은 <다음 기록 날짜>에 합쳐서 보입니다." |
| 시작일 전 기록이 없음 | 확인 범위에 "<첫 기록 날짜> 전의 변경은 확인할 기록이 없습니다." |

#### 지킬 것
- 저장된 기록만 읽는다. Polarion 을 새로 읽지 않고 AI 를 부르지 않는다. 같은 기간을 여러 번 만들어도 결과가 같다.
- "조회에서 빠짐"을 삭제로 단정하지 않는다. 삭제, 유형 변경, 권한 변경을 기록만으로 가릴 수 없다. 화면과 메일에 "Polarion 에서 확인"을 함께 적는다.
- 댓글 작성 정보를 아직 읽지 못한 댓글(댓글 읽기 상한·실패, REQ-QAINTEL-004)은 "작성 정보 미수집"으로 보인다. 다음 기록에서 읽히면 그 값을 쓴다.
- 작성자·담당자 이름은 이슈 조회가 함께 돌려준 사용자 이름을 쓰고, 없으면 사용자 번호를 쓴다.
- 이유: 기록이 하루 단위라서 하루 안의 여러 변경은 하나로 합쳐진다. 그래서 확인 범위를 늘 함께 보여 준다.

### REQ-ALMCHG-003 변경 리포트 화면

#### 하는 일
기간을 골라 그 기간의 이슈·SRS 변경을 날짜순으로 화면에서 본다. 메일에 없는 댓글 본문도 여기서 본다.

#### 언제
대시보드의 [변경 리포트] 링크, 변경 리포트 메일의 링크, 주소 `/qa-agent/changes?product=<이름>&since=YYYY-MM-DD&until=YYYY-MM-DD` 다.

#### 입력
제품, 시작일, 종료일이다. 날짜를 비우면 종료일은 마지막 기록 날짜, 시작일은 그 전 기록 날짜다. 처음 열면 가장 최근 하루치 변경이 보인다.

#### 순서
1. REQ-ALMCHG-002 로 기간의 변경 목록을 만든다.
2. 아래 구획으로 보여 준다.
3. 사람이 변경 종류를 고르거나 번호를 넣으면 목록을 거른다. 기간을 바꾸면 1번부터 다시 한다.

#### 결과
| 구획 | 담는 것 |
|---|---|
| 기간 선택 | 시작일·종료일 달력, [조회] |
| 요약 | 이슈·SRS 변경 종류별 건수, AI 분석 상태(켜짐·주간·꺼짐)와 밀린 변경 수 |
| 확인 범위 | 비교한 기록 날짜, 기록이 없는 날 알림(REQ-ALMCHG-002) |
| 이슈 탭 | 이슈마다 카드 하나. 번호·제목·Polarion 바로가기와 날짜순 변경 줄. 댓글 본문은 접어 두고 누르면 펼친다 |
| SRS 탭 | SRS 마다 카드 하나. 신규·수정·조회에서 빠짐, 바뀐 곳, 더해진·빠진 문장 |
| 거르기 | 변경 종류 선택, 번호 검색 |
| 메일 보내기 | [이 기간 리포트 메일 보내기] |

[이 기간 리포트 메일 보내기]를 누르면 수신자 수를 보여 주는 확인 창이 뜬다. 확인하면 REQ-ALMCHG-004 형식으로 이 기간의 메일 한 통을 보내고 결과(보냄·실패와 이유)를 화면에 표시한다.

#### 안 될 때
REQ-ALMCHG-002 의 "안 될 때"와 같은 문구를 화면에 표시한다. 메일 수신자가 없으면 버튼을 누를 수 없고 "메일 수신자가 설정되지 않았습니다."를 보인다.

#### 지킬 것
- 이 화면은 저장된 기록을 읽기만 한다. AI 를 부르지 않는다.
- 접속 권한은 대시보드와 같다. 메일 보내기도 [변경사항 점검하기](REQ-QAINTEL-021)처럼 일반 웹 접속에서 할 수 있다.

### REQ-ALMCHG-004 변경 리포트 메일

#### 하는 일
매 업무일 수집이 끝나면, 직전 기록부터 오늘 기록까지의 변경 리포트를 메일로 보낸다. AI 분석 설정과 상관없이 보낸다.

#### 언제
- 자동: 수집 실행(REQ-ALMCHG-001)이 끝난 직후다.
- 수동: 변경 리포트 화면의 [이 기간 리포트 메일 보내기]다(REQ-ALMCHG-003).

#### 입력
자동 메일의 기간은 직전 기록 날짜부터 오늘 기록 날짜까지다. 월요일이면 금요일부터, 연휴 다음 날이면 연휴 전 마지막 업무일부터다. 수동 메일은 화면에서 고른 기간이다.

자동 메일은 끝으로 비교한 기록을 한 벌 더 보관한다. 이것을 "메일 기준 기록"이라고 부른다. 같은 날 다시 수집해 그날 기록이 덮어써져도, 다음 자동 메일은 메일 기준 기록부터 비교한다.

> **예시** 10-16 04:00 수집으로 자동 메일이 나갔다. 10:00 에 사람이 [변경사항 점검하기]를 눌러 10-16 기록이 다시 저장됐다. 10-19 자동 메일은 10-16 04:00 기록 → 10-16 10:00 기록 → 10-19 기록 순서로 하루씩 비교한다. 04:00 부터 10:00 사이 변경은 10-16 날짜 줄로 실린다.

#### 순서
1. REQ-ALMCHG-002 로 기간의 변경 목록을 만든다. 자동 메일은 아래 조건이 모두 맞을 때 메일 기준 기록을 시작 기록 앞에 넣어 함께 비교한다.
   - 메일 기준 기록의 날짜가 기간의 시작 기록 날짜와 같다.
   - 두 기록의 내용(이슈·SRS 목록)이 다르다. 그날 기록이 메일 뒤에 다시 수집되어 바뀌었다는 뜻이다.
   - 조건이 맞지 않으면 메일 기준 기록을 쓰지 않는다.
2. 아래 구획대로 HTML 본문과 글 본문을 함께 만든다.
3. 이슈와 SRS 구획마다 대상을 `daily_qa.change_report.max_items` 개까지 싣는다. 넘으면 "나머지 <n>건은 화면에서 보기"와 화면 링크를 단다.
4. 실을 이슈를 작성자별로 묶는다.
   - 작성자는 이름순으로 놓는다. 작성자 이름을 모르는 이슈는 "작성자 미확인" 묶음으로 맨 뒤에 둔다.
   - 같은 작성자 안에서는 마지막 변경이 최근인 이슈부터 놓는다.

   이유: 이슈를 등록한 사람이 자기 이슈의 변경을 바로 찾을 수 있다. 절약 모드 요약 메일도 같은 순서로 묶는다.
5. 수신자에게 보낸다. 수신자는 요약 메일과 같은 순서로 정한다(`daily_qa.report_recipients`, 없으면 `DAILY_QA_EMAIL_TO`, `NOTIFY_EMAIL_TO`, `notifications.admin_email`).
6. 자동 메일이 기록을 비교했으면 오늘 기록을 메일 기준 기록으로 보관한다(`data/daily_qa/<제품>/change_mail_base/issues.json`, `srs.json`). 이슈와 SRS 를 따로 두고, 제품·종류마다 한 벌만 두어 매번 덮어쓴다.
   - 보관하는 경우: 메일을 보냄, 메일 발송 실패, 변경이 없어 보내지 않음, 첫 기록 저장.
   - 보관하지 않는 경우: 수집 실패, 오늘 이미 보낸 날, 발송을 끈 실행(`--no-email`), 자동 실행 꺼짐, 수동 메일.

이유: 수집 실패 메일은 기록을 비교하지 않았다. 이미 보낸 날 다시 보관하면 아침 메일이 비교한 기록을 잃는다.

#### 결과
제목은 `[QA Agent] <제품> 변경 리포트 · <시작>~<끝> · 이슈 <n>건 · SRS <n>건` 이다(REQ-MAIL-001 의 제목 규칙).

| 구획 | 담는 것 |
|---|---|
| 기간 | 시작·끝 시각, 비교한 기록 날짜 |
| AI 분석 | 자동 분석 상태(켜짐·주간·꺼짐), 밀린 변경 수와 [밀린 변경 분석] 안내 |
| 요약 | 이슈·SRS 변경 종류별 건수 |
| 이슈 변경 | 이슈 작성자(이슈를 처음 등록한 사람)별로 묶는다. 묶음 제목은 작성자 이름과 이슈 수다. 이슈마다 번호·제목, 날짜순 변경 줄, Polarion 바로가기 |
| SRS 변경 | 신규·수정·조회에서 빠짐. 번호·제목·바뀐 곳 |
| 확인 범위 | 기록이 없는 날 알림. 메일 기준 기록을 썼으면 "<날짜> 기록은 지난 자동 메일 뒤 다시 수집되어(<시각>) 지난 메일이 비교한 기록(<시각>)부터 이어서 비교했습니다." |
| 링크 | 같은 기간의 변경 리포트 화면 주소 |
| 맺음말 | "이 메일은 수집 결과를 자동으로 정리한 것입니다. AI 판단은 들어 있지 않습니다." |

메일에 넣는 것과 넣지 않는 것은 아래와 같다.

| 넣는 것 | 넣지 않는 것 |
|---|---|
| 번호, 제목, 변경 종류 | 댓글 본문 |
| 상태·담당자·심각도·연구소 결과·버전의 이전 값과 이후 값 | 이슈의 설명·재현 절차·발생 원인·조치 내용 문장 |
| 댓글 작성자 이름과 작성 시각 | SRS 본문 문장 |
| SRS 의 바뀐 곳과 더해진·빠진 문장 수 | AI 판단 문장 |

이유: 메일은 사내 시스템 밖으로 전달되기 쉽다(REQ-DAILY-008 과 같은 이유). 번호와 제목은 절약 모드 요약 메일(REQ-QAINTEL-048)도 이미 담는다.

> **예시** 월요일 자동 메일의 글 본문이다. 꺾쇠(`< >`) 안은 실제 값이 들어갈 자리다.
>
> ```text
> 제목: [QA Agent] VXvue 변경 리포트 · 10-16(금)~10-19(월) · 이슈 <n>건 · SRS <n>건
>
> 기간: 2026-10-16 04:00 ~ 2026-10-19 04:00 · 비교한 기록: 10-16, 10-19
> AI 분석: 꺼짐 · 밀린 변경 <n>건은 화면의 [밀린 변경 분석]으로 분석할 수 있습니다
>
> [요약]
> 이슈: 신규 <n> · 상태 변경 <n> · 담당자 변경 <n> · 댓글 추가 <n> · 내용 수정 <n>
> SRS: 신규 <n> · 수정 <n> · 조회에서 빠짐 <n>
>
> [이슈 변경]
> ■ <작성자 이름> (이슈 <n>건)
>   VP-<번호> <이슈 제목>
>     10-17(토) <시각>  댓글 추가 · <댓글 작성자>
>     10-19(월)        상태 <이전> → <이후>
>     10-19(월)        담당자 <이전> → <이후>
>
> [SRS 변경]
> 신규  VP-<번호> <SRS 제목>
> 수정  VP-<번호> <SRS 제목> · 바뀐 곳: 본문(더해진 문장 <n>, 빠진 문장 <n>)
>
> [확인 범위] 빠진 기록 없음
> 전체 보기: <서버 주소>/qa-agent/changes?product=VXvue&since=2026-10-16&until=2026-10-19
>
> 이 메일은 수집 결과를 자동으로 정리한 것입니다. AI 판단은 들어 있지 않습니다.
> ```

#### 설정
| 키 | 기본값 | 뜻 |
|---|---|---|
| `daily_qa.change_report.enabled` | `true` | 자동 변경 리포트 메일을 보낼지. 화면의 수동 메일은 이 값과 상관없다 |
| `daily_qa.change_report.send_when_empty` | `true` | 변경이 없는 날에도 "변경 없음" 메일을 보낼지. 수집이 돌았다는 것을 알리기 위한 값이다 |
| `daily_qa.change_report.max_items` | `50` | 이슈·SRS 구획마다 싣는 대상 수 상한 |

#### 안 될 때
| 경우 | 메일 |
|---|---|
| 수집 실패 | 제목에 `수집 실패`. 실패한 단계와 이유, "기준을 유지했고 다음 수집에서 다시 비교합니다." 변경 목록은 싣지 않는다 |
| 첫 기록 저장(기준 스냅샷) | "첫 기록을 저장했습니다. 다음 업무일부터 변경을 보냅니다." |
| 변경 없음 | `send_when_empty` 가 참이면 "변경 없음"과 확인 범위만 보낸다 |
| 메일 발송 실패 | 실행 기록에 실패와 이유를 남긴다. 실행 결과는 바꾸지 않는다. 화면에서 다시 보낼 수 있다 |

#### 지킬 것
- 자동 메일은 제품마다 업무일 하루 한 통이다. 놓친 예약 만회나 같은 날 다시 돈 실행이 같은 메일을 또 보내지 않는다.
- 메일 기준 기록은 자동 메일만 읽는다. 날짜별 스냅샷 폴더 밖에 두므로 AI 분석의 비교 기준(REQ-QAINTEL-003, REQ-QAINTEL-004, REQ-QAINTEL-027), 변경 리포트 화면, 수동 메일은 지금처럼 날짜별 기록만 쓴다.
- AI 분석 결과를 담는 요약 메일(REQ-DAILY-008)과 따로 보낸다.
- `daily_qa.schedule.enabled: false` 면 자동 메일도 보내지 않는다.
- 설정 탭의 시험 발송(REQ-MAIL-001)에 변경 리포트 견본을 더한다. 견본에는 "예시 자료" 표시를 단다.

### REQ-ALMCHG-005 저장 시점의 설정 기준 분석과 [밀린 변경 분석]

#### 하는 일
변경을 저장하는 때 자동 분석이 꺼져 있었다면 그 변경은 밀린 변경으로 남겨 두고, 다시 켜도 자동으로 분석하지 않는다. 켠 뒤에 저장한 변경은 자동으로 분석한다. 밀린 변경은 사람이 [밀린 변경 분석]을 누를 때만 분석한다.

이유: 꺼 둔 기간이 길면 켜자마자 Claude 사용량이 한꺼번에 몰린다.

#### 언제
- 자동: 자동 분석이 꺼진 상태에서 수집 실행(REQ-ALMCHG-001)이 AI 분석이 필요한 이벤트를 찾을 때, 그리고 다시 켠 뒤의 자동 분석이다.
- 수동: 대시보드의 [밀린 변경 분석]이다.

#### 순서
1. 자동 실행(예약·만회)이 변경을 저장할 때 자동 분석이 꺼져 있으면, AI 분석이 필요한 새 이벤트를 밀린 변경으로 저장한다. 사람이 누른 실행이 만든 이벤트는 밀린 변경이 아니다. 밀린 변경은 자동 분석 대기열과 재시도(REQ-QAINTEL-006)에 넣지 않는다.
2. 자동 분석(예약·놓친 예약 만회·한도 뒤 자동 재개)은 밀린 변경을 분석하지 않는다.
   - 꺼지기 전에 이미 대기 중이던 이벤트는 밀린 변경이 아니다. 켜면 지금처럼 자동으로 이어 간다.
   - 주간 모드에서 분석일이 아닌 날 찾은 이벤트도 밀린 변경이 아니다. 다음 주간 분석이 다룬다.
3. 밀린 변경이 있으면 대시보드에 "밀린 변경 <n>건 (<첫 날짜> ~ <마지막 날짜>)"과 [밀린 변경 분석]이 보인다.
4. [밀린 변경 분석]을 누르면 확인 창이 뜬다.
   - 건수, 기간, 분석 종류별 건수와 "Claude 사용량을 씁니다" 안내를 보인다.
   - 기간을 좁혀 일부만 고를 수 있다.
5. 확인하면 [변경사항 점검하기](REQ-QAINTEL-021)와 같은 실행 경로와 잠금으로 고른 이벤트를 분석한다. 실행 기록의 종류는 "밀린 변경 분석"이다.
6. 분석한 이벤트는 밀린 변경에서 빠진다. 한도(REQ-QAINTEL-025)나 [분석 중단](REQ-QAINTEL-036)으로 남은 이벤트는 다시 밀린 변경으로 돌아간다.
7. 끝나면 AI 요약 메일(REQ-DAILY-008)을 보낸다. 자동 분석이 꺼져 있으면 REQ-QAINTEL-038 의 7번처럼 메일을 생략하고 이유를 실행 기록에 남긴다.

#### 결과
분석 결과는 다른 분석과 같은 대시보드·상세 화면에 보인다. 밀린 변경 수가 줄어든다.

#### 안 될 때
| 경우 | 사용자에게 보이는 것 |
|---|---|
| 다른 실행이 돌고 있음 | REQ-QAINTEL-021 과 같은 "이미 실행 중" 응답 |
| 밀린 변경이 없음 | [밀린 변경 분석]을 보이지 않는다 |
| 고른 기간에 밀린 변경이 없음 | "고른 기간에 밀린 변경이 없습니다." |

#### 지킬 것
- 밀린 변경을 지우지 않는다. 사람이 분석하기 전까지 그대로 남는다.
- 밀린 변경인지는 변경을 저장하는 순간의 설정으로 정한다.

## 11. 테스트 사양

ID 규칙: `TEST-<CATEGORY>-NNN`. 모든 테스트는 가짜 Polarion·가짜 Claude 실행기를 쓴다.

### TEST-ALMCHG-001 AI 설정과 상관없는 수집

#### 검증 대상
REQ-ALMCHG-001

#### 선행 조건
가짜 Polarion 에 이슈와 SRS 가 있다. 자동 분석 설정을 일일·주간·중지로 바꿔 가며 쓴다.

#### 절차
1. 세 설정마다 업무일 예약 함수를 부른다.
2. 주간 모드는 첫 업무일과 그 밖의 업무일을 각각 부른다.
3. 공휴일과 `daily_qa.schedule.enabled: false` 에서도 부른다.

#### Expected Result
업무일에는 세 설정 모두 스냅샷과 변경 이벤트가 저장된다. 중지와 주간 모드의 분석일이 아닌 날은 Claude 호출이 0회이고 실행 기록에 "수집만 실행"과 이유가 남는다. 공휴일과 `enabled: false` 는 실행하지 않는다.

### TEST-ALMCHG-002 중간 기록을 거친 기간 비교

#### 검증 대상
REQ-ALMCHG-002

#### 선행 조건
네 날짜의 스냅샷이 있다. 한 이슈는 상태가 A → B → A 로 바뀌고, 한 이슈는 담당자가 바뀌고, 한 이슈에 댓글이 하나 생긴다. 업무일 하나는 기록이 없다.

#### 절차
첫 날짜부터 마지막 날짜까지 변경 목록을 만든다. 같은 기간으로 한 번 더 만든다.

#### Expected Result
상태 변경 두 줄이 날짜와 함께 나오고, 순 변화는 "변경 없음"이다. 담당자 변경 줄에 이전·이후 값이 있다. 댓글 줄의 날짜는 댓글 작성 시각이다. 확인 범위에 기록이 없는 날이 나온다. 두 번 만든 결과가 같다.

### TEST-ALMCHG-003 변경 리포트 화면

#### 검증 대상
REQ-ALMCHG-003

#### 선행 조건
TEST-ALMCHG-002 와 같은 스냅샷이다.

#### 절차
1. 날짜 없이 `/qa-agent/changes` 를 연다.
2. 기간을 넣어 연다. 변경 종류로 거르고 번호로 찾는다.
3. 잘못된 날짜와 366일 넘는 기간으로 연다.
4. [이 기간 리포트 메일 보내기]를 가짜 메일 발송기로 누른다.

#### Expected Result
날짜 없이 열면 가장 최근 두 기록 사이의 변경이 보인다. 거르기와 찾기가 목록을 줄인다. 잘못된 입력은 REQ-ALMCHG-002 의 문구로 400 이다. 메일이 한 통 나가고 결과가 화면에 보인다.

### TEST-ALMCHG-004 변경 리포트 메일

#### 검증 대상
REQ-ALMCHG-004

#### 선행 조건
가짜 메일 발송기를 쓴다. 금요일과 월요일 스냅샷이 있다.

#### 절차
1. 월요일 수집 실행을 돌리고 같은 날 한 번 더 돌린다.
2. 메일 글 본문과 HTML 본문을 읽는다.
3. 수집 실패, 첫 기록, 변경 없음, 대상이 상한보다 많은 경우를 각각 돌린다.

#### Expected Result
월요일 메일 한 통만 나가고 기간이 금요일부터 월요일이다. 본문에 번호·제목·이전·이후 값·댓글 작성자와 시각이 있다. 댓글 본문, 이슈 설명·재현 절차·원인·조치 문장, SRS 본문 문장이 없다. 실패·첫 기록·변경 없음·상한 초과는 "안 될 때" 표의 문구대로다.

### TEST-ALMCHG-005 밀린 변경

#### 검증 대상
REQ-ALMCHG-005

#### 선행 조건
자동 분석을 끈 상태에서 이틀 동안 AI 분석이 필요한 이벤트가 생긴다. 끄기 전에 대기 중이던 이벤트가 하나 있다.

#### 절차
1. 자동 분석을 켜고 예약 실행을 돌린다.
2. [밀린 변경 분석]을 하루치 기간으로 좁혀 누른다.
3. 가짜 Claude 가 한도 응답을 주게 하고 나머지 하루치를 누른다.

#### Expected Result
1번에서 끄기 전 대기 이벤트만 분석되고 밀린 변경은 분석되지 않는다. 2번에서 고른 하루치만 분석되고 밀린 변경 수가 줄어든다. 3번에서 남은 이벤트가 밀린 변경으로 돌아간다.

### TEST-ALMCHG-006 같은 날 다시 수집한 뒤의 자동 메일

#### 검증 대상
REQ-ALMCHG-004

#### 선행 조건
가짜 메일 발송기를 쓴다. 절약 모드다. 금요일 04:00 수집 실행으로 기준 기록과 자동 메일이 있다.

#### 절차
1. 금요일 04:00 수집 실행을 돌린다. 이어서 이슈 상태를 바꾸고 같은 날 [변경사항 점검하기](`prepare`)를 돌린다.
2. 월요일 수집 실행에서 담당자를 바꾸고 돌린다.
3. 같은 흐름에서 AI 분석의 비교 기준과 변경 리포트 화면 목록을 읽는다.
4. 금요일 재수집 없이 월요일을 돌린 경우와, 메일 기준 기록의 날짜가 시작 기록 날짜와 다른 경우를 각각 돌린다.

#### Expected Result
월요일 자동 메일에 금요일 날짜의 상태 변경 줄과 월요일 날짜의 담당자 변경 줄이 함께 있다. 확인 범위에 다시 수집한 안내가 있다. AI 분석의 비교 기준은 금요일 날짜 기록(재수집 내용)이고, 날짜별 스냅샷 폴더에는 메일 기준 기록이 없다. 재수집이 없거나 날짜가 다르면 메일 기준 기록을 쓰지 않고 안내도 없다.
