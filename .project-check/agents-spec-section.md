## 사양 기반 개발 (SPEC)

<!-- spec-workflow: v9 -->

`SPEC.md`가 이 프로젝트가 **어떻게 동작해야 하는가**의 기준이다. 코드의 현재 동작은 사양이
아니다. 아래는 상위 기준이고, 실제 절차(계획·테스트·검증)는 기존 Skill을 그대로 쓴다.

**사양 문서는 두 층일 수 있다** — `SPEC.md`에 인덱스 구역(`<!-- spec-index: v1 -->` … `<!-- spec-index: end -->`)이
있으면 `SPEC.md`는 공통 사양(목적·범위·구성·비기능·데이터·설정·오류·보안)과 인덱스를 담고, 큰 기능마다
`specs/<기능>.md`가 그 기능의 요구사항(`REQ-*`)·테스트 사양(`TEST-*`)·추적성을 담는다. 인덱스가 없으면
`SPEC.md` 한 파일이 사양의 전부이고, 그대로 두어도 된다.

- 새 기능 문서는 워크스페이스에서 `node tools/add-spec-feature.js <프로젝트> <기능-이름> "<표시 이름>"`으로
  만든다. 문서와 인덱스 행을 함께 만든다. 인덱스에 없는 `specs/` 문서는 준비 검사가 오류로 잡는다.
- 요구사항을 문서 사이로 옮기지 않는다. 기존 요구사항은 있던 자리에 두고 새 문서만 더한다.
  이유: 옮기다가 요구사항이나 추적성 행이 빠져도 알아챌 방법이 없다.
- 각 문서의 12절 추적성 표는 그 문서가 정의한 ID를 담는다. 같은 행을 두 문서에 적지 않는다.
- 기능 문서는 1·2·5·11·12절을 쓴다. 절 번호의 뜻은 `SPEC.md`와 같고, 빠진 번호는 공통이라 `SPEC.md`에 있다.
- ID는 문서가 달라도 프로젝트 전체에서 하나뿐이다. 기능 문서마다 CATEGORY를 다르게 둔다.
- backtick 파일 경로는 모든 문서에서 프로젝트 루트 기준이다. Markdown 링크만 그 문서 위치 기준이다.

**작업 시작 전** — 기능 추가·변경·버그 수정이면 먼저 사양에서 ① 관련 Requirement,
② 그 Requirement의 구현, ③ 관련 테스트, ④ 변경 영향 범위를 확인한다. 어느 문서를 볼지는
`SPEC.md`의 인덱스로 찾는다. 해당 Requirement가 없는 신규 기능은 **구현 전에** 사양에 추가한다.
typo, 주석, 문서만 바꾸는 작업은 예외다.

**구현** — 사양에 없는 기능을 임의로 추가하지 않는다. 요구사항이 불충분하거나 모순되면
추측으로 확정하지 말고 SPEC의 "13. 미확정 사항"에 `(TBD)` 또는 `확인 필요`로 남기고
사용자에게 알린다.

**변경 요청 판별** — 요청을 받으면 먼저 현재 SPEC · 요청 · 기존 구현 · 변경 의도를 대조해
둘 중 무엇인지 정한다.

- **사양 변경**: `SPEC.md` 수정 → 테스트 수정·추가 → 구현 → 검증 → `CHANGELOG.md`
- **기존 사양 미충족(버그)**: SPEC 유지 → 재현 테스트 → 코드 수정 → regression 확인 → `CHANGELOG.md`

버그를 고치려고 올바른 기존 사양을 바꾸지 않는다.

**완료 전** — `Requirement → 구현 → 테스트 → 실제 실행 결과`를 모두 확인한다. 테스트 PASS는
실제 동작 검증을 대체하지 않는다. 실행 가능한 프로젝트는 대표 실행 경로를 실제로 돌리고
출력을 읽는다.

**완료 시** — 검증을 통과하면 관련 문서(`CHANGELOG.md`, `progress.md`, 필요하면 `README.md`와
`SPEC.md`)를 갱신하고 저장소를 커밋·푸시한다. 사용자 요청을 기다리지 않으며 하위 프로젝트
세션에도 동일하게 적용한다. 게이트·CI·라이브 세션 충돌 회피는 설치된 키트의 공통 `AGENTS.md`
push 규칙을 따른다.

**사람이 읽는 SPEC (`docs/SPEC.html`)** — 번호만 보고도 무슨 기능인지 알 수 있게 SPEC과 CHANGELOG를
다음처럼 쓴다. 페이지(기능 목록, 요구사항 카드의 상태·구현·테스트·참조됨·변경 이력, 목차·검색,
지금 읽는 절 표시)는 여기서 자동으로 만들어지므로 SPEC에 같은 내용을 다시 적지 않는다.

- 문서 앞에 읽는 순서를 안내한다. 목적·전체 흐름을 본 뒤 필요한 기능과 요구사항을 찾도록 연결한다.
- 각 기능의 첫머리에 누가·언제 쓰고 무엇을 넣어 무엇을 얻는지 적는다. 큰 기능은 사용 순서대로
  REQ-ID를 묶은 "요구사항 지도"를 둔다. HTML이 만드는 기능 목록을 다시 적지는 않는다.
- 요구사항 카드는 `하는 일 → 언제 → 입력 → 순서 → 결과 → 설정 → 안 될 때 → 지킬 것` 중 필요한 칸을
  쓴다. 첫 칸에서 사람이 얻는 결과를 설명한다. 구현·테스트·상태는 12절에만 둔다.
- 예약 실행이 있으면 4절에 시각·시간대·실행 위치·실행 조건·결과 저장 위치·알림 경로를 표로 적는다.
  예약이 없으면 이 표를 만들지 않는다. 최근 설치·실행·전송 확인 결과는 `progress.md`에 둔다.
- 표현만 정리할 때는 이전 문서를 보관하고 `node .project-check/spec-preservation.js <이전.md> <개정.md>`로
  ID 순서·중복, 카드별 코드 값·숫자·따옴표 문구·참조 ID, 기존 흐름도·12절 추적성을 확인한다.
  이 도구는 문장의 의미를 판정하지 않으므로 원문과 직접 대조한다. 두 층 사양은 문서마다 검사한다.
  사양을 의도적으로 바꾸는 작업은 이 검사와 구분한다. 기존 프로젝트 본문을 자동으로 다시 쓰지 않는다.

- **`SPEC.md` 1절에 `### 한눈에 보기` 흐름도를 반드시 둔다.** 처음 보는 사람이 이 그림 하나로 무슨 프로젝트이고
  어떤 흐름으로 돌아가는지 알아야 한다. 무엇이 시작하는지(사람의 요청·예약 실행·입력 파일), 자동화가 차례로 하는
  큰 일, 결과가 남는 곳, 실패하면 가는 곳을 담는다. 세부 단계는 4절에 쓰고, 여기서는 5~10개 상자로 전체만 보인다.
  기능 문서(`specs/`)가 있으면 각 기능이 어디에 끼는지 상자 이름으로 보인다. 없거나 그릴 수 없으면 준비 검사가
  `SPEC_OVERVIEW_MISSING`·`SPEC_OVERVIEW_INVALID`로 경고한다.
- REQ·NFR 제목 줄에 기능 이름을 쓴다: `### REQ-EXPORT-001 CSV 저장`. TEST 절차는 제외.
- 5절 첫 REQ 앞에 `| 카테고리 | 이름 |` 기능 그룹 표를 둔다. NFR 카테고리도 넣는다.
- 구현·테스트·상태는 12절 추적성 표에만 쓴다. 카드와 기능 목록이 거기서 읽는다.
- 12절 Test 열에는 테스트 파일 경로, `<도구> --self-test`, 11절에 정의한 TEST-ID만 쓴다. README 같은 일반 파일은 안 된다.
- 12절 Status는 `draft`·`implemented`·`verified`·`deprecated` 중 하나다. `verified`는 게이트(`botyard.json`의
  `verify` 명령)가 실행하는 자동 테스트가 있을 때만 쓴다. 수동 절차만 있으면 `implemented`로 둔다.
- CHANGELOG 항목 앞에 ID를 붙인다(`- REQ-EXPORT-001: …`). 머리의 형식 예시 블록 안에는 쓰지 않는다 —
  예시 블록은 이력으로 읽히지 않는다. 예전 항목에 ID를 추측으로 소급하지 않는다.
- 흐름도는 `flow` 코드 블록으로 쓴다(`수집 -> 해석 -> 저장`, `저장 -(실패)-> 알림`). 외부 스크립트
  (Mermaid 등)를 쓰지 않는다. 그림은 프로젝트 안 파일만 Markdown 이미지 문법으로 넣는다(예: `docs/images/` 아래 파일).
- `SPEC.md`, `specs/` 문서, `CHANGELOG.md`를 고쳤으면 `node .project-check/render-spec-html.js .`로 HTML을 다시
  만들어 같은 커밋에 넣는다. 기능 문서는 인덱스 순서대로 같은 페이지에 이어진다. HTML은 사본이므로 직접 고치지 않는다. 준비 검사가 낡은 HTML을
  실패로, 이름 없는 제목과 예시 블록 속 항목을 경고로 잡는다.

**SPEC 문장 쓰기** — SPEC은 이 프로젝트를 처음 보는 사람, 개발을 모르는 사람도 읽고 이해할 수
있게 쓴다. CHANGELOG 항목도 요구사항 카드에 그대로 보이므로 같은 기준으로 쓴다.

- 한 문단에는 한 가지 이야기만 쓴다. 세 문장, 300자를 넘으면 문단을 나눈다.
- 차례가 있는 동작은 번호 목록, 조건이 여럿이면 글머리표 목록, 항목마다 값이 다르면 표로 쓴다.
- 규칙과 이유를 한 문장에 섞지 않는다. 이유는 `이유:`로 시작하는 줄을 따로 둔다.
- 예외·주의·예시는 인용 블록으로 뺀다: `> **예외** 휴장일에 잘못 쌓인 기록만 지울 수 있다.`
  (`**주의**`, `**예시**`, `**참고**`도 같다). HTML에서 색이 있는 상자로 보인다.
- 추상적인 설명보다 예를 먼저 든다. "A계좌와 B계좌에 같은 종목이 있으면 따로 기록한다."
- 전문 용어는 쉬운 말로 바꾼다. 코드 이름(함수·열·시트·파일)은 뜻을 먼저 쓰고 괄호에 넣는다:
  "기록 번호(`record_seq`)". 꼭 필요한 용어와 코드 이름은 `| 용어 | 뜻 |` 표에 모은다.
  공통 용어는 1절 아래에, 기능에만 쓰는 용어는 해당 기능의 첫머리에 둔다.
  HTML에서는 본문의 그 용어에 마우스를 올리면 뜻이 보인다.
- 화면·시트·메뉴에 실제로 보이는 이름은 영어라도 그대로 쓴다. 그 밖의 영어 단어는 한국어로 쓴다.

| 이런 말 대신 | 이렇게 쓴다 |
|---|---|
| 단조 증가 | 계속 커지기만 한다(줄거나 겹치지 않는다) |
| append-only | 기존 줄은 고치거나 지우지 않고 새 줄만 더한다 |
| 멱등(idempotent) | 여러 번 실행해도 결과가 같다 |
| fallback, 폴백 | 안 될 때 대신 쓰는 방법 |
| 정합성, 무결성 | 서로 맞는지, 빠지거나 틀린 값이 없는지 |
| 원복, 롤백 | 원래대로 되돌린다 |
| 관측 | 수집한 값, 기록 |
| 트리거 | 실행 시점, 실행 조건 (Apps Script 화면의 `트리거` 메뉴처럼 실제 이름이면 그대로) |
| 스키마 | 열 구성, 데이터 형식 |
| dedupe key | 같은 기록인지 가리는 기준 |
| 영속, 불변 | 저장해 둔다, 바꾸지 않는다 |

AI가 쓴 티가 나는 말투를 피한다.

- 줄표(`—`)로 문장을 이어 붙이지 않는다. 두 문장으로 나눈다.
- "A가 아니라 B다", "~을 잃지 않는다" 같은 대구를 되풀이하지 않는다. 할 일을 바로 쓴다.
- "조용히", "실제로", "명시적으로", "보장한다", "단일 원본" 같은 말을 버릇처럼 붙이지 않는다.
- 굵은 글씨는 놓치면 안 되는 곳에만, 한 문단에 한 번까지 쓴다.

준비 검사가 위 표의 말과 300자가 넘는 문단을 `SPEC_PLAIN_LANGUAGE` 경고로 알린다. 경고가 없다고
쉬운 글이 된 것은 아니다. 다 쓰고 나면 처음 보는 사람의 눈으로 한 번 읽는다.

**SPEC / CODE 불일치** — 조용히 맞추지 말고 다음 형식으로 보고한다.

```text
SPEC / CODE MISMATCH

Requirement:
Specification:
Current Implementation:
Difference:
Action: SPEC 수정 / CODE 수정 / 사용자 확인 필요
```

코드의 현재 상태를 정당화하려고 SPEC을 고치지 않는다.

**ID 규칙** — `REQ-<CATEGORY>-NNN`, `NFR-<CATEGORY>-NNN`, `TEST-<CATEGORY>-NNN`.
CATEGORY는 대문자·숫자, NNN은 세 자리. 한 번 부여한 ID는 재사용하거나 의미를 바꾸지 않고,
삭제한 ID를 다른 기능에 돌려쓰지 않는다. 추적은 테스트 쪽에 남긴다(예: 테스트 위에
`Validates: REQ-QUERY-001`). 검색용 주석을 모든 함수에 강제로 달지 않는다.

**문서 경계** — 같은 내용을 두 곳에 두지 않는다.

| 파일 | 담는 것 |
|---|---|
| `SPEC.md` | 현재 시스템이 어떻게 동작해야 하는가 (두 층이면 공통 사양과 기능 문서 인덱스) |
| `specs/<기능>.md` | 그 기능의 요구사항·테스트 사양·추적성 (두 층일 때) |
| `CHANGELOG.md` | 무엇이 변경되었는가 |
| `progress.md` | 현재 작업이 어디까지 진행됐는가 |
| `knowledge/` | AI가 작업할 때 필요한 판단 규칙·맥락 |
| `README.md` | 사람이 설치하고 사용하는 방법 |
| `AGENTS.md` | AI가 따라야 하는 작업 규칙 |

SPEC 내용을 `knowledge/`에 복제하지 않는다. knowledge는 Requirement ID를 **참조**만 한다
(예: "REQ-EXPORT-001을 고칠 때 한글 파일명 encoding 회귀를 항상 확인한다").
