# 기존 보고서·기록 변경 전후 검사

## 1. 기준과 허용 변경을 먼저 확정

- 같은 제품·문서 유형·업무의 최근 유효 승인본을 내용 기준으로 선택한다. 사용자 지정 선례가 다른 제품이면 등록 유형·첨부·승인 절차만 참고한다. 선례별 역할을 기록한다. Word와 승인 스캔 PDF가 다르면 승인 PDF의 실제 페이지와 표를 대조하고 기준 Word를 별도 사본으로 정합화한다. 승인 서명을 복제하지 않는다.
- 현재 시험 증거에서 보고서 번호·날짜·OS/KB·실제 시험 환경·결과를 확인한다. 제품 표기 버전(예: V1.0.12)은 실제 설치 상세 빌드(예: 1.0.12.105)와 구분한다. 환경 값은 현재 증거, 항목명·단위·표기·행 순서는 기존 양식을 따른다. 이전 결과 또는 장비 값을 그대로 재사용하지 않는다.
- 사용자 요구 한 가지를 예시로 들더라도 전체 변경 대상이 보고서/TC 전수 대조라면 모든 위치를 검사한다. 문장 어순·대소문자·띄어쓰기·기호·기존 오탈자·체크리스트명·섹션·표 구조를 임의 개선하지 않는다. 승인된 예외(서명란 삭제, 표지, 개행, 허용된 구조 변경)는 별도 기록한다.
- 원본을 보존하고 사본을 편집한다. 기준 파일과 PLM 대상 ID/리비전·첨부 파일명을 확정한 뒤 검사한다. 파일명을 보고 제품·버전·승인 상태를 추정하지 않는다.

## 2. 편집 이전에 허용 변경 목록 작성

Skill 폴더에서 Python 3으로 다음 읽기 전용 명령을 실행한다. Windows에서는 `py -X utf8` 또는 기존 Python 실행파일을 사용한다.

```text
python scripts/qa_document_guard.py inspect "<기준.docx>"
python scripts/qa_document_guard.py compare "<기준.docx>" "<수정본.docx>" --allow "<허용변경.json>"
python scripts/qa_document_guard.py pdf "<PLM 생성.pdf>" --pages 4 --require "2:Report No: <실제번호>" --require "2:<실제 빌드>" --reference "<검증한 로컬 PDF>"
```

inspect의 위치와 값을 사용해 편집 전에 아래 JSON을 만든다. SHA256은 inspect 결과, 각 reason은 사용자가 요청한 수정 또는 실제 시험 근거다. 여러 위치에 동일 날짜·이름이 있으면 각 위치를 지정한다. 패턴 일괄 허용, 후보 diff를 그대로 허용 목록으로 바꾸기, 모르는 값을 임의 승인하지 않는다.

```json
{
  "baseline_sha256": "<inspect 결과>",
  "changes": [
    {"path": "word/document.xml/p[2]", "before": "이전 값", "after": "새 값", "reason": "현재 회차의 확인한 근거"}
  ]
}
```

추가·삭제는 해당 위치의 before/after에 null을 넣는다. 구조 노드 추가·삭제로 뒤쪽 위치가 이동하면 기준/대상 구조를 정렬하거나 모든 영향 위치를 명시적으로 검토한다. JSON의 실제 null 값은 inspect가 객체 표기로 나타내므로 삭제와 다르다.

## 3. 등록 전·후 통과 조건

1. compare의 종료값 0, `passed: true`, `unexpected`·`unused`·`review_required`가 빈 목록이어야 한다. 기준 SHA256과 실제 업로드할 후보 SHA256이 일치해야 한다. DOCX는 본문·중첩 표·머리글·바닥글·각주·댓글·이미지·삽입 개체 해시·관계까지 위치별로 확인한다. Word 변경 추적 또는 외부 참조 문서(altChunk/subDoc)는 직접 원문을 확인하고 기준을 정리한 뒤 다시 검사한다. 해시가 같은 삽입 개체의 의미는 자동 추출로 확인한 것이 아니므로 렌더링 검사는 필수다.
2. 비교 성공은 텍스트/구조 검증이다. 실제 Word/PDF 렌더링에서 모든 페이지의 표지, 서명란, 머리글·바닥글, 표 잘림·넘침·페이지 공백을 확인한다. 레이아웃·미디어 의미가 달라지면 사용자 승인 범위인지 확인한다. 검사 미통과 상태에서 기록을 변경하지 않는다.
3. ALM 기존 TC/LiveDoc 수정은 현재 ID, 전체 속성·Step·Expected·Test Data·관계·보존 대상 이력으로 동일 구조의 JSON을 구성한다. compare로 준비본을 확인하고 저장 후 다시 전체 조회한 JSON을 기준과 동일 허용 목록으로 비교한다. 접근 불가/누락/잘림은 검증 실패 범위로 표시하고 추가 쓰기를 중단한다. 조사/준비 요청에는 저장하지 않는다.
4. PLM 기존 문서는 ID·리비전·첨부·체크아웃 소유자·승인 상태를 먼저 기록한다. 권한이 있는 자기 체크아웃만 관리하고 기존 첨부를 필요한 범위에서 교체한다. 같은 객체로 돌아와 새 첨부·리비전·비어 있는 체크아웃 상태를 확인한다. 저장/교체 응답 불명확 시 재조회 전 같은 조작을 반복하지 않는다.
5. PDF 변환은 체크인 이후 새 산출물인지 현재 리비전·첨부 수정시각·PDF 생성 표시와 실제 문구로 판별한다. 기존 PDF 이름만으로 성공이라 하지 않는다. 새로 열어 제한 시간 동안 적절히 재조회하고, 생성 실패·지연은 별도로 보고한다. PDF 명령은 텍스트형 PDF의 물리 페이지와 지정 문구, 선택적으로 검증된 로컬 렌더 PDF의 전체 페이지 텍스트를 대조한다(pypdf 필요). PDF 자체의 생성 출처·레이아웃·스캔 이미지의 의미는 직접 검증해야 한다. 이미지 전용/텍스트 추출 실패는 자동 PASS로 처리하지 않는다.
6. 준비·본문 검사·레이아웃·업로드·체크인·변환·재조회 각 상태를 나눠 보고한다. 승인/서명은 사용자가 한다. 전체 비교를 못 했으면 확인 범위와 미확인 범위를 적고 전수 확인이라 하지 않는다.

## 4. 연결 장애와 재개

교육자료 서버 / 운영 Teamcenter·Polarion / Computer Use 연결을 별개로 확인한다. 기존 로그인 브라우저의 실제 탭·주소·객체 ID를 읽을 수 있어야 쓰기를 시작한다. Native pipe 오류는 QA 서버 장애로 간주하지 않는다. 도구의 지원된 연결/재선택으로 한 번 복구를 확인하고, 여전히 접근할 수 없으면 사용자가 연결을 복구할 때까지 쓰기를 중단한다. 권한·인증·보안 제한을 우회하지 않는다. 재개 시 이전 작업의 마지막 확인된 객체와 상태, 파일 해시를 읽고 아직 수행되지 않은 단계만 진행한다.

VXvue·Bellalun은 자사 업무 지침과 시험 증거에서 제품별 내용·버전을 확인한다. XIPL 공용 매뉴얼은 모듈 기능만 설명하며 제품별 지원·라이선스·UI 조건의 근거가 될 수 없다. 두 제품 조건을 각각 해당 제품 사양에서 확인한다.

## 5. QA 문서 변환 결과를 쓸 때

DOCX·PDF를 Markdown으로, XLSX·CSV를 JSON으로 변환한 자료는 검색용 파생본이다. 원문을 보존하고 표·병합·행/문단·결과 이력·버전·표기·누락 및 변환 경고를 직접 대조한다. 변환 전후의 의미가 다른 형식은 단순 텍스트 일치만으로 승인하지 않는다. 정기 보고서 갱신에는 기준 DOCX와 수정 DOCX, 기존 TC 갱신에는 동일 구조의 전체 JSON 조회본을 검사한다. 이미지 전용 PDF는 실제 페이지를 확인하며 텍스트 추출 성공에 포함하지 않는다. 전환·변환 자체가 제품 시험 성공이나 운영 기록 저장을 뜻하지 않는다.
