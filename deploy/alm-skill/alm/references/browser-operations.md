# 로그인된 브라우저에서 ALM 작업하기

이 절차는 사용자가 구체적인 ALM 작업을 요청했을 때 적용한다. 미래의 사용 의향이나 안내 페이지를 만드는 요청은 현재 ALM 데이터를 변경할 권한으로 읽지 않는다.

## 사용하는 연결

대량 Checklist Import·SRS 연결·문서 구성에는 [일괄 등록 절차](checklist-registration.md)를 함께 적용한다. UI는 현재 Computer Use 도구로 제어하고, 서비스 API는 기존에 구성되어 정상 인증된 연결을 사용한다. 브라우저 쿠키를 서비스 API 인증으로 추출하지 않는다. API가 없는 환경에서도 화면 조사와 지원되는 작업은 계속하고, 권한·지원 기능의 차이는 보고한다.

현재 실행 환경에서 제공하는 Computer Use 스킬과 도구 설명을 먼저 읽는다. 사용자가 Edge·Chrome 또는 특정 탭을 지정했다면 그 브라우저의 기존 로그인 세션을 사용한다. 도구가 제공하는 브라우저·탭 목록과 접근성 정보에서 대상을 선택한다. 일반적인 서버 자료 조회는 이 ALM 스킬의 읽기 도구와 제품 스킬을 사용한다.

새 자동화 전용 브라우저나 별도 프로필로 로그인 세션을 대체하지 않는다. 기존 브라우저의 쿠키·토큰·비밀번호를 추출하거나 프로필을 복사하지 않는다. 디버깅 포트·브라우저 보안·확장 권한을 임의로 바꾸지 않는다. 기존 사용자 탭·미저장 편집·다른 업무를 보존한다.

브라우저 탭 API가 없으면 컴퓨터 사용 도구가 제공하는 기존 창 제어 기능을 확인할 수 있다. 그러나 창 식별자·제목·실제 화면·접근성 정보가 서로 맞고 ALM 주소와 프로젝트를 확인할 수 있을 때만 진행한다. 창 목록에 Edge가 보이는 것만으로 페이지 제어가 가능하다고 판단하지 않는다. 대상과 다른 앱 화면이 나오거나 도구가 불가하면 입력하지 않고 연결 오류와 미수행 범위를 알린다.

## 요청을 작업 범위로 바꾸기

먼저 서버 가이드에서 해당 절차와 현재 자료 판을 읽는다. 필요한 경우 제품 스킬로 해당 제품의 사양·기존 TC·Expected를 확인한다. 브라우저에서 현재 서버·프로젝트·대상 ID·객체 유형·상태를 읽는다. Target Version·Plan Scope·시험 빌드·문서 Revision을 구분한다.

작업에 필요한 이름·버전·대상·수정값이 자료나 현재 화면에서 확인되면 다시 묻지 않는다. 기존 기록을 바꿀지 신규 생성할지, 대상 프로젝트나 버전처럼 결과를 바꾸는 정보가 남으면 변경 전에 확인한다. “정리해줘”라는 요청을 이슈 등록이나 전체 상태 변경으로 확대하지 않는다.

구체적으로 등록·수정해 달라는 요청이 이미 있으면 그 범위의 일반 저장마다 허락을 반복해서 묻지 않는다. 작업 전에는 대상과 변경할 내용을 짧게 알린다. 사용하는 컴퓨터 제어 도구가 별도 확인을 요구하는 행동은 그 정책을 따른다. 삭제·접근 권한 확대·새 인증 정보·법적 서명 등은 일반 속성 저장과 구분한다. 확인이 필요하면 적용되는 도구 정책과 행동을 정확하게 설명하고, 검토할 결과를 준비한 뒤 묻는다.

전자서명은 사용자가 직접 처리한다. 최종 승인도 사용자에게 넘긴다. 서명할 문서와 개정·검토 결과·다음 Action까지 준비하고 사용자에게 넘긴다. 개인 인증이나 실제 수행자의 확인을 AI가 대신했다고 기록하지 않는다.

## 지원할 수 있는 작업과 완료 기준

| 작업 | 먼저 확인할 것 | 저장 후 확인할 것 |
|---|---|---|
| TC 신규 생성 | 프로젝트·유형·제목·Old ID·사전조건·단계·Expected·분류 | 새 ALM ID·단계 수·필수 속성·기존 항목 중복 여부 |
| TC 속성 및 단계 수정 | 정확한 ID·원래 값·현재 문서 상태·요청 변경 범위 | 같은 ID의 변경값·보존한 단계·관련 링크 |
| SRS와 TC 연결 | 양쪽 ID와 제품·버전·기존 관계·바라보는 방향 | is verified by 또는 verifies 관계와 Coverage |
| Test Run 생성 | Title·템플릿·Plan Scope·대상 TC·파라미터·시험 환경 | 새 Run ID·포함 TC 목록·범위·초기 상태 |
| Issue 작성 또는 수정 | 재현조건·실제 현상·Expected 근거·발생 버전·담당자·TC | Issue ID·저장된 속성·본문·첨부·관계 |
| Excel Import | 신규 또는 Roundtrip·원본 사본·시트·시작 셀·열 매핑·대상 개수 | Preview와 처리 결과·같은 ID 또는 새 ID·내용·중복 |
| LiveDoc 구성과 이동 | 문서 유형·대상 Space·개정·이동할 Work Item | 문서 안의 대상 ID와 Heading·목차·저장 상태 |
| 결과 기록 | 사용자가 제공했거나 실제 실행에서 얻은 시험 증거·버전·대상 | 개별 실행 기록과 전체 Run 상태·증거·Issue 연결 |

입력 준비·Preview·임시 편집·저장·저장값 재조회는 서로 다른 단계다. 끝난 단계까지만 보고한다. 사용자가 Preview까지만 요청하면 실제 Import를 실행하지 않는다. 원본 Excel과 기존 ALM ID를 임의로 지우지 않는다.

연구소의 수정 완료, 문서의 기대결과, Coverage 링크, 저장 성공 팝업만으로 시험을 Passed로 기록하지 않는다. 실제 제품 시험을 요청받은 것이 아니라 ALM 기록 입력을 요청받았다면 사용자가 제공한 실행 증거의 범위로 입력하고 증거 출처를 남긴다. 수행하지 않은 TC·관찰하지 않은 결과를 만들지 않는다.

## 화면 조작과 재조회

현재 도구가 제공하는 접근성 요소·텍스트·속성으로 대상을 찾는다. 번호·좌표를 과거 화면에서 재사용하지 않는다. 상태가 바뀌면 새 화면을 읽고 다음 대상을 선택한다. 현재 모달·편집 문서·선택 행이 다른 객체를 가리고 있지 않은지 확인한다.

Save 후에는 ID로 같은 객체를 다시 열거나 읽기 가능한 다른 화면으로 조회하여 실제 저장값을 확인한다. 목록의 첫 행이나 잘린 Title을 동일 객체라고 가정하지 않는다. 여러 항목을 바꾸면 요청한 ID 전체와 실제 변경한 ID 전체를 대조한다.

Save·Import 뒤 연결이 끊기거나 응답이 불명확하면 먼저 생성·변경 여부를 조회한다. 생성 결과를 모르는데 다시 Save나 Import를 눌러 중복을 만들지 않는다. 확인하지 못하면 결과를 불명으로 남기고 추가 쓰기를 멈춘다. 대상을 다시 찾을 수 없는 상태에서 다른 행으로 대체하지 않는다.

## 결과 보고

서버·프로젝트·대상 ID, 요청한 변경, 확인된 저장값, 관련 링크나 증거 위치, 미수행·확인 불가 항목을 간결하게 보고한다. 가능하면 변경 전후를 비교한다. 인증정보와 불필요한 개인 정보·브라우저 기록을 캡처나 로그에 남기지 않는다.

예시 요청은 “로그인된 Edge ALM의 지정 프로젝트에서 이 TC 목록으로 Test Run 초안을 만들고 Plan Scope와 포함 ID를 확인해줘”이다. 실제 작업에서는 프로젝트·TC 목록·Run 이름·버전이 현재 화면이나 사용자 자료에서 확인되어야 한다. 구체적인 실데이터 등록 시험 전에는 이 절차가 있다는 사실과 브라우저 작업 성공을 구분한다.

## 작업별 예시와 보고

[업무 요청과 결과 예시](work-examples.md)는 입력·실행 단계·결과 보고 형식·미완료 기준을 제공한다. 구체적인 요청에는 예시를 설명하는 데서 끝내지 않고 현재 대상에서 허용된 동작을 진행한다. 설명·검토·준비 요청은 그 범위를 지킨다.

보고는 `대상 → 요청한 작업 → 수행한 조작 → 재조회한 값과 증거 → 미완료·이유 → 다음 담당자` 순서로 작성한다. 저장·관계·첨부·최종 상태를 각각 확인하고 화면에 보이는 객체 ID와 리비전/실행 번호를 남긴다. 예시의 완료 문구를 실제 실행 없이 복사하지 않는다.
