# Checklist 일괄 등록과 미서명 문서 완성

검색어: Excel Import, A~K, Old ID, Old SRS ID, verifies, module, Basic Function, SignatureTable, timeout, 재개.

사용자가 Checklist 등록·SRS 연결·문서 정리를 요청했을 때 적용한다. 제품 TC의 의미와 등록 대상은 제품 스킬에서 확인하고, 이 절차는 ALM에 옮기는 방법을 담당한다. 새로운 버전의 ID·개수·열·제외 목록·권한은 현재 자료에서 다시 확인한다.

## 1. 요청을 완료 범위로 정하기

- 조사·준비안만 요청: 원본과 화면 조사, 매핑·대상·파일 준비안을 제시한다. Import 파일 생성·Preview·저장은 요청 범위 안에서만 수행한다.
- 전체 등록 또는 이전과 같은 상태까지 등록 요청: 원본 대조 → 파일 준비·재읽기 → Preview → 신규 Import → 생성 ID 수집 → 문서 편입 → 실제 verifies 연결 → 문서 표시 정리 → 전체 재조회까지 진행한다. 이미 승인한 일반 저장마다 허락을 반복하지 않는다.
- 문서 결재표의 표시, 결재경로 속성 설정, 상태 전환, 전자서명은 별도 결과다. 기본 종료점은 미서명 Draft 문서이며 전자서명·최종 승인은 사용자가 직접 한다. 사용자가 더 좁은 범위를 정하면 그것을 따른다.

착수 시 프로젝트, 대상 버전·시트·범위, 신규 생성/기존 갱신, 문서·Space, 내용 범위, 중복 처리, 참조·보관 항목을 자료와 현재 화면으로 확인한다. 실제 결정을 바꾸는 모호성만 묶어 질문하고 독립 조사는 계속한다.

## 2. 원본과 등록 대상을 고정하기

서버 snapshot·원본 SHA-256·수집 시각·시트·헤더·원행 번호를 기록한다. 다운로드 폴더 등 사용자가 지정한 파일과 서버 파일이 다르면 양쪽 해시와 TC ID별 내용을 대조한다. 수정시각이나 같은 행 수만으로 같은 파일이라고 하지 않는다. 병합 셀·줄바꿈·빈 셀과 실제 누락도 구분한다.

대상 목록은 `원행 → Old ID → 신규 ALM ID`로 추적한다. 실행 TC, 삭제 예정, 검증 제외/미수행 보관 기록, 별도 문서 참조를 구분하고 사용자가 정한 포함 범위를 따른다. 중복을 허용했으면 내용 중복을 임의 제거하지 않는다. 한 번의 생성 결과가 중복되지 않도록 재개하는 책임은 그대로 남는다.

원본 해시가 작업 도중 바뀌면 기존 기준본과 이미 저장한 ID를 보존한다. 새 판의 추가·ID 공란/삭제·분류·내용 변화를 ID와 내용으로 대조한다. 불명확한 쓰기와 새 판에 의존하는 변경을 멈추고, 기존 대상 유지 또는 변경분 반영의 결정이 필요한 항목만 묻는다. 기존 기준본 유지 답변이면 차이는 별도 목록으로 두고 승인된 대상의 연결·문서 정리·검증을 계속한다. 원본에서 사라진 ID를 ALM에서 자동 삭제하지 않는다.

## 3. 열 매핑과 Excel Import

아래는 변경사항 Checklist에서 확인된 매핑 후보다. 해당 프로젝트의 실제 Import 필드·enum·필수 여부를 먼저 확인한다. 제품별 필드 ID가 다르면 현재 설정에 맞춘다.

| 원본 | ALM 매핑 후보 |
|---|---|
| A Category | STC Category (`stcCategory`), 현재 enum에 명시적으로 매핑 |
| B TC ID | Old ID (`oldId`), ALM ID와 구분 |
| C 버전 | 버전 (`productVersion`), 문서 Revision과 구분 |
| D SRS No | Old SRS ID (`oldSrsId`), 실제 관계는 5절에서 별도 생성 |
| E 변경사항 | 변경사항 (`changes`) |
| F 변경사항 상세 | 변경사항 상세 (`changesDetail`) |
| G Title | Title |
| H Precondition | 테스트 조건 (`preconditions`) |
| I Test Step | Test Steps의 Step Description |
| J Expected Result | Test Steps의 Expected Result |
| K Test Data | TC 필드 Test Data (`testData`) |

A~K만 요청했으면 과거 수행 결과·수행자·Issue·Comment 열을 새 실행 결과로 옮기지 않는다. 원래 빈 Test Data는 그대로 둔다. 구체적 TC ID·SRS 번호와 파일 경로를 다음 작업의 고정값으로 넣지 않는다.

번호가 있는 데이터 목록을 Step으로 자동 분해하지 않는다. Step–Expected의 원래 비연속 번호와 묶음을 보존한다. 무손실 분해가 어려우면 현재 템플릿이 허용하는지 확인해 원본 I/J 전체 블록을 같은 Test Steps 행에 보존하고 그 구조를 설명한다. 파일을 저장한 뒤 모든 대상 셀·행 대응을 다시 읽어 비교한다.

신규 생성은 현재 지원되는 일반 Excel Import를 사용한다. Roundtrip은 기존 ID 갱신과 구분한다. 첫 데이터 셀·헤더·시트·전체 대상 수·enum 매핑을 Preview에서 확인한다. Preview가 첫 일부만 표시하는 제한이 있으면 그 수를 밝히고 전체 저장 검증을 따로 한다. 처리 중 Committing 또는 timeout이 생겨도 생성 여부를 모른 채 Import를 다시 누르지 않는다.

생성 후 전체 페이지를 수집하고 ID가 연속이라는 이유로 누락 없이 생성됐다고 하지 않는다. 모든 Old ID의 생성 ID·유형·필드 대응과 신규 생성 수를 원본에 대조한다. 기존 갱신 요청이면 원래 ALM ID가 유지됐는지 확인한다.

## 4. 문서 만들기와 편입

문서 위치·유형·현재 상태와 참고 문서를 먼저 확인한다. 프로젝트에 Basic Function Test Case 같은 표준 문서가 있으면 실제 표지·결재표·개정 이력·TC 표시 설정을 읽어 참조한다. 버전명만 비슷한 변경사항 문서를 결재표의 기준으로 자동 선택하지 않는다.

새 문서명·제품 버전은 대상 버전으로 작성한다. 참고 문서의 고유 문서번호·수행 결과 링크·과거 서명·작성자·승인 날짜를 복사하지 않는다. 문서 Revision은 제품 버전과 별개다.

현재 지원되는 방식으로 생성된 대상만 문서에 편입하고 원본 순서로 정렬한다. 문서 표시가 `paragraph`이면 TC ID만 보일 수 있다. 표준의 `titleTestSteps` 같은 표시 방식을 비교해 Title·Step/Expected 표·Precondition·Test Data·연결 관계를 표시한다. 매핑하지 않은 수행 필드가 빈 쉼표나 선택 안내만 만든다면 표시 설정에서 정리하고 수행값을 꾸며 채우지 않는다.

문서 본문을 API로 바꿀 때는 먼저 본문·표시 설정을 백업한다. 변경 전후의 Work Item ID 집합·중복·순서를 비교하고, 기존 대상 이외의 TC가 섞이거나 빠지면 저장하지 않는다. Heading ID 형식은 현재 서버 문서화 또는 UI가 생성한 형식으로 확인한다. 임의의 Heading ID를 만들지 않는다. Heading이 없는 문서의 빈 목차 안내는 제거하거나, 승인된 Heading 구조를 구성한 후 실제 목차가 채워졌는지 확인한다.

### 결재표 표시와 실제 결재경로

표준 문서가 아래 구성을 사용하는 경우 공통 매크로 include와 표 호출을 함께 보존한다. 아래는 실제 참조 문서에서 다시 확인해서 적용하는 예이며 모든 프로젝트의 공통 설정은 아니다.

```text
{include-macros:vlib/_default.Macros}
#SignatureTable($document)
```

`ApprovedTimeString`, `RevisionHistory`도 같은 라이브러리에 의존할 수 있다. include 없이 호출만 복사하면 함수 이름이 본문에 그대로 출력될 수 있다. 저장 뒤 화면에서 Creator/Reviewer/Approver 표와 개정 이력이 렌더링되고 매크로 원문이 남지 않았는지 확인한다. 표의 작성자·작성일은 현재 문서에서 계산되어야 하고 검토·승인 서명은 임의 채우지 않는다.

결재표가 보이는 것과 `approvalType` 등 실제 결재경로 필드가 설정된 것은 별개다. 둘을 따로 조회한다. 403 또는 읽기 전용 필드는 권한을 확대하거나 다른 경로로 우회하지 않는다. 허용된 본문 구성·독립 검증은 계속한다. 조회로 공란을 확인했으면 미설정, 조회 자체가 막혔으면 현재 값 확인 불가로 보고하고 필요한 권한을 알린다. 쓰기 403만으로 기존 값이 없다고 단정하지 않는다. 미서명 표시를 승인 완료로 보고하지 않는다.

## 5. SRS 실제 관계를 일괄 연결하기

D열에서 실제 식별자를 추출하고 각 대상이 현재 프로젝트의 SRS 유형인지 조회한다. 쉼표·줄바꿈 등으로 여러 번호가 있으면 각각 검증하고 `(TC ID, 관계 역할, SRS ID)`의 중복을 제거한 기대 관계 집합을 만든다. N/A·Release Note·외부 이슈 번호는 존재하지 않는 SRS를 만들어 연결하지 않고 별도 분류한다. Old SRS ID 문자열 입력은 verifies 생성이 아니다.

수백 건을 TC 상세 화면에서 반복 연결하기 전에 현재 지원되는 일괄 경로를 확인한다.

1. 기존 정상 서비스 API 연결이 있으면 같은 서버·프로젝트·대상 ID·연결 계정의 허용 범위를 확인한다. 도구 정책이 허용하는 서비스 API로 처리하고, 브라우저 내부 fetch나 쿠키 추출로 대체하지 않는다. 기존 PC의 인증 설정 경로·토큰을 Skill에 넣지 않는다. 새 인증·권한 확대가 필요하면 현재 정책에 따른다.
2. API가 없으면 UI의 Bulk Edit/연결 메뉴가 실제로 관계 추가를 지원하는지 확인한다. 메뉴 존재만으로 지원을 단정하지 않는다. 같은 SRS별 TC 묶음 등 실제 지원되는 방법을 사용한다.
3. Excel의 Linked Work Items 열이 읽기 전용이거나 unlock 불가이면 그 열의 Roundtrip 편집을 반복하지 않는다. Export 경고는 현재 작업이 추출인지 Import 실패인지 구분해 설명한다.

지원 여부를 확인한 REST v1 연결에서는 다음 형태를 사용할 수 있다. 예시 ID는 합성 값이다. URL의 TC가 출발점이고 `workItem`의 SRS가 도착점이다.

```text
GET  /polarion/rest/v1/projects/{projectId}/workitems/{tcId}/linkedworkitems
POST /polarion/rest/v1/projects/{projectId}/workitems/{tcId}/linkedworkitems
```

```json
{"data":[{"type":"linkedworkitems","attributes":{"role":"verifies"},"relationships":{"workItem":{"data":{"type":"workitems","id":"Example/SRS-1"}}}}]}
```

먼저 새 TC 한 건의 Old ID·Old SRS ID·유형·기존 관계를 확인하고, 누락 관계만 추가하여 GET으로 실제 방향·역할·ID를 확인한다. 정상 확인 뒤 같은 절차를 전체 대상에 자동 적용한다. 한 TC가 여러 SRS를 검증하면 지원되는 배열 요청으로 누락 관계를 묶는다. 기존의 다른 관계는 보존한다.

처음에는 순차로 시험하고 서버 응답이 안정적이면 소수 동시 요청으로 진행한다. 진행 단위는 성공 응답 수가 아니라 저장 후 재조회한 TC 수·관계 수다. 대상별 기대·기존·추가·재조회 결과를 기록해 중단 후에도 기존 관계를 다시 읽고 빠진 것만 처리한다. 지속 오류·불명확한 저장·rate limit이면 해당 쓰기를 멈추고 독립 검증만 계속한다.

timeout은 실패 확정이 아니다. 동일 대상 GET으로 기대 관계를 확인한다. 이미 있으면 재전송하지 않는다. 조회 실패나 불명확한 상태이면 그 대상을 결과 불명으로 남긴다. 정확한 대상에 관계가 없음을 확인하고 원인이 해소되었을 때만 한 번 재시도하고 다시 조회한다. 429는 Retry-After가 있으면 그 조건을 따르고 요청량을 줄여 정상 조회가 회복됐는지 확인한 후 누락분만 재개한다. 반복 timeout의 원인이 확인되지 않으면 재시도를 계속하지 않는다. 401/403은 인증·권한을 바꾸어 우회하지 않으며, 404/405는 대상 존재와 해당 서버 버전의 endpoint 지원을 구분한다. 최신 문서에 있는 backlink 일괄 endpoint가 현재 서버에도 있다고 가정하지 않는다.

## 6. 전체 저장 검증과 사용자에게 넘길 결과

| 대조할 결과 | 근거 |
|---|---|
| TC 전체 생성/유지 | 모든 페이지의 실제 ALM ID·유형·Old ID와 원본 목록 양방향 비교 |
| 정의 보존 | A~K 전체 매핑 필드, I/J 내용·묶음·번호·누락, K 실제 공란/값 |
| 중복 | 생성 ID·Old ID 중복과 사용자가 허용한 원문 내용 중복을 구분 |
| 문서 소속·순서 | 각 TC의 실제 module 관계와 저장된 문서의 TC ID 목록·순서 |
| verifies 전체 | 기대 관계 집합과 저장 관계 집합의 차집합·예상 외 관계·역방향 여부 |
| 문서 표시 | 표지·결재표·개정 이력·TC 표·빈 안내·미서명 상태의 실제 화면 |
| 실제 결재경로 | 해당 문서의 현재 속성값·권한·미설정 필드, 전자서명과 구분 |

Export의 Module 공란은 문서 미소속의 확정 근거가 아니다. 현재 API의 module 관계와 문서 내부 ID를 조회한다. 목록 요청의 `fields[workitems]=@all`, 지원되는 `include=linkedWorkItems`와 전체 페이지를 사용하면 필드·관계를 일괄 대조할 수 있다. 기본 응답이 ID·Title만 반환하는 경우를 내용 누락으로 오인하지 않는다.

MCP가 IP·환자 식별자 등을 가린 텍스트는 원문 손실 증거가 아니다. 허용된 원본 API·Export와 대조하고 마스킹된 값을 추측 복원하거나 ALM에 덮어쓰지 않는다. 실제 원문에서도 특수문자 등이 사라졌으면 해당 TC·필드·문자 차이를 좁혀 보고한다. HTML 같은 다른 필드 형식을 지원 확인 없이 반복 쓰지 않는다.

최종 보고에는 문서 링크, 생성 ID 전체 또는 대응 파일, TC 수·관계 수, 내용/Step/Expected 누락, 중복·문서 소속·관계 대조 결과, 원본 변경 차이, 권한 제한과 미수행을 담는다. 준비안·파일 준비·Preview·실제 Import·문서 편입·관계 저장·표시 확인·결재경로·전자서명/승인을 각각 완료한 범위로 보고한다.
