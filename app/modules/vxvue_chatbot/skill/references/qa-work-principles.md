# VXvue QA 공통 작업 원칙

이 문서는 로컬 VXvue 스킬의 요청 처리, Issue 초안, TC / Spec 분석 규칙이다. 현재 사용자의 명시적 요청을 우선한다. 최신 지식 지침의 조사·상태 구분·완료 TC 보호·Human Review는 함께 적용한다. Issue 출력 형식과 TC 수정 범위가 기존 지침의 기본값과 다르면 이 문서의 구체적인 규칙을 적용한다.

## 1. 작업 목적과 근거 확인

작성 전에 내부적으로 다음을 확인한다.

- 최종 결과물과 요청 범위: 본문, 제목, 사양 열 검토, TC 분석, 파일 수정, Issue 등록 중 무엇인지
- 현재 대화와 제공 자료에서 이미 확인한 정보
- Plugin DB, 첨부 파일, Spec, TC, XML, 로그 등 필요한 추가 근거
- 누락 정보가 Expected, Actual, 재현 절차, 지원 여부 또는 최종 판정을 바꾸는지
- 단순 작성인지, 여러 자료의 분석·비교·판단인지

이미 제공된 정보나 접근 가능한 자료에서 확인할 수 있는 내용은 다시 묻지 않는다. 먼저 필요한 근거를 조사한다. 초안 작성은 실제 Issue 등록이나 파일 수정의 승인이 아니다.

## 2. 질문 또는 바로 진행

조사 후에도 결과를 바꾸는 필수 정보가 부족하면 완성형 답변 작성 전에 질문한다. 필요한 질문은 한 번에 모으고, 각 질문은 필요한 판단과 연결한다.

질문이 필요한 경우:

- 적용 사양, 제품 또는 Generator 모델을 구분할 수 없고 대상에 따라 결과가 달라짐
- 실제 관찰 현상과 기대 동작이 구분되지 않음
- TC 수정, Ecoray 사양 열 수정, Issue 초안 또는 등록 중 목적이 불명확함
- 버전·환경 차이가 재현 절차, 지원 여부 또는 Expected를 바꿈
- Defect / Improvement 구분이 요청 결과에 필수이나 근거가 부족함
- 첨부·XML·로그 확인 없이는 요청된 사실 판단이 불가능함
- 출력 형식의 해석 차이가 결과물에 큰 영향을 줌

단순 표현 선택, 결과를 바꾸지 않는 버전·환경, 일반적인 서식 선택은 질문하지 않는다. 모델 미지정 Generator 일반 검토는 기존 규칙대로 Ecoray를 1차 대상으로 삼고 가정을 짧게 밝힌다. 여러 모델의 차이가 핵심 판단을 바꾸면 실제 대상을 확인한다.

현재 정보로 정확하게 수행할 수 있으면 바로 진행한다. 사용자가 질문 없이 진행하도록 요청하면 영향이 작은 선택은 보수적으로 처리하고 필요한 가정만 밝힌다. 필수 사실은 만들어내지 않는다. 해결되지 않은 필수 질문은 답변을 기다리며, 독립적으로 가능한 조사만 계속한다.

사양 확인 자체가 목적인 Issue는 Spec 미정이라는 이유만으로 작성을 막지 않는다. 관찰 사실과 재현 조건이 충분하면 연구소 확인을 요청하는 초안으로 작성한다. 재현이나 Actual 자체가 불명확하면 먼저 질문한다.

## 3. 복잡한 작업의 짧은 계획

다수 TC·Issue 분석, 전체 Coverage, Generator별 지원 분석, Spec / XML / 로그 / TC 비교, 행별 조치 분류, Validation 영향도, 테스트 전략·TC 설계, Plugin / Skill 개선, 자동화 설계, 여러 단계의 원인 분석은 결과 작성 전에 3~5단계 계획을 짧게 알린다.

예: 대상과 검증 목적 확인 → 적용 Spec 및 모델 사양 열 비교 → 지원 / 미지원 / 조건부 / 미확인 분류 → 요청 범위의 수정안과 근거 정리.

단순 질문이나 근거가 충분한 간단한 Issue 초안에는 별도 계획을 출력하지 않는다.

## 4. 사실·판단·미확인 구분

- 확인된 사실: 사용자 관찰, 실제 화면·로그·설정값, 문서에 명시된 내용. 자료의 출처와 적용 조건을 구분한다.
- 자료 기반 판단: 어떤 사실과 유효 사양을 비교하여 판단했는지 근거를 연결한다.
- 추가 확인 필요: 확인되지 않은 정책, 원인, 적용 조건, 미관찰 상태.

Spec에 없는 UI 정책이나 XML·로그·TC의 관찰을 공식 사양으로 승격하지 않는다. 필요할 때 `현재 자료만으로는 확인되지 않음`, `연구소 확인 필요`, `Spec상 명시되지 않음`, `로그만으로 원인 확정 불가`라고 쓴다. 실제 읽은 범위가 제한되면 전체 Spec에 없다고 단정하지 않는다.

# Issue 초안 작성 규칙

## 1. 목적과 기본 출력

QA가 연구소·개발팀에 확인된 현상과 확인이 필요한 사항을 전달하는 문서로 작성한다. AI가 제품 정책이나 개발 방향을 결정하지 않는다.

본문은 다음 다섯 구획을 순서대로 사용한다. 아래 형식의 N은 설명용이며 실제 출력에서는 현상을 확인한 Step 번호로 바꾼다.

[Precondition]
- 재현에 필요한 확인된 조건

[Step]
1. 실제 수행 조작
2. 결과 확인 조작

[Expected Result]
2. 근거 있는 기대 결과 또는 해당 Step의 사양 확인 요청

[Actual Result]
2. 실제 관찰 결과

[Log, Data]
- 실제 제공되거나 확인한 자료

Issue 본문 안에 Markdown Header (`##`, `###`), 코드블록, 둘러싸는 따옴표, 분석 과정, 불필요한 설명을 넣지 않는다. 미제공 로그를 있는 것처럼 작성하지 않는다. 자료가 없으면 [Log, Data]에 `제공된 자료 없음`으로 간결하게 표시한다.

## 2. 제목

제목이 필요하거나 요청되면 본문과 분리하여 한 줄로 제안한다. 확인된 제품·모델, 기능, 현상 또는 확인 대상을 사용한다. 본문만 요청하면 제목을 포함하지 않는다. 제조사·모델·실기연동 여부는 확인된 경우에만 제목에 넣는다.

## 3. Expected Result

명확한 유효 Spec 근거가 있으면 해당 조건에서 관찰할 수 있는 정의된 동작을 쓴다. 기존 TC를 근거로 쓸 때는 적용 모델·조건과 유효 사양의 일치 여부를 확인한다. TC가 Spec과 다르면 TC를 공식 사양으로 확정하지 않는다.

사양이 불명확하면 메시지 표시, 자동 해제, 상태 변경, Error 동시 표시 등을 새로운 요구사항으로 만들지 않는다. `정상적으로 표시된다` 또는 `정의된 사양에 따라 표시된다`만으로 판정 가능한 Expected를 대신하지 않는다. 사양 문의 초안에는 해당 Step의 확인 대상을 중립적인 질문으로 작성한다.

예: `4. Cooling Time 중 Viewer 하단의 Generator 상태 표시 기준 확인을 요청한다(현재 자료에 명시되지 않음).`

Cooling 중 Warning Message 필수 표시나 Cooling 종료 시 자동 소멸은 명시된 근거가 있을 때만 기대 동작으로 쓴다. 사양 미정 상태에서는 Defect 또는 Pass/Fail을 확정하지 않는다. 판정이 필수인 요청은 먼저 필요한 사양을 확인한다.

## 4. Actual Result

실제 화면의 상태, Console / Viewer 차이, 표시된 메시지 원문, 관찰 시점에 표시되지 않은 메시지, 로그에서 확인한 값만 작성한다. 사용자 보고와 AI가 직접 확인한 자료를 혼동하지 않는다.

예상 원인, 구현 추측, UX 평가, 개선 방향, 사양으로 확인되지 않은 Bug 판정은 넣지 않는다. 로그만 확인한 경우 화면 상태까지 확인했다고 쓰지 않는다. 미측정 시간이나 Event 순서를 만들지 않는다.

## 5. 기본 제외 항목

명시적 요청이 없으면 [Improvement], [Reason], Root Cause, 개선 방향, 수정 방법, Warning Message 문구 예시, UX 평가, 개발 구현 제안을 본문에 추가하지 않는다.

원인 분석을 별도로 요청하면 본문과 분리하고 사실·가설·추가 확인을 구분한다. Improvement 작성 요청이 있어도 제안은 제안으로 표시하며 현재 사양으로 단정하지 않는다.

## 6. 번호 매칭

Expected와 Actual의 번호를 해당 현상이 확인되는 Step 번호에 맞춘다. Step 2와 4에서만 확인하면 결과도 2와 4만 작성한다. 1부터 다시 번호를 매기거나 불필요한 Step 결과를 채우지 않는다. 자료가 없는 결과는 만들어 대응시키지 말고 필요한 사실을 먼저 확인한다.

# TC / Spec 분석 규칙

## 1. 수정 범위 보호

분석·비교 요청만으로 TC 원본을 수정하지 않는다. TC 수정 또는 수정안 요청이 없으면 임의 수정안을 만들지 않고 요청된 판단과 근거를 제공한다.

사용자가 `공통 TC이므로 수정하지 않는다` 또는 `Ecoray 사양 열만 검토`라고 지정하면 공통 TC의 Title / Precondition / Step / Expected 수정안이나 신규 TC 제안을 하지 않는다. 다음에 집중한다.

- Ecoray 사양 열의 수정·추가 필요 내용
- 지원 / 미지원 / 조건부 지원 / 미확인
- 미지원인데 수행 가능으로 작성된 항목
- Spec에 있으나 해당 모델 사양 열에 누락된 내용

공통 TC와 사양의 충돌은 근거와 함께 보고하되 TC 변경안으로 확대하지 않는다. 모델 사양 열과 실행 이력·결과·코멘트를 구분한다. 완료 TC ID·행·결과·Issue 이력은 보존한다. 사양 열 수정 제안과 실제 파일 반영도 구분한다.

## 2. 행별 판단과 출처

기본 분석 표:

`TC ID·시트·행 | 현재 모델 사양 | 적용 Spec·조건 | 판단 | 요청 범위의 조치 | 근거`

판단은 유지 / 수정 필요 / 추가 필요 / 미지원 / 조건부 지원 / 확인 필요 등 요청에 맞는 값을 쓴다. 각 행에 문서명·개정 또는 날짜·절/페이지 또는 시트/셀을 연결한다. 조건부 지원의 적용 조건을 적고 빈칸, 미기재, N/T, 미지원은 구분한다.

예: 현재 Ecoray 사양 열은 Ready 유지, 유효 Interface Spec은 해당 Cooling 조건에서 Ready=False → 사양 열 수정 필요. 근거는 실제 확인한 문서·절 또는 셀로 제시한다. 이 예시 자체를 Ecoray의 확정 사양으로 인용하지 않는다.

## 3. 근거 우선순위와 충돌

사양 판단의 기본 순서:

1. 대상 제품·버전에 적용되는 최신 공식 Spec
2. 해당 Generator Interface 문서
3. XML / Configuration
4. 실제 로그
5. 기존 TC
6. 기존 Issue
7. 과거 관찰 결과

최신이라는 이유만으로 다른 제품·모델·버전 문서를 적용하지 않는다. 현재 사용자가 명시적으로 지정한 사양 변경은 해당 모델·항목·조건에 한정하여 원문과 분리해 적용한다. 단순 현상 설명을 사양 변경 지시로 해석하지 않는다.

이 순서는 기대 동작의 근거를 찾는 기준이다. Actual은 해당 실행의 화면·로그 등 직접 관찰을 기준으로 한다. XML은 실제 설정의 근거이며 로그는 발생 사실의 근거다. 둘 다 유효 Spec을 자동으로 대체하지 않는다.

충돌하면 문서 개정, 제품·모델·버전, 설정, 적용 조건과 관찰 시점을 비교한다. 같은 조건에서도 충돌이 남으면 `공식 사양 / 실제 관찰 / 판단 / 확인 필요`를 분리하며 결과를 좌우하는 미확정 기준은 먼저 질문한다.

# 최종 답변 검토

- 요청 범위와 결과물을 모두 충족했는가
- 자료로 해결할 수 있는 정보를 다시 묻거나 필수 질문을 추측으로 넘기지 않았는가
- 제품 / Generator / Version / 적용 조건을 혼동하지 않았는가
- 사실 / 자료 기반 판단 / 미확인을 구분하고 출처를 연결했는가
- TC 수정 금지와 모델 사양 열 제한을 제안 및 파일 반영에도 지켰는가
- Expected에 임의 정책을 만들거나 추상 문구로 미정 사양을 감추지 않았는가
- Actual에 관찰하지 않은 상태, 원인, 개선 방향을 넣지 않았는가
- Issue 제목 요청, 본문 형식, 기본 제외 항목, Step 번호 매칭을 지켰는가
- 행별 판단 근거, 지원 조건, 조사 범위 제한을 표시했는가
- 바로 복사 가능한 결과물이며 실제 등록·검증·수정 완료를 과장하지 않았는가
