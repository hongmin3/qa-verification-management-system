QA Agent 사용법

QA Agent 는 두 가지를 합니다. 매일 점검 대시보드(/qa-agent)는 매일 아침 Polarion 의 SRS·이슈 변경을 찾아 바뀐 것만 분석합니다. 단일 이슈 분석(/qa-agent/issue-analysis)은 사람이 이슈 하나를 골라 검증 범위를 깊게 봅니다. AI가 QA를 판정하지 않습니다. 결과는 참고 초안이고 확정은 QA가 합니다.

A. 매일 점검 대시보드 — 매일 아침 무엇이 바뀌었나

서버가 평일 07:30(한국 시간)에 제품마다 스스로 돕니다. 공휴일에는 돌지 않습니다. Polarion 의 SRS·이슈를 전부 읽어 어제 저장한 것과 비교하고, 바뀐 것만 분석합니다. 바뀐 것이 없으면 AI 를 부르지 않습니다(실행 결과 변경사항 없음). 처음 도는 날은 비교할 어제 자료가 없어 기준만 저장합니다(기준 스냅샷 생성).

상태만 바뀐 이슈, 심각도·버전 같은 속성만 바뀐 이슈는 기록만 남기고 분석하지 않습니다.

자동 분석은 TC·Checklist·매뉴얼을 보지 않습니다. 사람이 넣는 자료라 최신이 아닐 수 있기 때문입니다. TC 와 맞춰 보는 일은 버튼을 누를 때만 하고, 매뉴얼 점검은 담당자가 명령(--on-demand manual-check)으로만 돌립니다.

  • 최신 분석 결과 카드는 결론(사양과 다름 검토 필요 근거 부족 참고 문제 없음), 한두 문장 요약, QA 할 일 3줄까지만 보입니다. 문제 없음 은 접어 둡니다.
  • [상세보기] 맨 위에 결론·바뀐 사양·근거·할 일이 있고, 나머지 분석 기록은 자세히를 펼쳐 봅니다. 초안 TC 는 참고용입니다. 원본 Checklist·Polarion 에는 사람이 옮깁니다.
  • 지식 문서 업로드 현황은 담당자가 직접 올려야 하는 문서(TC·Checklist, 매뉴얼, ALM 을 쓰지 않는 제품의 사양서)의 최신본과 서버에 올라간 날짜입니다. ALM 에서 자동으로 가져오는 사양서, QA 규칙, 지침 프롬프트는 여기 보이지 않습니다.
  • 실행 상세에서 단계별 상태, 찾은 변경 목록, 결과 파일(초안 Excel·audit.json)을 봅니다.

B. 지금 실행 — 기간을 골라 바로 돌리기

  1. 대시보드 실행 칸의 분석 기간에서 시작일과 종료일을 고릅니다. 기본은 어제~오늘입니다.
  2. [지금 실행]을 누릅니다. 실행은 서버에서 따로 돌고, 끝나면 마지막 실행 칸이 바뀝니다.
  3. 시작일 날짜(또는 그 전 가장 가까운 날)에 저장한 자료와 비교합니다. 종료일이 지난 날이면 새로 읽지 않고 저장된 자료끼리 비교합니다.

이미 분석한 변경은 다시 분석하지 않으므로 같은 기간을 여러 번 돌려도 AI 사용량이 늘지 않습니다. 이미 도는 실행이 있으면 "QA Agent가 이미 실행 중입니다." 로 막힙니다. 종료일은 오늘보다 늦을 수 없고, 시작일은 종료일보다 늦을 수 없습니다.

B-2. 현재 상태 점검 — 이슈 기록이 없는 기간

이슈 스냅샷이 쌓이기 전의 기간은 이슈가 언제 어떻게 바뀌었는지 알 수 없습니다. 그런 기간은 [현재 상태 점검]으로 지금 이슈 전체를 그 기간의 SRS 변화와 맞춰 봅니다.

  1. 분석 기간을 고르고 [현재 상태 점검]을 누릅니다. 확인 창이 뜨면 확인합니다.
  2. 코드가 이슈를 나눕니다: 연결 SRS 가 바뀐 이슈(수정 완료 · Spec 판정 · 그 밖), SRS 는 그대로인 Spec 판정 이슈, 기간 안 신규 이슈. 나머지는 AI 에 보내지 않습니다.
  3. SRS 하나와 그 SRS 의 이슈를 묶어 가벼운 모델로 판정합니다(일치 · 부분 일치 · 충돌 · 근거 부족).
  4. 실행 상세 맨 위에 "현재 상태 기준 점검" 알림과 묶음별 건수가 보이고, 판정 카드에는 현재 상태 기준(기간 이력 없음) 표시가 붙습니다.

충돌·부분 일치로 나온 이슈는 단일 이슈 분석으로 깊게 확인하세요. 사용량 한도에 걸리면 남은 대상은 대기로 남고 다음 실행이 이어서 점검합니다. 같은 기간을 다시 눌러도 이미 본 이슈·사양 조합은 다시 분석하지 않습니다.

C. 기간 조회 — 지난 분석 모아 보기

기간 조회에서 시작일·종료일(과 변경 종류)을 고르면 그 기간에 찾은 변경과 분석 결과를 한 화면에 봅니다. 날짜는 한국 시간 기준입니다.

D. Claude 사용량 한도

Claude 세션(5시간) 한도나 주간 한도에 걸리면 대시보드 맨 위와 요약 메일 첫 줄에 언제 초기화되는지 보입니다. [지금 실행]을 눌렀을 때도 같은 안내가 나옵니다.

  • 한도 동안에도 변경 찾기는 계속합니다. 분석할 것은 "분석 대기"로 남습니다.
  • 세션 한도는 초기화 5분 뒤 서버가 한 번 다시 돌아 밀린 분석을 합니다. 주간 한도는 초기화 뒤 첫 평일 예약 실행이 이어서 합니다.
  • 로그인 토큰이 만료됐으면 서버 관리자가 토큰을 바꿀 때까지 분석하지 않습니다.

쓴 토큰은 비용 대시보드의 "QA Agent 점검" 줄에 자동으로 더해집니다.

단일 이슈 분석 사용법

Issue 하나를 넣으면 관련 사양 → 기존 TC → Regression 범위를 근거와 함께 정리합니다.

0. 이 기능이 대신하는 일

Issue 하나를 검증 범위로 옮기려면 원래 다음을 손으로 합니다.

  • Issue 본문에서 재현 조건·발생원인·조치내역을 읽고 정리한다
  • 연결된 SRS 번호를 사양서 5권에서 찾아 본문을 확인한다
  • TC Excel 수천 행에서 이 기능을 검증하는 TC를 찾는다
  • 그 TC가 수정 전 상태에서 Fail로 검출되는지 판단한다
  • 같은 Root Cause로 영향이 갈 다른 영역을 떠올린다
  • 어느 근거로 그렇게 판단했는지 다시 찾아 적는다

이 기능은 이 여섯 단계를 자동화하고, 마지막에 근거 링크가 붙은 검토 화면을 줍니다. 판정을 대신하지는 않습니다.

1. 먼저 준비돼야 하는 것

세 가지가 있어야 분석이 시작됩니다. 하나라도 없으면 G1 Gate가 막고 AI를 호출하지 않습니다.

  • 제품 사양서 — Knowledge에 등록된 사양서. VXvue는 ALM 크롤러 연동으로 매주 자동 갱신됩니다.
  • Test Case — Knowledge에 등록된 TC Excel. 다중 시트를 지원하고, 컬럼 자동 탐지에 실패하면 수동 매핑 화면이 뜹니다.
  • QA 규칙 문서 — 제품 지식 폴더의 [QA 작성 규칙] … 가이드_Rev*.md와 … 지침 프롬프트. Knowledge 화면의 지식 폴더 수집으로 가져옵니다.

규칙 문서가 없으면 분석하지 않습니다. 규칙 없이 낸 판정은 담당자마다 달라지고 근거를 되짚을 수 없기 때문입니다.

2. Issue 넣기 — 두 가지 방법

① Export 폴더에서 고르기. 이 PC에 ALM-QA-Automation 의 issue-export 앱 polarion_backup/ 폴더가 있으면 Issue ID 목록이 자동으로 채워집니다. 실행마다 생기는 하위 폴더까지 찾고, 같은 Issue 가 여러 번 수집됐으면 가장 최근 것을 씁니다. 목록에서 고르면 됩니다.

② JSON 첨부. 서버처럼 그 폴더가 없는 환경에서는 <ISSUE-ID>/backup.json 파일을 직접 첨부합니다.

Export 폴더가 없는 서버에서는 Issue ID만으로 이슈를 읽을 수 없어 번호 입력칸이 나오지 않습니다. 반드시 backup.json을 첨부하세요.

이슈 유형. 비워 두면 연구소 검토 결과로 유형을 정합니다. 결과가 “QA 확정 필요”였다면 양식의 이슈 유형에서 골라 다시 실행하세요. QA가 고른 유형은 결과 화면에 QA 선택으로 표시되고 G1의 “유형 확인” 대기가 풀립니다.

Issue 본문이 [Precondition] / [Step] / [Expected Result] / [Actual Result] 형식으로 작성돼 있으면 구획이 자동 분리됩니다. 형식을 안 지킨 Issue도 분석되지만, 어느 구획이 없는지 결과에 표시됩니다.

3. 검증 환경 입력 — 여기만 사람이 채웁니다

규칙이 “QA만 아는 사실”로 정해 둔 값입니다. 자동으로 알아낼 수 없고, 최종 판정에 영향을 주므로 먼저 묻습니다.

항목왜 묻는가비워 두면
실제 수행 가능 여부수행할 수 없는 절차를 Expected로 만들지 않기 위해G4가 “확인 필요”로 대기
Test Data 준비데이터 없이 Pass 판정을 만들지 않기 위해G4가 “확인 필요”로 대기
실제 X-ray Exposure 가능불가면 실제 촬영 결과를 Expected로 쓰지 않음해당 없음으로 처리
Dose Table 제공없으면 공식 촬영 가능 조합·출력 정확도를 확정하지 않음해당 없음으로 처리
확보한 관찰 수단무엇으로 결과를 볼 수 있는지없음으로 처리
반드시 필요한 관찰 수단필요한데 없으면 다른 수단으로 Pass 처리하지 않기 위해제약 없음

반드시 필요한 관찰 수단을 골랐는데 확보하지 못했으면 G4가 분석을 중단합니다. 예: API 응답을 봐야 판단되는 Issue인데 API 접근이 없으면, UI만 보고 Pass로 만들지 않습니다.

정보가 부족한 상태에서도 초안이 필요하면 “초안으로 작성”을 체크하세요. 미확정 항목이 “확인 필요”로 표시된 초안이 나오고, 화면 상단에 초안 모드가 붙습니다.

4. 조사 범위 제한

근거 검색은 늘 등록된 사양서·TC 전체를 봅니다. 범위 글을 적어도 검색 대상을 줄이지 않습니다. 적은 범위는 AI에 참고로 전하고, 결과 화면에 “제한된 범위 기준”으로 표시합니다.

범위 밖 항목을 “확정 불가”로 따로 표시하는 기능은 아직 없습니다. AI가 범위 글을 따라 답할 때만 그렇게 나옵니다.

사양이 여러 권으로 나뉘어 있어도 “사양 존재 여부” 판단에는 항상 전체를 하나의 집합으로 봅니다. 일부만 보고 “사양 없음”이라고 하지 않기 위한 규칙입니다.

6. 탭별로 무엇을 보는가

Issue 탭

Issue 구조화 결과와 AI의 의미 분석(Trigger / Root Cause / 수정 대상 / Before→After)입니다.

  • 유형은 Polarion 연구소 검토 결과에서 코드로 분류합니다. lab_fixed→Program Fixed 처럼 대응이 명확한 값은 AI 없이 정해집니다.
  • 대응이 갈리는 값(lab_noact 등)은 확정하지 않고 후보만 보여주고 QA가 고르게 합니다.
  • 발생원인·조치내역은 탐색 단서입니다. 이것만으로 “정상”이나 “사양대로”가 확정되지 않습니다.
  • 본문 이미지·첨부는 목록으로만 보여줍니다. 이미지는 AI가 판정하지 않습니다.

Specification 탭

검색한 사양 Chunk와 관련도 판정입니다. 상단에 정확 일치 몇 건 + 용어 유사도 몇 건이 나옵니다.

  • 정확 일치는 SRS 번호·DICOM Tag·Command 번호처럼 문자열이 그대로 맞은 것입니다. 가장 강한 근거입니다.
  • 용어 유사도는 뜻이 비슷한 문장을 찾은 것입니다. 참고 신호이고 확정 근거로는 약합니다.
  • 근거마다 문서명 · 페이지 · 절이 붙습니다. 원문에서 바로 찾아갈 수 있어야 하기 때문입니다.
  • 취소선·삭제 표시가 있는 근거는 “현재 적용 여부 확인 필요”로 표시됩니다.

TC Coverage 탭

기존 TC마다 판정과 근거가 나옵니다. 가장 중요한 값은 “Root Cause 검출 가능/불가”입니다.

QA Action 탭

판정 전체를 표로 보고 승인 / 거절 / 수정 후 승인 / 근거 추가 필요를 기록합니다. QA 결정은 AI 판정을 덮어쓰지 않고 따로 쌓입니다 — 나중에 AI 결과와 QA 결정을 비교해 규칙을 고치기 위한 자료입니다.

같은 판정에 결정을 다시 적으면 화면에는 최신 결정이 보이고, 이전 결정은 지워지지 않고 결정 기록 N건을 펼치면 보입니다. 기록한 뒤에는 폼이 있던 탭으로 돌아옵니다.

다음은 QA 승인이 필수입니다: TC 실제 변경, SRS Link 확정, Pass/Fail, Issue Close, 새로운 결함 확정, Release 승인.

7. AI에 실제로 무엇이 나갔는지 확인하기

결과 화면 아래 “AI 에 실제로 보낸 것 / 받은 것”을 펼치면 다음이 원문 그대로 나옵니다.

  • System Instruction (프롬프트 YAML 원문)
  • 주입한 규칙 발췌 — 제품 규칙 문서에서 이 판단에 필요한 절만 자른 것
  • 보낸 입력 JSON 전체와 그 글자 수
  • 받은 응답 JSON 전체

사양서·매뉴얼·TC 원본 파일은 서버 밖으로 나가지 않습니다. 나가는 것은 검색으로 추린 사양 Chunk 발췌, TC 후보의 일부 필드, 구조화된 Issue 필드, 그리고 규칙 발췌뿐입니다. 실제 payload를 여기서 직접 확인할 수 있습니다.

8. 토큰을 아끼는 방식

  • Gate가 먼저 막습니다. 근거가 없으면 AI 호출이 0회입니다.
  • 호출은 1회입니다. Issue 분석·사양 관련도·TC Coverage·Regression을 한 번에 받습니다. Skill마다 나눠 부르면 같은 근거를 네 번 보내게 됩니다.
  • 규칙을 잘라 보냅니다. 규칙 전문 약 30KB 중 그 판단에 해당하는 절만 2~5KB 넣습니다.
  • 후보를 줄입니다. 정확 일치로 근거가 확보되면 유사도 후보 수를 줄입니다.
  • 같은 입력은 캐시합니다. 재실행 시 호출이 발생하지 않습니다(화면에 “캐시 적중” 표시).
  • Issue Comment는 최근 3건만, 사양 Chunk는 1,200자까지, TC는 판정에 쓰는 필드만 보냅니다.

비용 대시보드에서 호출 수·토큰·캐시 적중을 집계해서 볼 수 있습니다.

9. 규칙 어디까지 구현됐는지 보기

규칙 구현현황에서 제품 규칙 문서의 절마다 어떤 방식으로 구현했는지와 Skill별로 규칙이 몇 KB 주입되는지를 볼 수 있습니다. 규칙 Rev가 올라가 새 절이 생기면 테스트가 실패하도록 해 두어, 새 규칙이 조용히 빠지지 않습니다.
