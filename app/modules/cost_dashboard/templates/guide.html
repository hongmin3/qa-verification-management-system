무엇을 보는 화면인가

사내 서비스로 계속 운영하려면 분석 1건의 비용이 예측 가능해야 합니다. 이 화면은 호출이 실제로 몇 번 발생했는지와 캐시가 얼마나 재사용됐는지를 기능별로 집계합니다.

토큰입력·출력 토큰 누적. 캐시 적중은 합산하지 않습니다 (실제 비용이 0이므로)분석당 입력 토큰이 계속 커지면 검색 후보 상한을 확인하세요

비용이 줄어드는 지점

이 시스템이 비용을 줄이는 방식은 “싼 모델을 쓰는 것”이 아니라 보낼 양을 줄이고, 안 보내도 되는 경우 아예 보내지 않는 것입니다.

#기법효과
1Gate가 먼저 막는다근거가 부족한 Issue는 API 호출이 0회. QA Agent 이력에서 “Gate 차단”으로 표시됩니다
2Rule Engine 사전 필터비기능 변경은 AI 대상에서 제외
3기준 사양서 Diff진짜 바뀐 줄만 분석
4Exact → BM25 후보 압축전체 사양서·전체 TC를 보내지 않음. 실측 전체 코퍼스의 1.37%만 전송
5정확 일치 시 후보 축소확실한 근거가 확보되면 유사도 후보 수를 줄임
6규칙 발췌 주입QA 규칙 전문 약 30KB → 해당 Skill 절만 2~5KB (85~94% 절감)
7Structured Output 단일 호출Issue 분석·사양 관련도·TC Coverage·Regression을 한 번에 받음
8quick / detail 2단계 + PASS short-circuit매뉴얼 개정 검증에서 문제없으면 비싼 호출 생략
9SHA-256 응답 캐시같은 입력은 API 호출 자체가 없음
10thinking_budget=0내부 추론 토큰 소비 차단
11모델 등급 라우팅기본은 Flash. 근거가 흩어져 있거나 Root Cause가 불명확할 때만 상위 등급
12일일 토큰 한도초과 시 새 분석 실행을 차단

일일 토큰 한도 설정

config.yaml의 analysis.daily_token_limit에 하루 총 토큰 상한을 넣습니다. 0이면 비활성입니다. 넘으면 새 분석 실행이 429로 차단되고, 실행 중인 분석에는 영향이 없습니다.

현재 설정 상태는 /config/status에서 확인할 수 있습니다 (API Key 값은 반환하지 않고 설정 여부·길이·출처만 보여줍니다).

모델 등급과 단가

등급은 입력에서 세어지는 신호로만 정합니다 — 난이도 판정에 또 LLM을 부르지 않습니다.

등급언제단가 (1M 토큰, 입력/출력)
Flash-Lite
gemini-3.1-flash-lite		요약·분류·정형 추출 (현재 QA Agent는 사용하지 않음)$0.10 / $0.40
Flash (기본)
gemini-3.5-flash		Issue 분석·사양 추적·TC Coverage·Regression$0.30 / $2.50 (잠정)
상위 등급
gemini-3.5-flash		Root Cause 불명확 · 근거가 3개 이상 문서에 흩어짐 · API/DICOM 연동 판단기본과 동일

단가는 config.yaml의 models.pricing에 있고 값이 바뀌면 그곳만 고칩니다. 각 분석 결과에 추정 비용이 표시되지만 실제 청구는 Google 콘솔이 기준입니다. 상위 등급 모델이 계정에서 제공되지 않으면 기본 모델로 물러나고, 물러났다는 사실이 결과에 남습니다.

Pro 계열은 쓰지 않습니다. 같은 Issue·같은 입력으로 비교한 결과, Pro는 thinking을 끌 수 없어 내부 추론 토큰이 출력의 2배 붙고(1만 토큰), 111초가 걸리면서도 근거가 하나도 없는데 TC 40건을 전부 “유지”로 단정했습니다. 느리고 비싸고 결과가 더 나빴습니다. 이 파이프라인의 AI 작업은 이미 압축된 근거에 대한 구조화 판정이라 내부 추론이 필요하지 않습니다. 직접 확인하려면 python scripts/compare_models.py --product VXvue --issue <ID>를 실행하세요 (실제 API를 호출합니다).

참고 규모

실측 기준(VXvue Issue 1건 = 입력 약 12.1K 토큰)으로 사용자 5명 × 하루 10건 × 월 20일 = 월 1,000건이면, Flash 기준 월 수 달러 수준입니다. 캐시 적중과 Gate 차단이 있으면 그보다 낮아집니다.

비용이 예상보다 많을 때 확인 순서

  1. 분석 상세 화면의 감사 영역을 펼쳐 입력 JSON 글자 수와 규칙 발췌 크기를 봅니다.
  2. 입력이 크면 retrieval.specification_top_k, qa_agent.tc_candidate_limit, qa_agent.rule_char_budget을 낮춥니다.
  3. 모델 등급이 계속 상위로 올라가면 결과 화면의 라우팅 이유를 봅니다. Root Cause 미명시가 잦다면 Issue 작성 품질 문제일 수 있습니다.
  4. 같은 분석을 반복 실행하고 있다면 캐시 적중이 올라가야 정상입니다. 안 올라가면 입력이 매번 미세하게 다른 것입니다.
  5. 호출 수가 분석 건수보다 많으면 재시도가 발생한 것입니다 — 응답 JSON이 잘려 실패했는지 로그를 확인하세요.
