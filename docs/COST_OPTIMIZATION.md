## 2026-10-13 일일 점검 사용량 조사

사용자는 모델을 Opus 5.5, 추론 정도를 `medium`으로 유지하고 구조부터 줄이기로 결정했다.
현재 일일 점검은 Claude CLI를 직접 부른다. 아래 공용 AI 통로의 응답 캐시와 Gemini 추론 설정은 이 CLI 작업에 적용되지 않는다.

실행 `20261013-125746-vxvue`는 사용자의 요청으로 중단했다. 수집 자료와 저장된 결과 1건을 보존했다.
아래 수치는 종료 로그가 남은 7회 호출의 합이다. 중단 당시 진행 중이던 호출의 사용량은 포함하지 못했다.

### 적용하는 수정

- 댓글 근거의 `ref`만 출력한 결과가 필수 `location` 누락으로 전체 재분석되던 버그를 고친다. 댓글 번호를 그대로 위치로 쓰고 입력에 있는 댓글인지 기존 검사를 거친다. 없는 번호를 만든 근거로 채택하지 않는다(REQ-QAINTEL-017, REQ-DAILY-007).
- CLI 호출 안내에 입력 후보 우선·근거 부족이나 충돌 때 추가 검색·읽은 공통 출력 형식 재사용을 적는다. 후보 수·본문과 규칙의 검토 항목은 유지한다(REQ-QAINTEL-011).
- 실행 중단 요청으로 Claude 하위 프로세스와 다음 작업을 멈추고, 수집·저장된 결과와 남은 대기 이벤트를 보존한다(REQ-QAINTEL-036).

재현 회귀시험에서 댓글 위치 보완은 전체 분석 1회로 저장됐다. 실제 운영에서 얼마나 줄었는지는 새 AI 호출을 하지 않아 아직 측정하지 않았다.

### 기존 분석 이력과 결과 캐시

운영 서버의 AI 결과는 1건이다. 규칙 점검 214건은 AI를 호출하지 않아 AI 결과 캐시 대상으로 계산하지 않는다.
담당자 PC의 AI 결과는 23건(예전 사양 변경·TC 비교 21, 수정 완료 1, 댓글 1)이다. 예전 분석 종류를 현재 자동 사양 변경 분석의 결과로 바꾸어 재사용하지 않는다.

일일 점검은 같은 변경을 중복 저장하지 않고 `remaining_analyses`의 완료한 분석을 건너뛴다.
Finding 중복 제외는 호출 뒤에 하므로 그것만으로 AI 사용량을 아끼지는 못한다. 공용 화면 분석의 `ai_cache`와 일일 CLI의 호출 경로도 다르다.

사용자가 이번 작업에 정확히 같은 입력의 성공 결과 캐시를 추가하기로 승인했다(REQ-QAINTEL-037).
기준에는 제품·분석 종류·본문/댓글·변경 전후·사양 후보/검색 색인·규칙/출력 형식·모델/추론 정도·사용자 답변을 포함한다.
실행·작업·이벤트 번호는 새 실행에 다시 연결하고, 형식·근거 검사는 다시 한다. 원본 실행 링크와 재사용 수를 신규 AI 호출 수와 구분한다.

실패·취소·한도·형식 오류·미해결 질문·근거 부족·접근 불가 작업 결과를 자동 재사용하지 않는다.
전체 실행을 나중에 중단해도 그 전에 성공해 저장한 작업은 조건이 맞으면 재사용한다.
기준 해시가 없는 예전 이력을 자동으로 캐시에 넣지 않는다. 묶음 구성이 바뀌면 첫 버전은 새 분석을 허용한다.

결과 캐시는 기본으로 켜져 있다(`daily_qa.result_cache.enabled: true`). 입력이나 규칙이 바뀌면 새로 분석한다.
캐시 조회·저장에 오류가 나면 정상 AI 경로를 이어가고 감사 기록에 남긴다. 재사용 결과는 현재 실행의 새 결과로 저장하며 사람의 승인 상태는 복사하지 않는다.
실행 상세에는 새 AI 작업 수와 재사용 묶음·결과 수를 나눠 보이고 원본 실행으로 연결한다.

이번 실패 출력 3개는 저장된 입력·SRS·이슈 스냅샷과 새 검증기로 다시 검사했다.
결과 14개는 통과했고 1개는 제외됐다. 필드 제외 기록도 남는다. 추가 AI 호출과 운영 결과 저장은 모두 0이며, 자동 캐시 대상과 별개로 보관한 검토 자료다.

### 다음 절감 순서

| 순서 | 방안 | 보존할 것과 확인할 것 |
|---|---|---|
| 1 | 강화한 입력 후보 우선·검색 재사용 안내의 효과를 측정한다 | 후보 수·본문·현재 근거 검사를 유지한다. 새 호출의 도구 사용 기록으로 왕복 감소를 비교한다 |
| 2 | 같은 이슈가 수정 완료·새 댓글 분석에 함께 들어갈 때 근거를 한 번 읽어 두 결과를 만든다 | 두 종류의 판정·결과·이벤트 완료 기록은 각각 남긴다. 작업·출력 형식의 사양 변경과 회귀시험이 필요하다 |
| 3 | 작업별 대화 횟수와 환산 비용에 상한을 둔다. 재시도도 같은 예산에 포함한다 | 한도는 근거 부족 판정으로 바꾸지 않고 남은 작업을 대기로 남긴다. 초과 뒤 즉시 전체 재시도하지 않는다 |
| 4 | 같은 배치에서 반복되는 근거 본문을 공용 자료로 한 번만 보낸다 | 대상별 검색 이유와 참조 위치를 유지한다. 고유 후보가 많은 배치에는 절감 효과가 작을 수 있다 |

CLI는 `--max-turns`와 `--max-budget-usd`를 지원한다. 금액 상한은 CLI 추정치이며 호출 도중 초과할 수 있다. 상한 값과 초과 뒤 처리는 사양으로 정한 다음 구현한다. [CLI 옵션](https://code.claude.com/docs/en/cli-reference)

작업 상한을 30개에서 더 낮춰 나눠 실행하는 것은 한 번의 사용량을 줄이는 방법이다. 같은 대상 전체를 결국 분석하면 총 사용량 절감으로 계산하지 않는다.

## 왜 이것이 핵심 설계 원칙인가

사양서·TC·매뉴얼 원문을 통째로 LLM에 넘기면 정확도는 높아 보여도 호출당 토큰이 급증하고,
분석 1건마다 비용이 선형으로 늘어나 사내 서비스로 지속 운영하기 어렵다. 이 프로젝트의 원칙은
하나다.

> **판단이 꼭 필요한 지점에서만, 최소한의 근거로 LLM을 부른다.**

파싱·검색·후보 압축·1차 필터링은 전부 결정적인 Python Rule Engine이 처리하고, AI는 판단이 필요한 단계에서 압축한 근거를 받는다. QA 점검은 변경이 필요한 작업 묶음만 분석하고, 매뉴얼 검증은 변경마다 quick 판정 뒤 필요할 때 detail 판정을 부른다.

부수 효과가 하나 더 있다. Rule Engine이 처리하는 구간은 **매번 같은 입력에 같은 출력**을
내므로, 결과가 흔들리는 범위 자체가 좁아진다.

## 파이프라인 — 단계마다 입력을 줄인다

괄호 안은 관련 코드와 설정이다.

**1. Rule Engine 사전 필터**
매뉴얼 검증에서 페이지 번호·저작권 표기·목차 리더 점선 같은 `NON_FUNCTIONAL_CHANGE`는 애초에
AI 분석 대상에서 제외한다.
`app/modules/manual_review/change_filter.py::is_functional_change`

**2. SRS 스냅샷 비교**
QA Agent 점검은 날짜별 SRS 스냅샷을 비교해 바뀐 항목과 필드만 분석 후보로 남긴다.
`app/modules/daily_qa/srs_snapshot.py`

**3. BM25/RAG Top-K 후보 압축**
매뉴얼의 사양서 근거는 BM25로 상위 `retrieval.specification_top_k`(기본 8)건을 고른다. QA 점검은 분석 종류별로 후보를 압축하고 기본 자동 분석에는 TC·매뉴얼 원문을 보내지 않는다. TC 점검과 초안은 사람이 요청할 때 수행한다.

**4. 정확한 식별자와 검색 후보 압축**
QA 점검은 식별자 정확 일치를 앞에 두고 남은 후보를 BM25로 고른다. Claude는 후보를 먼저 읽고 근거 부족이나 충돌이 있을 때 추가 검색한다.
`app/retrieval/hybrid.py`

**5. 구조화된 응답**
공용 AI 통로는 JSON Schema에 맞춘 응답을 받는다. TC·근거 ID를 코드로 검증한 뒤 사람이 확인한다.
`app/core/gemini_client.py`, `app/modules/daily_qa/schema.py`, `app/modules/daily_qa/evidence_validation.py`

**6. 매뉴얼 quick/detail 2단계 + PASS short-circuit**
매뉴얼 개정 변경은 먼저 짧은 quick 판정만 수행하고, 결과가 PASS면 비용이 큰 detail 호출을
생략한다. 문제가 의심될 때만 상세 근거·판정을 추가로 요청한다.
`app/prompts/manual_revision_{quick,detail}.yaml`

**7. SHA-256 응답 캐시**
공용 AI 호출은 `sha256(model + prompt명 + prompt버전 + prompt내용)`을 키로 캐시된다. 동일
입력으로 재분석·재검증하면 API 호출 없이 캐시 응답을 그대로 재사용한다.
`app/core/gemini_client.py`, `analysis.cache_enabled`

**8. Gemini의 `thinking_budget=0`**
Gemini의 구조화 호출은 근거 기반 구조화 추출·판정이라 별도의 내부 추론이 필요 없다.
`thinking_config.thinking_budget=0`으로 내부 reasoning 토큰 소비를 비활성화해 같은
`max_output_tokens` 예산을 응답 생성에 온전히 쓴다.
`app/prompts/*.yaml`

**9. 일일 토큰 한도 + 감사 기록**
`analysis.daily_token_limit`을 넘으면 새 분석 실행 자체를 차단한다 (`/config/status`에서 사용량
확인). 완료된 모든 호출은 요청 문서, Knowledge 근거, System Instruction, AI 에 실제로
전달된 입력 JSON과 원본 응답, 모델·캐시·생성 설정, BM25 후보 순위·점수를 분석 상세 화면에서
그대로 열람할 수 있어 비용과 판단 근거를 사후 검증할 수 있다.
