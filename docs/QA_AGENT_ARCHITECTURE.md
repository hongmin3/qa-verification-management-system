# QA 점검 구조와 공용 자료

> 상위: [문서 지도](README.md) · [QA Agent 화면](modules/qa-agent.md) · [QA Intelligence 엔진](modules/daily-qa.md) · [사양](../specs/qa-intelligence.md)

QA 담당자가 검토할 변경과 근거를 찾도록 Polarion 자료를 수집하고 이전 스냅샷과 비교한다. 바뀐 자료만 Claude로 분석하고 결과는 공용 DB·실행 상세·요약 메일에 남긴다. 최종 QA 판단과 원본 TC·Polarion 수정은 사람이 한다.

단일 이슈 분석은 2026-10-13 사용을 종료했다. 전용 엔진을 확장하는 옛 목표와 모델 비교 명령은 현재 구조에 포함하지 않는다. 변경 이력은 [CHANGELOG](../CHANGELOG.md), 당시 요구사항은 [SPEC](../SPEC.md)의 폐기 카드에 남는다.

## 1. 실행 흐름

```flow
제품별 일일·주간 예약 또는 지금 실행 -> 분리 프로세스 -> 제품 잠금
제품 잠금 -> Polarion 읽기 -> 제품별 스냅샷 비교 -> 변경 이벤트 저장
변경 이벤트 저장 -(분석 대상 없음)-> NO_CHANGE·Claude 호출 0회
변경 이벤트 저장 -> 후보와 작업 묶음 -> Claude CLI·제품 규칙 Skill -> 형식·근거 검사
형식·근거 검사 -> Finding·감사 기록 -> 대시보드·실행 상세·메일
Finding 상세의 수동 요청 -> TC 점검·검증 TC 초안
분리 프로세스 -(실패·한도·중단)-> 사유·진행 숫자·저장 결과 보존
```

핵심 앱은 FastAPI·Jinja2·SQLite로 구성한다. 웹 서비스와 예약·수동 분석은 프로세스를 분리한다. `services/*` 하위 서비스는 자체 프로세스와 DB를 사용하며 공용 DB를 직접 읽지 않는다. 결합 범위는 URL 링크와 nginx 경로다([공용 구조](SHARED_PLATFORM_ARCHITECTURE.md)).

## 3. 검색과 규칙

정확한 식별자가 있는 후보를 먼저 고르고, 나머지 후보는 BM25로 찾는다. 서로 다른 점수를 더해 순위를 만들지 않는다. 작업별 후보와 본문·근거를 먼저 읽고 근거 부족이나 충돌이 있을 때 검색 범위를 넓힌다. 같은 작업의 공통 형식을 반복해서 읽지 않도록 Skill이 안내한다(REQ-QAINTEL-011).

현재 분석은 제품 설정과 제품 규칙 Skill을 사용한다. `app/core/qa_rules.py`의 제품 규칙 읽기·발췌, `/qa-agent/rules`의 구현 현황은 공용 기능으로 유지한다. 규칙이 허용하지 않는 자동 확정과 실제 환경 판단은 초안으로만 남는다.

현재 이슈 상태 점검은 변경 이력이 없는 기간에도 자료를 읽어 검토할 내용을 제시한다. 기본 자동 분석은 TC·매뉴얼 원문을 보내지 않는다. TC 점검·검증 TC 초안·사양–TC 연결·매뉴얼 누락 후보는 사용자 요청 경로를 따른다.

## 4. 모델과 외부 전송

QA 점검은 서버의 Claude CLI와 격리 작업 폴더를 사용한다. 읽기·검색과 결과 파일 쓰기만 허용하고 명령 실행·웹·MCP는 막는다. 전송 전 마스킹한 입력과 Claude의 읽기·검색 기록을 실행별로 남긴다([보안 통제](SECURITY_AI_AGENT.md)).

매뉴얼 개정 검증은 공용 `app/core/gemini_client.py` 통로를 사용한다. 기본 제공자는 설정된 Claude CLI이고 Gemini도 선택할 수 있다. 해당 경로는 도구 없는 구조화 응답을 받으며 quick 뒤 필요한 경우 detail 판정을 수행한다.

모델·추론 정도는 실행 시작 때 정한 값으로 고정하고 감사 기록에 남긴다. 공용 모델 설정의 저장은 서버 안에서만 허용한다(REQ-AICALL-007). 자동 점검의 일일·주간·중지 정책은 일반 사내 웹에서 제품별로 저장한다(REQ-QAINTEL-038).

## 5. 저장과 결과 재사용

실행·제품·이벤트·Finding을 구분해서 저장한다. Claude가 만든 번호와 근거는 현재 자료로 다시 검사하며 이전 승인 상태를 새 실행으로 복사하지 않는다. 같은 작업의 입력·규칙·자료·모델·출력 형식이 모두 같고 성공 검사를 통과한 경우만 결과 저장본을 다시 쓴다(REQ-QAINTEL-037).

저장본을 다시 읽을 때도 결과 형식과 근거를 검사한다. 조건이 다르거나 자료 접근·캐시 조회에 문제가 있으면 새 분석 경로로 간다. 저장본 저장 실패는 이미 성공한 결과를 유지한다. 화면은 재사용 수와 새 Claude 호출·토큰·비용을 구분하며 원본 실행을 연결한다.

## 6. 예약·한도·중단

일일 모드는 매 업무일, 주간 모드는 매주 첫 업무일에 분석과 메일을 수행한다. 공휴일·추가 휴일은 로컬 표로 판단한다. 놓친 예약은 선택한 실행일 당일에 한 번만 만회한다. 서버 예약 비활성화는 제품별 화면 설정보다 우선 적용한다.

사용량 한도 뒤 자동 재개는 일일 모드에서만 한다. 주간 대기 분석은 다음 주 예약 또는 수동 실행에서 이어 간다. 자동 중지 중에는 수동 분석은 가능하지만 메일은 생략한다. 자동 중지로 진행 중인 분석을 강제로 종료하지 않는다.

현재 실행의 [분석 중단]은 실행·제품·잠금·프로세스 신원을 확인한 뒤 협력적 요청으로 종료한다. 메일 단계에 들어간 실행은 중단하지 않는다. 중단 시 이미 저장한 자료와 결과·사용량은 보존하며 미처리 이벤트는 대기로 남긴다(REQ-QAINTEL-036).

## 7. 폐기 경계와 남기는 자료

단일 이슈 분석의 전용 화면·API·엔진·응답 검증·승인 UI·프롬프트·모델 비교 명령은 제거한다. 옛 대기 작업은 다시 실행하지 않고 기록을 보존한 채 끝낸다. 분석·입력·결과·승인·사용량의 과거 DB 행은 삭제하지 않는다(REQ-QAAGENT-016).

공용 Polarion 본문·식별자 유틸, Regression 축 상수, 제품 지식 수집과 규칙 현황은 현재 사용처가 있으므로 유지한다. 모든 변경은 [SPEC](../SPEC.md)와 [QA Intelligence 사양](../specs/qa-intelligence.md)의 요구사항·테스트 추적을 따른다. 현재 설치·실행·전송 증거는 [progress](../progress.md)에 따로 남긴다.
